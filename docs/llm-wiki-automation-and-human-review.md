# LLM Wiki 与 Obsidian：自动整理和人工参与的边界

更新日期：2026-09-29。本文比较工作流程，不涉及 Elsewhen 与 Obsidian 的同步。

## 结论

LLM Wiki 的核心是保留原料，让 AI 持续维护可追溯的知识网络。Obsidian 提供 Markdown 阅读、编辑、双向链接和导航；AI Agent 负责摄取、归纳、关联和维护。Obsidian 本身不会自动完成这些工作。

Elsewhen 已按这个边界对齐：单篇提炼和跨资料主题自动保存为参考知识，后台发现冲突、陈旧和重复候选。人工确认集中在个人规则与受保护内容的修订，不需要逐篇审批普通新增产出。当前仍是有界整理，不能视为全库知识质量已验收。

## Obsidian 配合 LLM Wiki 的实际用法

依据 [Karpathy 的 LLM Wiki 原始说明](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)，这是工作模式，不是一个自带后台任务的 Obsidian 插件。Agent 与 Obsidian 同时操作、展示同一份 Markdown 知识库。

1. **收集**：人选择材料，放入原料目录，保留原始内容。
2. **摄取**：人要求 Agent 处理一份或一批材料。Agent 生成摘要，更新概念、实体、主题页面，补索引、出处和变更日志。一篇原料可以影响多张页面。
3. **使用**：人在 Obsidian 阅读、沿链接探索，也向 Agent 提问。Agent 查阅 Wiki，综合带出处的答案；值得保留的答案可以写回 Wiki。
4. **维护**：人定期发起检查，Agent 找出矛盾、过时结论、孤立页面和缺失链接，再组织修订。

原始实践偏向逐份摄取、人在过程中指导，也允许批量处理。目录监听、定时检查、后台任务是可加的实现方式。**由人发起摄取，不等于每次页面更新都要人点采纳。**

原料和产出都应可供人阅读。原料用于核对证据；产出用于归纳、比较和检索，同时服务人和 AI。整理后的参考知识不自动等于“我认可的个人规则”。

## 与 Elsewhen 当前实现对照

| 环节 | 当前实现 | 边界或差距 |
| --- | --- | --- |
| 原料 | 保存原文、来源快照和版本；导入有预览与确认 | 用户决定收集范围，产出不能覆盖原料 |
| 事件整理 | 原始事件先落库，后台分析与知识整理随后运行 | AI 失败不影响原始记录 |
| 来源整理 | 应用运行、模型可用时，后台处理符合条件的来源版本，生成适合的方法、案例或原则，或跳过 | 自动保存为参考知识；有去重、租约和失败退避 |
| 人工保护 | 尊重人工待确认或拒绝的提案、正文修改、已确认属性与规则 | 自动化不会绕过这些选择 |
| 按需提炼 | 可选“提炼知识”的新增参考产出直接保存 | 历史人工待审/拒绝决定仍有效；涉及人工编辑或确认内容时保留待审 |
| 信息组织 | 原文、产出、关联、来源与修订分区展示 | 来源与产出有可追溯联系 |
| 知识使用 | 检索、选材、引用进入对话等流程 | 效果仍须用真实问题和已有数据库验证 |
| 跨来源整理 | 后台结合相关资料创建或修订共享主题，至少引用两份独立来源；原料与主题互相可达 | 每次最多 8 份来源、3 个已有主题；关键词检索可能漏召回，不自动合并实体 |
| 维护 | 来源/断链检查之外，后台生成带逐字摘录的冲突、陈旧、重复提示；来源变化后旧提示失效 | 是待核对线索，不裁定真伪；未变化来源每 30 天最多重查一次 |

“后台自动”指当前应用中的工作器运行；不是应用关闭后仍有独立服务持续处理。也不意味着普通 AI 对话结束后，会有任务替它继续兑现“稍后回复”的承诺。

## 推荐的自动化与人工边界

下表说明推荐的职责分工；具体实现范围以以上对照表和测试记录为准。

| 工作 | 推荐方式 | 人的参与 |
| --- | --- | --- |
| 确定收集范围和整理目标 | 人发起或配置 | 决定哪些材料值得纳入、要解决什么问题 |
| 已授权材料入库、快照和来源记录 | 自动 | 异常时查看或纠正 |
| 摘要、分类、提炼参考知识 | 自动保存，允许修改、拒绝和追溯 | 不必逐篇采纳普通新增参考产出 |
| 索引、链接、候选关联、重复检测 | 自动 | 有歧义的实体合并交人判断 |
| 跨资料主题页 | 自动综合，逐项保留出处和不确定性 | 人可纠正；不能覆盖人工确认的结论 |
| 冲突、陈旧、失效来源检测 | 自动检查和标记 | 对需要采信的争议结论作判断 |
| 无人工修改的生成参考页更新 | 自动、保留修订记录 | 可查看变化和恢复 |
| 用户写过或确认过的重要内容变更 | 先生成差异 | 确认实质修改 |
| 升级为个人规则 | AI 可提议 | 明确确认“这适用于我，我决定采用” |
| 删除原料、不可逆合并、对外发布 | 生成可检查的操作内容 | 确认执行 |

当前人工确认还承担对话写操作的权限边界。因此，取消新增参考产出的逐项采纳，不应顺带取消对话中修订、导入、归档等动作已有的确认机制。

## 以“构建 IP 系统的底层逻辑”为例

理想流程是：收藏文章 → 保留原文 → 自动提炼参考方法 → 关联到 IP、定位、内容生产等主题 → 与已有材料比较 → 以后提问时综合引用。

如果两篇文章对定位有不同建议，系统应并列条件和出处，不静默选一条当作真理。当用户决定“以后我的内容就按这个方法做”，才确认个人规则。

当前已有原文、方法产出、跨资料主题和来源关联链路。后台找到相关原料时会尝试主题整合；材料不够时允许没有主题。历史人工待确认或拒绝的提案不会被自动采纳，已有 IP 方法与待审修订也继续保留。

## 已对齐与剩余边界

已统一新增参考产出的自动保存，补齐跨资料主题维护和内容检查，后台更新会刷新已打开的知识视图。全局审阅只列待确认提案，已完成产出回到页面阅读。

全文分块阅读、逐页面来源更新、策略升级重算、失败退避均自动执行；普通对话保存引用知识会继承结构化出处。对话和提案修订现在遵守相同的规则强度与过期确认校验。

需要人的判断仍集中在：采纳人工页的修改、选择适用条件、判断冲突是否解决、确认规则，以及预览确认共享主题合并/拆分。局部采纳只在来源不变时使用；历史正文恢复也经过提案确认。后台不会擅自归档主题或提升规则。

仍需真实材料评估召回、归纳和提示的准确度。超容量主题保留正文并提示人工预览拆分。当前没有自动裁定冲突、自动合并实体或关闭应用后独立运行的服务。实现和验证边界见 [缺口交付核对](llm-wiki-implementation-gaps.md)。

来源重新认可后的过期依赖更新自动恢复；人工纠正中间知识后，下游自动标记待复核并暂停有效引用。排除或替换来源、确认下游修订、关联冲突的解决修订由人决定。处理历史与原料整理队列均可在现有页面内查看，见 [R01–R06 实现范围](llm-wiki-implementation-gaps.md)。

## v9 补齐后的分工（2026-09-30）

| 工作 | 自动部分 | 人工参与 |
| --- | --- | --- |
| 上游纠正传播 | 标记过期，按依赖顺序准备修订，保留拒绝记录 | 查看正文与适用条件，逐项或每批最多 20 项确认 |
| 阅读与采用 | 保存状态，筛选列表，记录生成元信息和版本号 | 标记阅读/使用进度，比较并选择采用版本 |
| 主题结构整理 | 保存历史、校验撤销基准与后续引用 | 预览后确认；需要时发起整批撤销 |
| 普通建议反馈 | 保存追加历史，将本会话最近有效反馈供后续回复参考 | 选取建议后接受、忽略、改写或撤回 |

这些操作都不是每份资料必须完成的前置步骤。普通参考知识仍自动整理，用户按实际使用需要参与。Obsidian 本身不会提供这套后台任务，本文也没有引入 Obsidian 同步。实现与规模边界见 [评估文档](llm-wiki-scale-and-refactoring.md)。
