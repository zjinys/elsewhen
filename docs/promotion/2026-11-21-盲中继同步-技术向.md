# 多端同步，但中继是盲的

> 目标渠道：GitHub README / Linux.do / r/selfhosted（技术向）
> 切入点：C——盲中继同步做技术信誉素材
> 注：发布前请对照 relay 实现核对技术细节描述（分片、加密、恢复语义），确保无过度承诺

## 正文

"本地优先"这个赛道有一个照妖镜问题：**同步。**

数据存本机，大家都会说。但一个 local-first 应用一旦有了第二个设备，麻烦就来了——同步怎么办？翻翻市面上同类产品的做法，基本三种：

1. **官方云同步。** "你的数据存在你自己的设备上"，除非你开了同步——然后你的全部数据躺进厂商的数据库。本地优先的承诺在同步这一刻作废。
2. **第三方网盘。** 把同步问题外包给 Dropbox/iCloud，加密状态看运气，冲突处理看缘分。
3. **自己搭。** Syncthing 很好，但你不能要求每个用户都会配。

这三种的共性是：**同步链路上总有一双看得见的眼睛。**

### Elsewhen 的选择：盲中继

Elsewhen 是一个本地优先的个人事件系统（记录 → AI 分析 → 知识库），Rust 核心 + Flutter 界面，多端同步是刚需——我的记录在手机、台式机、笔记本之间必须一致。

同步架构上我们没做"可选云"，而是做了一条**盲中继（blind relay）**：

- 中继是一个可以自托管的小服务，它只负责**转发加密数据分片**
- 它没有能力解密、没有能力重组、没有能力读懂任何一条你的记录
- 数据的权威方是你的设备：快照、增量、恢复语义全部由端侧决定，中继只是数据面的一条管道
- 喜欢折腾的话，一条命令把 relay 跑在你自己的 VPS 上，从此链路上唯一的"第三方"是你自己

换句话说：多设备体验和云同步产品一样——装上、配对、传完就能用——但架构上没有"厂商数据库"这个环节存在。

（截图位：relay 侧日志/抓包，展示中继视角下数据的不可读性）

### 为什么做这么"狠"

因为 Elsewhen 存的东西决定了它必须这样。这是一个**个人事件系统**：你随手记的每一句话、每一次分析、每一个目标偏差，都在里面。这种数据给云同步，等于把整本日记交给一个商业实体保管。

所以同步层的设计目标从一开始就不是"方便"，而是"**链路上不存在能读你数据的一方**"。盲中继是结论，不是妥协。

### 顺带说下工程上比较有意思的部分

- 同步以**分片**为单位增量传输，传输窗口有前台服务保活（国内 ROM 冻结后台进程的问题单独处理过）
- 配对、初始快照、后续增量各有明确的恢复语义：中断可以续，过期 claim 会被标记为"不确定"而不是默默重放
- 中继本身无状态倾向，重建容器不丢数据（数据卷独立）

这套东西的详细设计文档会陆续开源在仓库 `docs/roadmap/` 下（同步数据面 v3、配对收敛、生命周期边界各有一份）。

如果你在做 local-first 产品，或者你只是想要一个"多端同步但没人能偷看"的个人记录系统，欢迎交流。
