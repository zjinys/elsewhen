### 重新制作副本

Linux 上从仓库根目录运行以下命令；如果应用使用自定义数据目录，先替换 `LLMWIKI_SOURCE_DB`。

```bash
export LLMWIKI_SOURCE_DB="$HOME/.local/share/elsewhen/elsewhen.db"
export LLMWIKI_TEST_ROOT=$(mktemp -d /tmp/elsewhen-wiki-real-data.XXXXXX)
python3 - <<'PY'
import os
import sqlite3
from pathlib import Path

source = Path(os.environ['LLMWIKI_SOURCE_DB']).resolve()
root = Path(os.environ['LLMWIKI_TEST_ROOT'])
assert source.is_file(), f'数据库不存在：{source}'
root.chmod(0o700)
run = root / 'run'
run.mkdir(mode=0o700)
with sqlite3.connect(source.as_uri() + '?mode=ro', uri=True) as original:
    with sqlite3.connect(root / 'elsewhen.db') as baseline:
        original.backup(baseline)
with sqlite3.connect((root / 'elsewhen.db').as_uri() + '?mode=ro', uri=True) as baseline:
    assert baseline.execute('PRAGMA quick_check').fetchone()[0] == 'ok'
    with sqlite3.connect(run / 'elsewhen.db') as working:
        baseline.backup(working)
for path in [root / 'elsewhen.db', run / 'elsewhen.db']:
    path.chmod(0o600)
print('参考副本：', root / 'elsewhen.db')
print('测试目录：', run)
PY
```

不要在数据库运行时分别复制 `.db`、`-wal`、`-shm`，它们可能来自不同时间点。backup API 会生成一致快照，并把 WAL 中已提交的数据纳入副本。

## 4. 提炼已有文章，再比较回答

先测默认流程：打开原料页“产出”，不点击提炼。应用后台应自动把未处理版本整理为参考知识，材料不足时允许不生成；可在全局“知识审阅 → 自动整理与洞察记录”核对任务结果。重复进入或重启不应重复生成，失败会退避；原文仍在“原文”分区。不要把原料数量与知识页数量强制对应。

本次 IP 页已有人工采纳方法及一条待审修订，后台会尊重这两项决定。打开 IP 原料“产出”应直接看见既有方法；打开方法“关联”应有原料入口，来源仍指向第 1 版，无需重做。需要验证首次自动整理时，选择副本中尚无人工提案/定稿的其他现有原料。

定向提炼作为可选对照：

1. 在 IP 原料页点击“提炼知识 → 提炼方法”。检查“产出”中的结果、适用条件和页内“查看原料”，尤其看有没有把作者观点改写成普遍真理或你的个人事实。
2. 没有对应知识页时，新参考产出直接保存，无需再次采纳；没有人工修改或确认的参考页也可自动更新。IP 方法已有人工采纳记录，其修订仍待确认；点击“确认修订”后留在原料页。历史人工待审/拒绝提案不会借此次点击自动采纳。
3. 查看“来源与修订”：必须绑定本次原料版本，新产出强度为“参考材料”，没有被自动设置为已确认规则。原料和知识互相可达；不能仅凭相近标题判断原文被替换。
4. 重新开对话问 Q2，再加一个应用问题：“我想把 IP 文章里的思路用于下一条内容，先检查哪些条件、怎么组织内容？请区分原文观点与你的建议。”
5. 比较提炼前后的回答是否更具体、出处是否更清楚、是否保留适用条件。不要把建议更长或页数更多当作效果提升。

如果想测试拒绝建议，在人工修改过的知识页使用“检查更新”，对待审修订点“拒绝建议”；重新打开应保留原正文与拒绝决定。普通新增参考产出已直接保存，不再提供“保存前拒绝”这一步。升级“已确认规则”时，应有单独的确认框；取消不会改变已保存强度。

### 跨资料主题与内容检查

从副本已有原料中挑选两篇确实相关的文章，例如 IP 定位、流量与内容生产；先记下各自的共同点、分歧和适用条件。如果只有一篇相关原料，将跨资料质量标为“材料不足”，不要人为挂接无关页面。

1. 保持应用开启，在“知识审阅 → 自动整理与洞察记录”查看“主题整理与检查”。不需要点击单篇提炼，也不需要新增人工后台启动按钮。成功但产出为 0 允许出现，是否漏掉有价值主题需要另记质量问题。
2. 打开两篇原料的“产出”。若生成共享主题，应看到同一张标有“跨资料主题”的页面，而不是两份同名摘要。打开主题的来源，至少有两个独立原料和精确版本；两篇原文仍完整。已经打开的列表和产出应在后台保存后刷新。
3. 提问“我的 IP 材料对定位和内容生产有哪些共同建议，哪些取决于阶段？请引用资料。”核对共享主题是否帮助比较和应用，是否保留分歧，而不是把文章观点说成个人事实。
4. 在“来源与内容检查”查看冲突、陈旧或重复候选。每项应标明“待核对（AI 提示）”并带原文摘录；逐项回到来源确认摘录存在、判断是否成立。没有真实问题时允许无提示。忽略后当前提示不再出现，来源变化后旧提示失效。
5. 重启副本应用，已成功处理的同一版本在 30 天复查周期内不重复请求；新来源版本可以触发重新整合。更新同一主题时必须保留旧来源身份，并指向各自最新版本；之前回答的旧引用仍可查看。

当前相关主题发现每次最多选 8 份来源和 3 个已有主题。长文按块阅读全文并缓存归纳，来源变化另按依赖页逐一维护，保留混合事件依据。超容量主题需要在产出页预览拆分。仍须检查归纳有没有遗漏尾部条件、反例和否定，不以“全文阅读完成”或“没有报错”当作质量通过。

## 5. 复测页内空回复、空头承诺与追问进度

在操作副本打开 Omni flash 原料页及其已有 AI 会话，查看历史中的更新请求和空回复。先直接发 `？`，不要重新粘贴原要求：AI 应知道你在催上次的改进任务，并结合原要求继续处理或说明实际进度。不能只说“模型返回了空”，也不能要求把已有请求再发一次。退出测试应用并以同一副本重启后，可再次追问，核对任务仍能接上。

另建对话，复制当时的**真实请求**重试，作为新会话对照；旧会话续聊和新会话结果分别记录，不能混算。再做下面的明确请求与确认流程。

对照请求：

> 请根据这页原文生成一个改进版视频 prompt，保留镜头与场景限制。先完整展示改进稿，把它作为这页的派生产物供我确认保存。

按顺序检查：

1. 回复应包含可用稿件、待确认内容，或说明这次原任务还没完成。只留下“马上处理，稍后回复”并结束，记行为失败；明确未完成可通过诚实性检查，但**任务效果仍记未完成**。
2. 有待确认草稿时先发 `搞定了吗？`。应展示或解释已有草稿，说明尚未保存；不能替你确认、生成重复草稿或声称已经保存。
3. 核对草稿后明确回复 `好`。应只保存一次，能打开派生产物，素材原文仍可查看。即使最终组织话术失败，也要根据真实执行结果说明已保存或保存失败。
4. 再问 `？`，应说明刚才的保存结果，不能重新执行。同一会话取消任务后追问，或转问另一问题，不能擅自恢复已取消的旧任务。

本地自动化场景可从仓库根执行 `cargo test --all-targets`、`cargo build --release`，然后在 `ui` 目录执行 `fvm flutter test --no-pub test/conversation_continuity_bridge_test.dart test/knowledge_bridge_test.dart test/knowledge_integration_bridge_test.dart test/knowledge_flow_test.dart --reporter expanded`。这些测试用独立临时库和本地脚本化 Provider 覆盖持续预告、空回复、旧会话追问、自动整理及确认，不是现有模型的效果评分。

若失败，记录准确时间、会话/页标识、用户请求、UI 结果，并保存同一时段的 `agent-debug.log`。现有日志可以看到部分轮次和工具结果，但缺少逐请求 `finish_reason`、推理用量等信息；因此历史 `token_usage` 的累计数字不能单独证明是推理耗尽还是工具循环未收敛。详细原因和建议改法见 [调查复核](../notes/implemented/bug-fix/2026-09-29-empty-reply-root-cause-investigation.md)。

## 6. 拒绝、来源更新与人工保护

这些操作都在副本里做，记录操作前后的页面与回答。

### 不认可来源

对 IP 原料页在“来源与修订 → 来源 → 材料评价”选择“不认可”，新开对话重复应用问题。该材料及其依赖方法不能继续作为正面依据推荐；明确询问它为何不被采用时，可以展示原文并解释状态。旧回答的历史引用仍应保留。

查看“知识审阅”的来源问题。“忽略提示”只处理提醒，不应自动恢复材料效力。完成后在副本中取消“不认可”，再继续其他测试。

### 有真实新版本的来源

选择你实际会重复导入、且内容已经变化的同一 URL 或同一路径文件：预览差异 → 取消并核对旧版本 → 再预览并确认 → 查看两个原料版本。人工确认过的依赖方法正文应保留并提示复核，点方法页“检查更新”，核对新建议后确认。

没有发生真实来源变化时，这项填“暂不可测”，不要为了凑通过率改动真实材料，也不要期待重复抓取同一篇未更新推文凭空生成新版本。历史 `note` 若按无 URL 文本识别，粘贴改写稿可能成为新原料，不能当作同源版本测试。

接受修订后重新问相关问题，引用应对应新版本；以前的回答仍能打开旧版本。可以先保存一条成功引用的回答作为对照。纯自动生成、尚无人编辑或确认的参考知识可随新来源版本自动更新；人工定稿和个人规则需要你确认更新。

### 人工编辑期间的旧建议

在新方法页生成待审修订，暂不确认；手工添加一条实际需要的备注并保存，再接受旧建议。应提示版本已变化，保留人工备注，要求重新审阅。若该方法曾升级为规则，重新生成后点击“确认修订”表示同时确认修订后的规则和适用条件；规则强度保留，不静默降级。尚未点击时规则正文不变。

## 7. 用已有事件观察自动积累

先看“设置 → 数据 → 知识消化 → 查看队列与运行日志”。不要把“副本启动后没有重处理全部 90 条事件”判成失败：已确认成功或跳过的任务不会因为重启重新执行，历史无待处理项时可以没有新页面。

在日常使用中选择可以发送给当前 Provider 的真实事件继续记录；若只在副本测试，新增记录不会同步回日常库。新事件立即保存，知识消化有 10 分钟沉淀窗，并等待分析/到期重试。错误应能查看，重启后任务能继续；不手工改数据库时间或清空任务表。

在“知识审阅 → 自动洞察运行记录”检查自动洞察。每日节奏和有界窗口意味着它不会每发一条消息就产生一条洞察；成功且结果为 0 允许通过运行检查。质量另记：是否有准确事件支持、是否重复旧结论、是否给出有用的新观察、是否过早给人下定论。

连续记录 7 天时，每天保留 3 个实际提问及其结果，重点统计“知识库帮我省了什么”“哪里仍需自己找材料”“哪条建议必须纠正”，不要以知识页或洞察数量作为主要指标。

## 8. 本地记录表与判断标准

把结果保存在测试目录里的 Markdown，不把原始私密回答写入仓库。每个问题记录：

| 项目 | 内容 |
| --- | --- |
| 环境 | 时间、Git 提交、模型、测试副本、是否旧会话 |
| 输入 | 原始问法、预期材料和版本、事先写好的正确要点 |
| 输出 | 完整回答、实际引用、错误提示、是否需要重试 |
| 准确度（0–2） | 0：关键事实错误；1：遗漏重要条件；2：事实和条件完整 |
| 引用（0–2） | 0：缺应有出处或错误出处；1：仅部分结论被支持；2：出处和版本支撑结论；无需引用时填“不适用” |
| 实用性（0–2） | 0：无法使用；1：需较多修改；2：能用于当前任务 |
| 修正成本 | 改了什么、花了多久、是否为命中材料而改变问法 |

Q1、Q2、Q3 至少各用新主对话重复 3 次，保留全部结果。建议初次验收要求：Q1/Q3 三次都准确且有有效引用；Q2 至少两次找到合适依据；没有把外部事实当个人经历、绕过确认、覆盖原文或拒绝后继续正面采用的问题。

同时单列数据缺口：缺原料、缺适用条件、来源过期、无事件依据。修好数据后再测，才能区分“检索算法没找到”和“这条知识本来就不满足使用条件”。

7 天后用绝对数量加比例报告，例如“12 个相关问题中 9 个找到有效材料，3 个漏召回”；同时列出错误引用、空回复、人工修正耗时。程序回归命令仍是仓库根的 `cargo test --all-targets` 和 `ui` 目录的 `fvm flutter test --no-pub`，与这份真实效果记录分别保存。


## 9. 本轮新增能力：用现有材料复测

先按前文备份并启动副本，避免修改原库或重复使用已改变的数据作对照。2026-09-29 只读统计：当前库 49 页、21 份当前原料，其中 9 份超过 1400 字、3 份超过 6000 字，适合直接选择长文样本。

1. **全文处理**：从长文章末尾挑一个重要限制/反例，记下原句。保持应用开启，在“知识审阅 → 自动整理与洞察记录”观察材料标题、版本、分段范围与完成原因。中途关闭再打开，应从未完成片段继续。对照最终知识是否保留该限制，不能仅看任务成功。
2. **再次引用**：就同一知识问两种表达（如“目标用户”和“受众”），检查引用片段是否在相关位置。让 AI 将回答保存为方法，核对草稿的来源与适用条件，确认后在新对话检索。无出处笔记不应显示为已继承依据。
3. **来源更新**：只在副本更新原文。查看依赖页的来源版本；普通参考应自动更新，人工修改页/规则应保持正文并产生修订。不要为测试删除既有人工拒绝决定。
4. **审阅**：对来源不变的修订展开“逐段审阅”，只选一处修改，确认其他段落未变化；需要时勾选本次解决的提示。来源改变时应要求完整确认。个人规则修订后强度保持不变。
5. **恢复**：在“来源与修订”展开知识页历史，生成恢复提案，再到产出页确认。应恢复所选正文，原料历史不回退，当前来源和规则强度保留。
6. **主题整理**：在共享主题的产出页展开“整理主题结构”，预览拆分或选择其他主题预览合并。确认前不改变页面；确认后旧主题归档，仍能沿关联查看新页和全部来源。核对有没有丢掉原先有价值的条件。
7. **预算与费用**：Provider 设置增加“上下文窗口”和“输出上限”。填写该中转实际可用上限。未填写时使用保守默认；未知 tokenizer 可能提前拒绝过长请求。观察真实 usage 和等待时间，记录一次长文需要多少调用。此项需要你启用的模型，迁移检查本身不调用模型。

本轮已执行的现有数据验证：从原库只读备份到临时目录，在副本升级 v5→v7；104 条原始事件、32 份原料快照正文逐条一致，SQLite 完整性检查通过。这是数据与迁移验证，尚未执行上述真实模型质量评分。


## 10. 来源修复与维护闭环：继续使用自己的材料副本

仍在前述操作副本中测试。选一张引用两份原料的现有主题，先记下两份原文和主题当前正文。若没有合适的共享主题，先等后台结合相关材料生成；不要为了凑测试而假造个人事实。

| 场景 | 操作 | 应观察到的结果 |
| --- | --- | --- |
| 移除无效来源 | 将其中一份原料标为不认可；主题 → 来源与修订 → 修复来源依据，只保留有效原料，或选择另一份替代材料 | 先出现待审修复；确认前主题不变；确认后来源集合与正文一起更新，原料仍在 |
| 剩余依据不足 | 不选任何原料，且知识没有有效事件依据 | 提示补充有效材料，不产生无依据的新知识 |
| 重新认可 | 在来源有新版本、依赖仍旧且任务被跳过的情况下，重新认可该来源，保持应用运行 | 后续知识 tick 自动恢复必要检查；人工拒绝过的提案不会因此被采纳 |
| 人工纠正传播 | 从方法/主题生成一个产物；修改上游正文或适用条件 | 产物出现上游变化提示并暂停有效引用；检查更新使用新条件，确认后提示消失 |
| 两级产物 | 再从第一个产物生成第二个产物，然后纠正最上游知识 | 两级均待复核；先确认上游产物，再处理下一层 |
| 跨页冲突 | 在一个有冲突提示的原料页展开关联解决记录；选择覆盖双方来源的主题，核对其当前修订并说明分歧如何处理 | 确认后提示从待办消失；原料页和主题页的处理记录都可查看说明与对应修订 |
| 完整历史 | 展开处理记录，查看一次采纳、一次拒绝或忽略 | 可核对原建议、实际结果和处理状态；新记录保留修改前正文，旧记录缺失的部分不伪造 |
| 后台解释 | 打开知识审阅 → 整理队列，切换等待/跳过/待处理，必要时加载更多 | 未开始或等待长文阅读的任务也可见；点任务能回到对应页；刷新列表不会主动运行模型 |

对生成质量额外核对：移除 A 后，正文是否仍错误沿用只由 A 支持的说法；人工新增的限制是否进入下游；冲突解决说明是否真的解释了各自条件。通过流程测试不能代替这些判断。

本次在此前现有数据副本的另一份临时副本上执行 v7→v8 迁移，104 条事件和 32 份快照正文逐条一致，完整性检查通过。没有启动个人原库或调用真实外部模型；以上材料质量场景仍由实际使用验收。


## 11. v9 功能与规模回归

在已有资料副本上，可依次检查：

1. 在「来源与修订」设置已读或值得使用，再到浏览区按阅读状态筛选；检查原文不变。
2. 从同一原料的页内对话保存两版同类型产物，在产出区展开比较并采用一版；修改产物后检查旧采用修订仍可读取。
3. 修改上游方法，等待后台准备直接下游修订，再在知识审阅中批量确认；下一层应在上游确认后准备。
4. 合并或拆分主题，查看方案历史，再撤销：旧主题恢复、新主题归档。若先编辑新主题，撤销应失败并保留编辑。
5. 对回复中的一段建议反馈忽略或改写，再继续同一会话；确认反馈能读取/撤回，且没有自动执行建议。

数据量不足时，运行 `synthetic_wiki_scale` 合成测试，步骤和限制见 [规模评估](../llm-wiki-scale-and-refactoring.md)。功能测试不代替真实模型质量验收。
