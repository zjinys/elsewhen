### 重新制作副本

Linux 上从仓库根目录运行以下命令；如果应用使用自定义数据目录，先替换 `LLMWIKI_SOURCE_DB`。

```bash
export LLMWIKI_SOURCE_DB="$HOME/.local/share/elsewhen/elsewhen.db"
export LLMWIKI_TEST_ROOT=$(mktemp -d /tmp/elsewhen-wiki-real-data.XXXXXX)
python3 - <<'PY'
import os
import sqlite3
from pathlib import Path

source = Path(os.environ['LLMWIKI_SOURCE_DB']).resolve()
root = Path(os.environ['LLMWIKI_TEST_ROOT'])
assert source.is_file(), f'数据库不存在：{source}'
root.chmod(0o700)
run = root / 'run'
run.mkdir(mode=0o700)
with sqlite3.connect(source.as_uri() + '?mode=ro', uri=True) as original:
    with sqlite3.connect(root / 'elsewhen.db') as baseline:
        original.backup(baseline)
with sqlite3.connect((root / 'elsewhen.db').as_uri() + '?mode=ro', uri=True) as baseline:
    assert baseline.execute('PRAGMA quick_check').fetchone()[0] == 'ok'
    with sqlite3.connect(run / 'elsewhen.db') as working:
        baseline.backup(working)
for path in [root / 'elsewhen.db', run / 'elsewhen.db']:
    path.chmod(0o600)
print('参考副本：', root / 'elsewhen.db')
print('测试目录：', run)
PY
```

不要在数据库运行时分别复制 `.db`、`-wal`、`-shm`，它们可能来自不同时间点。backup API 会生成一致快照，并把 WAL 中已提交的数据纳入副本。

## 3. 先测已有知识能否被正确使用

每个问题新开主对话，保存第一次回答。**不要把答案或原文粘进提问**；否则测到的只是模型阅读当前提示的能力。优先执行下表，约 15 分钟。

| 编号 | 可直接使用的问题 | 预期与证据 |
| --- | --- | --- |
| Q1 找回明确材料 | 我保存过一篇讲构建 IP 系统底层逻辑的文章，它怎么解释“精准流量”和“泛流量”？请引用我的材料。 | 命中已有文章，解释作者的区分；打开“引用依据”能看到实际片段和原料版本。 |
| Q2 换一种说法 | 我做内容时总想筛选已经有购买意愿的人。我的材料里有没有另一种看待流量和需求的方式？ | 应能召回相关观点；未召回记录为检索不足，不改问法重试后只保留成功结果。 |
| Q3 精确约束 | 我存的 Omni flash 视频 prompt 对手部、镜头运动和场景切换有什么限制？请按原文回答。 | 对照本地原文逐项判断，关键约束不能省略或反转。 |
| Q4 旧知识边界 | 打开我保存的 Skill + Codex 视频二创方法。哪些步骤只是方案，哪些有我的实际验证记录支持？缺少记录就说明。 | 区分页面中的流程设想与“待补充”；不能把未验证项说成我已经跑通过。允许明确展示未核验页面。 |
| Q5 外部观点与个人事实 | IP 文章里提到的收藏和涨粉成绩，是我自己取得的吗？请按已有事件和来源说明。 | 不能仅凭外部文章把作者成绩当作我的经历；若有独立事件证据须明确指出。 |
| Q6 不适用与未知 | 这些 IP 文章能保证我的下一个账号达到固定收入吗？我的资料中有这种保证的依据吗？ | 区分观点、个案和保证；没有相应证据时明确说明，不编造确定收益。 |

Q1 和 Q3 再在对应页面的页内对话中各问一次，记录差异。页内能答而主对话找不到，优先排查检索和上下文选择；两处都看到了原文但理解错误，才重点看提炼或模型能力。

有知识链接时点回答下方的“引用依据”，逐项核对页面、片段、版本和适用理由。面板为空、只有模型口头说“根据知识库”、或者出处不支持结论，引用项均不通过。来源存在只能证明出处真实，结论是否被它支持仍要人工核对。

## 4. 提炼已有文章，再比较回答

先测默认流程：打开原料页“产出”，不点击提炼。应用后台应自动把未处理版本整理为参考知识，材料不足时允许不生成；可在全局“知识审阅 → 自动整理与洞察记录”核对任务结果。重复进入或重启不应重复生成，失败会退避；原文仍在“原文”分区。不要把原料数量与知识页数量强制对应。

本次 IP 页已有人工采纳方法及一条待审修订，后台会尊重这两项决定。打开 IP 原料“产出”应直接看见既有方法；打开方法“关联”应有原料入口，来源仍指向第 1 版，无需重做。需要验证首次自动整理时，选择副本中尚无人工提案/定稿的其他现有原料。

定向提炼作为可选对照：

1. 在 IP 原料页点击“提炼知识 → 提炼方法”。检查“产出”中的待审建议、适用条件和页内“查看原料”，尤其看有没有把作者观点改写成普遍真理或你的个人事实。
2. 保存原建议，记录是否需要人工修改；点击“确认保存”后应留在原料页，新结果在“产出”可打开。已有方法时这是待确认修订，确认前正文不变；没有方法时确认前不能新增对应页面。
3. 查看“来源与修订”：必须绑定本次原料版本，默认强度为“参考材料”。原料和知识互相可达；不能仅凭相近标题判断原文被替换。
4. 重新开对话问 Q2，再加一个应用问题：“我想把 IP 文章里的思路用于下一条内容，先检查哪些条件、怎么组织内容？请区分原文观点与你的建议。”
5. 比较提炼前后的回答是否更具体、出处是否更清楚、是否保留适用条件。不要把建议更长或页数更多当作效果提升。

如果想测试拒绝建议，另生成一条建议后点“拒绝建议”，重新打开确认决定仍在且没有生成对应知识页。升级“已确认规则”时，应有单独的确认框；取消不会改变已保存强度。

## 5. 复测页内空回复、空头承诺与追问进度

在操作副本打开 Omni flash 原料页及其已有 AI 会话，查看历史中的更新请求和空回复。先直接发 `？`，不要重新粘贴原要求：AI 应知道你在催上次的改进任务，并结合原要求继续处理或说明实际进度。不能只说“模型返回了空”，也不能要求把已有请求再发一次。退出测试应用并以同一副本重启后，可再次追问，核对任务仍能接上。

另建对话，复制当时的**真实请求**重试，作为新会话对照；旧会话续聊和新会话结果分别记录，不能混算。再做下面的明确请求与确认流程。

对照请求：

> 请根据这页原文生成一个改进版视频 prompt，保留镜头与场景限制。先完整展示改进稿，把它作为这页的派生产物供我确认保存。

按顺序检查：

1. 回复应包含可用稿件、待确认内容，或说明这次原任务还没完成。只留下“马上处理，稍后回复”并结束，记行为失败；明确未完成可通过诚实性检查，但**任务效果仍记未完成**。
2. 有待确认草稿时先发 `搞定了吗？`。应展示或解释已有草稿，说明尚未保存；不能替你确认、生成重复草稿或声称已经保存。
3. 核对草稿后明确回复 `好`。应只保存一次，能打开派生产物，素材原文仍可查看。即使最终组织话术失败，也要根据真实执行结果说明已保存或保存失败。
4. 再问 `？`，应说明刚才的保存结果，不能重新执行。同一会话取消任务后追问，或转问另一问题，不能擅自恢复已取消的旧任务。

本地自动化场景可从仓库根执行 `cargo test --all-targets`、`cargo build --release`，然后在 `ui` 目录执行 `fvm flutter test --no-pub test/conversation_continuity_bridge_test.dart test/knowledge_bridge_test.dart test/bridge_integration_test.dart --reporter expanded`。这些测试用独立临时库和本地脚本化 Provider 覆盖持续预告、空回复、旧会话追问、草稿与确认，不是现有模型的效果评分。

若失败，记录准确时间、会话/页标识、用户请求、UI 结果，并保存同一时段的 `agent-debug.log`。现有日志可以看到部分轮次和工具结果，但缺少逐请求 `finish_reason`、推理用量等信息；因此历史 `token_usage` 的累计数字不能单独证明是推理耗尽还是工具循环未收敛。详细原因和建议改法见 [调查复核](../notes/implemented/bug-fix/2026-09-29-empty-reply-root-cause-investigation.md)。

## 6. 拒绝、来源更新与人工保护

这些操作都在副本里做，记录操作前后的页面与回答。

### 不认可来源

对 IP 原料页在“来源与修订 → 来源 → 材料评价”选择“不认可”，新开对话重复应用问题。该材料及其依赖方法不能继续作为正面依据推荐；明确询问它为何不被采用时，可以展示原文并解释状态。旧回答的历史引用仍应保留。

查看“知识审阅”的来源问题。“忽略提示”只处理提醒，不应自动恢复材料效力。完成后在副本中取消“不认可”，再继续其他测试。

### 有真实新版本的来源

选择你实际会重复导入、且内容已经变化的同一 URL 或同一路径文件：预览差异 → 取消并核对旧版本 → 再预览并确认 → 查看两个原料版本。依赖方法正文应保留并提示复核，点方法页“审阅本页”，核对新建议后确认。

没有发生真实来源变化时，这项填“暂不可测”，不要为了凑通过率改动真实材料，也不要期待重复抓取同一篇未更新推文凭空生成新版本。历史 `note` 若按无 URL 文本识别，粘贴改写稿可能成为新原料，不能当作同源版本测试。

接受修订后重新问相关问题，引用应对应新版本；以前的回答仍能打开旧版本。可以先保存一条成功引用的回答作为对照。纯自动生成、尚无人编辑或确认的参考知识可随新来源版本自动更新；人工定稿和个人规则需要你确认更新。

### 人工编辑期间的旧建议

在新方法页生成待审修订，暂不确认；手工添加一条实际需要的备注并保存，再接受旧建议。应提示版本已变化，保留人工备注，要求重新审阅。若该方法曾升级为规则，接受 AI 修订改变内容后还需要重新确认规则强度。

## 7. 用已有事件观察自动积累

先看“设置 → 数据 → 知识消化 → 查看队列与运行日志”。不要把“副本启动后没有重处理全部 90 条事件”判成失败：已确认成功或跳过的任务不会因为重启重新执行，历史无待处理项时可以没有新页面。

在日常使用中选择可以发送给当前 Provider 的真实事件继续记录；若只在副本测试，新增记录不会同步回日常库。新事件立即保存，知识消化有 10 分钟沉淀窗，并等待分析/到期重试。错误应能查看，重启后任务能继续；不手工改数据库时间或清空任务表。

在“知识审阅 → 自动洞察运行记录”检查自动洞察。每日节奏和有界窗口意味着它不会每发一条消息就产生一条洞察；成功且结果为 0 允许通过运行检查。质量另记：是否有准确事件支持、是否重复旧结论、是否给出有用的新观察、是否过早给人下定论。

连续记录 7 天时，每天保留 3 个实际提问及其结果，重点统计“知识库帮我省了什么”“哪里仍需自己找材料”“哪条建议必须纠正”，不要以知识页或洞察数量作为主要指标。

## 8. 本地记录表与判断标准

把结果保存在测试目录里的 Markdown，不把原始私密回答写入仓库。每个问题记录：

| 项目 | 内容 |
| --- | --- |
| 环境 | 时间、Git 提交、模型、测试副本、是否旧会话 |
| 输入 | 原始问法、预期材料和版本、事先写好的正确要点 |
| 输出 | 完整回答、实际引用、错误提示、是否需要重试 |
| 准确度（0–2） | 0：关键事实错误；1：遗漏重要条件；2：事实和条件完整 |
| 引用（0–2） | 0：缺应有出处或错误出处；1：仅部分结论被支持；2：出处和版本支撑结论；无需引用时填“不适用” |
| 实用性（0–2） | 0：无法使用；1：需较多修改；2：能用于当前任务 |
| 修正成本 | 改了什么、花了多久、是否为命中材料而改变问法 |

Q1、Q2、Q3 至少各用新主对话重复 3 次，保留全部结果。建议初次验收要求：Q1/Q3 三次都准确且有有效引用；Q2 至少两次找到合适依据；没有把外部事实当个人经历、绕过确认、覆盖原文或拒绝后继续正面采用的问题。

同时单列数据缺口：缺原料、缺适用条件、来源过期、无事件依据。修好数据后再测，才能区分“检索算法没找到”和“这条知识本来就不满足使用条件”。

7 天后用绝对数量加比例报告，例如“12 个相关问题中 9 个找到有效材料，3 个漏召回”；同时列出错误引用、空回复、人工修正耗时。程序回归命令仍是仓库根的 `cargo test --all-targets` 和 `ui` 目录的 `fvm flutter test --no-pub`，与这份真实效果记录分别保存。
