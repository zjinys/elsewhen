# FR-PES-ARCH-002: LLM Wiki 知识库闭环技术设计

**版本**: v0.1  
**最后更新**: 2026-09-26  
**状态**: Proposed  
**关联需求**: [FR-PES-004](../product/FR-PES-004-LLM-Wiki知识库闭环.md)

## 1. 基线和边界

原 `src/wiki.rs::generate_digest` 只由 CLI 调用：读取最近 `days` 内最多 `max_events` 条事件，按 `last_digest_at` 的时间字符串过滤；成功后写游标。CLI 已随桌面构建移除，阶段 1 以事件级队列取代它（见 §2 实施记录）。`src/storage/wiki.rs::upsert_wiki_page` 合并事件 ID 并集、记录 revision，并保护人工编辑正文。`src/api/import.rs` 已将 URL 快照存入 `kind=source` 的 wiki 页；对话已有 `search_knowledge_base` 工具，页内对话能读取当前页面；洞察按固定 kind 和证据数选页。上述均保持兼容。

原 digest 游标不是处理确认：迟到记录、同时间戳、有限时间窗和批次中途失败都可能破坏完整性（实证：`LIMIT` 先于游标过滤，积压超上限时新事件永远取不到；游标写入 `now()` 而非本批最大时间，模型调用期间新增的事件被跳过）。新任务不得复用该游标作为进度依据。本文定义目标契约，表名和迁移号由实施时结合现有 schema 确认。

## 2. 事件消化任务

在事件提交成功的事务边界登记待处理事件 ID，或由后台对“事件表减已成功处理集”定期补偿；推荐事件级持久任务，唯一键 `(event_id, digest_version)`。与已有分析队列共享重试和可观测模式，但知识任务有独立状态和失败原因，不得把分析成功误当作知识消化成功。

事件级确认不能直接替换为一次事件一次模型调用：worker 将待处理事件组为有界批次，记录批次包含的事件 ID、版本与状态。先生成并校验完整提议，再在同一数据库事务中应用所有页面变更、revision、日志及批次成功确认；模型失败或校验失败不确认批次。需要把当前逐页写入及日志操作收拢到事务边界，避免部分写入后重试造成不可解释结果。若现有存储 API 暂不能支持批次事务，先采用持久批次结果 + 每项稳定幂等键 + 完成账本，并验证恢复路径，不宣称它是原子提交。

每条提议的 `source_event_ids` 必须是本批次的实际 ID；拒绝空来源或批次外 ID（明确无事件来源的知识类页面除外）。页面更新时按来源 ID 去重；非法提议进入可见失败或待审状态，不能悄悄推进批次。`--force` 走明确的版本化重处理语义，不绕开人工编辑保护。旧 `last_digest_at` 只作迁移观察字段：上线时对存量事件分批补偿或提供明确的回填范围选择，不静默假设旧游标之前均已处理。

**阶段 1 实施记录（2026-09-27）**：
- 迁移 v31：`knowledge_digest_jobs`（唯一键 `(event_id, digest_version)`，状态含 `skipped`，`failed_rounds` 记录冷却回队轮次）与 `knowledge_digest_runs`（每批一行：耗时、新建/更新/受保护页面、错误，不含事件原文）。存量事件按用户决定全量回填为 pending（全量重新消化）。
- 入队与事件写入同事务（`insert_event` / `submit_input_as_event` / 对话输入），10 分钟沉淀窗；可记录性 = 人工分类 ?? 分析结果 ?? 默认可记录，分析未终态时等待，分析最终失败仍消化。
- 批次：≤20 条、原文 ≤6000 字；整批校验（kind/slug/正文、来源编号全部属于本批且非空），通过后页面写入 + wiki_log + 任务确认 + 运行日志同一 `IMMEDIATE` 事务提交（`upsert_wiki_page_in_tx`）；任一失败整批回退、指数退避，5 次后 failed 并冷却 6 小时自动回队。
- 触发：Flutter 后台 worker 在分析队列排空后串行调用 `trigger_knowledge_digest()`；无手动入口、无重试按钮（用户决定）；设置 → 数据 → 知识消化可只读查看队列与运行日志。
- `--force` 重处理与旧 `last_digest_at` 随 CLI 移除不再适用；重处理通过升级 `digest_version` 实现。

## 3. 来源与页面关系

在 SQLite 增加独立来源实体（建议 `knowledge_sources`）存原文快照、类型、规范化出处、内容 hash、采集时间、版本及用户评价；来源与编译页用关系表连接，保留具体来源版本及可选片段。事件仍由 `events` 管理，通过事件来源关系或现有 `source_event_ids` 接入；不得复制事件成为新的可编辑原文。现有 `source` 页先作为兼容展示视图，在迁移中绑定同一来源 ID；迁移对 `source_url` 去重及无 URL 的文本素材分别设计稳定身份，回滚前保留旧页面和关联。禁止重复导入导致页面或来源重复。

知识页增加结构化 `applicable_when`、`strength` 及确认状态，仅适用于方法/案例/规律等需使用这些字段的类型；不要从 Markdown 正文正则解析权限字段。默认 `strength=reference`；只有显式确认能升至 `rule`。`opinion=reject` 的来源不作为正面证据。来源更新形成新快照版本和待审编译建议，不原地覆盖不可变旧快照；人工编辑保护沿用现有机制。

项目目录保留当前有界盘点流程：一个项目评估对应项目页和出处路径；只有显式文件模式才逐文件保存 source。目录增量快照及状态建议属于后续独立设计，不是来源层上线前置条件。

## 4. 共享选材契约

实现 Rust 侧候选检索接口：输入当前问题、任务类型、可选实体/话题线索和字符预算；输出 `page_slug`、命中理由、适用条件、证据来源、评价及可引用片段。先复用现有关键词搜索、页面类型和证据排序，增加明确的适用性过滤与总预算；不预设需要 embedding。不得以摘要包含关键词作为唯一的“适用”判断；模糊场景可让模型做有依据的最终选择，但引用必须可追溯。

对话在模型调用前执行有界选材，现有搜索工具仍保留作深入追问；话题分析、洞察、回顾逐步复用同一接口，记录实际选用/引用的页面 ID。不要只改变系统提示词声称所有消费端已接入。最终上下文预算目前仅在首次模型调用前压缩，工具后续轮次仍有边界缺口；选材输出必须自带预算，接入时覆盖多轮工具调用的总预算测试。未匹配时空选材是合法结果。

## 5. 维护和可观测性

来源变更以引用关系定位受影响页，生成待审修订，不级联静默覆盖。确定性 lint 校验不存在的来源、失效引用、无证据和断链；LLM lint 的矛盾/过期结论仅是附依据的建议。记录任务版本、处理 ID、错误类型、重试时间及被跳过原因；GUI 展示任务状态与审阅入口，日志不默认打印完整私密原文。保留 revision、wiki_log 和旧来源版本以便解释历史回答。

## 6. 实施与验证门槛

1. 先补队列、事件级确认和 GUI 任务状态；使用临时库测试同时间戳、迟到、窗口外积压、重复投递、断电式中断及非法 LLM JSON。CLI 已移除，消化只由应用后台 worker 驱动，不存在并行写入的第二入口。
2. 再迁移来源实体；使用现有 URL、文本和项目页的代表性数据做迁移前后页面/出处对账，验证同 URL 更新预览、拒绝评价和重启恢复。
3. 接入共享选材；逐消费端测“引用正确、不适用不引用、出处可展开、总预算有界”，以当前四透镜作回归基线。
4. 最后接来源更新和审阅工作台；测试冲突候选、规则升权确认、人工编辑页保护及修订拒绝后不会自动重提同一版本。

每期独立发布和验收；有真实 Provider 的端到端测试只用隔离的临时数据目录，不接触用户真实库。旧 [sources 路线图](../../sources-and-deep-chat.md) 中“聊天完全不注入 wiki”的现状描述已过时，实施前以现有工具与页面上下文代码为准。
