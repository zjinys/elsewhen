# 项目知识页与状态维护设计

> Status: proposed / future work
>
> 本文描述的是尚未实现的项目状态、增量快照和结构化项目维护方向，不是当前本地目录导入的行为规范。当前项目导入请以 [有界项目盘点与 AI 综合评估](notes/implemented/architecture/2026-09-23-bounded-project-assessment-synthesis.md) 为准：项目模式保存有界盘点报告，文件模式才逐文件建立 source 页；当前尚未实现本文中的 `knowledge_sources`、`source_files`、增量扫描、完成率字段和状态建议流程。

## 1. 背景

用户可以指定本地文档或项目目录，让 Elsewhen 理解用户正在做的项目和拥有的资产。项目目录通常包含大量代码、文档、依赖和构建产物，不能把所有文件直接写入知识库，否则会造成知识库膨胀、检索噪声过多和维护成本过高。

本设计将本地目录视为一个“知识源”，知识库只记录项目级的高价值信息；原始目录仍然是事实来源，需要时再按需读取具体文件。

## 2. 目标

- 一个项目目录对应一个项目知识页，而不是每个文件一个知识页。
- 知识页只保存支持用户判断和决策的高层信息。
- 支持项目持续变化时的增量扫描和更新。
- 用户可以直接修改项目状态和完成率。
- AI 可以提出项目状态或完成率修改建议，但不能静默覆盖用户修改。
- 话题分析必须考虑项目状态，特别是废弃项目是否值得恢复。

## 3. 项目知识页内容

项目页建议维护以下字段：

| 字段 | 说明 |
| --- | --- |
| 项目目标 | 项目要解决的问题和期望结果 |
| 项目状态 | 当前项目所处状态，见状态枚举 |
| 完成率 | 0 到 100 的用户可理解进度估计 |
| 卖点 | 产品或项目最有价值的差异化能力 |
| 当前阶段 | 例如想法、验证、开发、上线、维护 |
| 最近进展 | 最近一段时间完成的关键事项 |
| 主要阻塞 | 当前影响项目推进的问题 |
| 价值判断 | 对长期价值、短期价值和复用价值的判断 |
| 废弃原因 | 项目废弃时必须尽量记录原因 |
| 最近更新时间 | 最近一次事实或人工判断更新的时间 |

页面正文可以使用 Markdown，但关键字段应结构化保存，便于检索和决策：

```text
project_status
completion_rate
value_proposition
current_stage
blockers
abandoned_reason
status_updated_at
```

## 4. 项目状态

建议使用以下状态：

```text
idea        想法
active      进行中
paused      暂停
completed   已完成
abandoned   已废弃
archived    已归档
```

`abandoned` 和 `archived` 必须区分：

- `abandoned`：明确认为当前不再继续，未来默认降低推荐权重。
- `paused`：暂时停止，但仍然可能恢复，保留较高相关性。
- `archived`：从当前工作区隐藏或归档，不等于项目失败。
- `completed`：目标基本完成，可作为成果、案例或已有资产复用。

## 5. 本地目录的存储和扫描

### 5.1 知识源

一个目录对应一个知识源：

```text
knowledge_sources
- id
- root_path
- name
- source_type
- status
- scan_config
- last_scanned_at
- last_analyzed_at
- last_error
```

### 5.2 文件快照

文件只保存用于变化检测和按需读取的元信息：

```text
source_files
- source_id
- relative_path
- file_hash
- size
- modified_at
- language
- module
- is_deleted
```

默认忽略以下目录和文件：

```text
.git/
target/
node_modules/
.dart_tool/
build/
dist/
coverage/
```

### 5.3 文件分层

- A 类：README、架构文档、入口文件、配置文件。分析并保存摘要。
- B 类：核心模块文件。保存模块职责、导出接口和关键符号摘要。
- C 类：普通实现文件。只保存路径、hash 和模块归属。
- D 类：依赖、构建产物、缓存、生成代码。默认忽略。

未来方案可以保存项目地图和文件索引，但这些结构化快照目前尚未实现。当前项目模式不保存完整或截断文件地图，只保存有界盘点报告；用户需要具体文件内容时，使用显式的逐文件导入模式或后续按需读取能力。

## 6. 增量维护流程

每次扫描目录执行：

```text
扫描目录
  -> 计算文件 hash
  -> 比较上次快照
  -> 得到新增、修改、删除文件
  -> 只处理变化的 A/B 类文件
  -> 更新项目级知识页
  -> 记录项目级变更摘要
```

普通文件的变化只更新元信息，不触发完整 AI 分析。只有影响项目入口、架构、核心模块或用户显式关注的文件变化时，才重新分析项目页。

每次扫描记录：

```text
source_changes
- source_id
- scan_id
- change_type
- relative_path
- old_hash
- new_hash
- summary
- analyzed_at
```

项目页只保留最近若干条高层变化，例如：

```text
最近变化
- 新增本地目录导入能力
- 调整 Wiki 页面编辑流程
- 新增话题分析设计
```

## 7. 人工修改与 AI 建议

项目状态和完成率属于用户判断，AI 不应直接覆盖。

推荐流程：

1. AI 根据最近变化提出修改建议。
2. 展示建议依据和涉及文件。
3. 用户接受或拒绝。
4. 接受后写入结构化字段和知识页 revision。
5. 记录修改原因、来源和时间。

示例：

```text
AI 建议：完成率从 40% 调整为 55%。
依据：最近完成了目录导入、知识页写入和话题分析基础能力。

[接受] [拒绝]
```

用户在知识页直接修改状态时，应使用专门的状态更新操作，而不是依赖 Markdown 文本解析。人工修改后的字段应受到保护，自动扫描只能更新证据和变更记录。

## 8. 话题分析中的项目状态

话题分析检索项目时，必须把项目状态、完成率、价值判断和废弃原因一起作为上下文。

默认处理规则：

| 状态 | 默认决策含义 |
| --- | --- |
| active | 可以作为当前可执行资产 |
| paused | 分析暂停原因后，考虑恢复 |
| completed | 作为成果、案例或已有能力复用 |
| abandoned | 默认降低推荐权重，不直接建议投入 |
| archived | 低优先级参考 |
| idea | 只能作为待验证想法 |

废弃项目不能简单过滤。如果它与当前话题高度相关，并且已有代码、用户反馈、渠道或产品能力，系统应生成恢复建议：

```text
发现一个已废弃项目：旧电商工具

相关性：高
已有资产：代码、用户反馈、支付模块
废弃原因：获客成本过高

建议：可以评估恢复，但先用 3 天验证新的获客渠道；不建议直接恢复完整项目。
```

判断逻辑为：

```text
项目状态
+ 当前目标相关性
+ 已有资产
+ 历史废弃原因
+ 当前环境变化
= 继续、恢复或忽略的建议
```

## 9. 页面示例

```markdown
# 项目：Elsewhen

## 目标
构建一个本地优先的个人认知和决策支持系统。

## 状态
进行中

## 完成率
65%

## 卖点
- 本地优先
- 个人知识长期积累
- 结合真实资料提供决策支持

## 当前阶段
实现本地项目导入和话题分析。

## 最近进展
已完成知识页和目录扫描基础能力。

## 主要阻塞
增量更新机制和项目级摘要仍需完善。

## 项目价值判断
长期价值较高，但短期需要控制功能范围。
```

## 10. 实施顺序

1. 在当前有界项目盘点实现之上，增加项目知识页结构化字段和状态枚举。
2. 将本地目录导入改为“一目录一知识源、一项目一知识页”。
3. 增加文件快照和 hash 增量扫描。
4. 增加项目变更记录和知识页 revision。
5. 在 Flutter 知识页中增加状态、完成率编辑控件。
6. 增加 AI 的状态/完成率建议确认流程。
7. 将项目状态纳入话题检索和方案生成。
8. 增加废弃项目恢复建议和小规模验证任务。

## 11. 设计原则

> 知识库保存项目地图，原始目录保存项目事实，文件快照负责发现变化，AI 负责形成理解，用户负责确认重要判断。
