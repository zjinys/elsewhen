# Chat token budget optimization

目标：在不明显降低回答质量的前提下，降低输入 token 消耗，避免单次请求预算超限，并让每次压缩、重试和工具调用都可观测、可回滚。

## 现状基线

- 2026-11-24 本地记录约 47.6 万输入 token、5 千输出 token。
- 同一会话最近请求约 42k–54k prompt tokens。
- agent 最多 4 轮工具调用，空回复与 provider failover 会重复发送上下文。
- 常驻工具定义约 16k token，工具与历史共同挤占输入预算。

## 阶段

- [x] **P0：建立预算观测与基线**
  - 为每个请求记录 system、工具定义、历史、工具结果、摘要、用户输入各部分 token。
  - 记录压缩前后 token、实际 provider usage、cached tokens、重试次数和最终状态。
  - 增加单请求与单轮总预算指标，先只告警不改变行为。
  - 验收：能从数据库还原一次请求为何达到 50k token；现有聊天测试不变。

- [x] **P1：发送前最终预算闸门**
  - 在 provider 序列化完成后重新计算真实输入 token。
  - 预留输出预算和安全余量；超限时按优先级裁剪，而不是直接截断末尾。
  - system、当前用户消息、tool call 与对应 tool result 必须成组保留。
  - 第一次只记录裁剪决策，第二次开启默认阈值；保留配置开关回滚。
  - 验收：请求不会因输入超限发送；协议校验和预算测试覆盖所有裁剪路径。

- [x] **P2：分层历史压缩**
  - 默认保留最近 6–10 轮；较早对话替换为确定性摘要或短骨架。
  - 工具结果按结构化字段裁剪，旧 assistant 长回复只保留结论和引用。
  - 摘要失败时保留原文并降低可选背景，不阻塞当前回答。
  - 验收：常见长会话 prompt 降至 8k–16k；关键事实、当前任务和协议配对回归通过。

- [x] **P3：工具按需加载**
  - 首轮仅发送基础工具和工具启用入口。
  - 根据用户意图或模型明确请求加载对应工具；MCP 工具默认不常驻。
  - 限制单个工具结果大小并记录裁剪原因。
  - 验收：无工具问题不携带完整工具目录；工具调用成功率和专项测试不下降。

- [x] **P4：重试与 agent 轮次治理**
  - 普通请求默认最多 2 轮工具调用；协议修复、空回复、failover 共用同一总预算。
  - 重试只携带必要的最近请求，不重复附带可缓存的完整历史。
  - 达到预算或重试上限时返回可解释结果，不自动无限重发。
  - 验收：一次用户输入的累计 prompt 有硬上限；失败场景不会倍增 token。

- [x] **P5：缓存与自适应优化**
  - 固定 system prompt、工具前缀和摘要版本，提升 provider prompt cache 命中率。
  - 按模型真实 usage 校准估算系数和输入预算。
  - 通过灰度指标比较 token、延迟、成功率、回答质量和用户追问率。
  - 验收：连续一周无预算事故，输入 token/回答下降，质量回归无显著退化。

## 建议初始参数

- 普通聊天输入预算：8k–16k。
- 检索型聊天输入预算：16k–24k。
- 输出预留：2k–4k；安全余量：1k。
- 工具结果默认上限：1k–2k token。
- 工具轮次：默认 2，特殊任务显式提升。

## 风险与回滚

上下文压缩可能遗漏早期事实，工具裁剪可能损失调试信息，过低预算可能导致回答截断。所有阶段通过 feature flag 开启；保留原始上下文快照、裁剪原因和一键恢复旧预算的配置。任何预算超限、工具协议错误或回答质量回归，先关闭对应 flag，再根据观测调整阈值。

## 完成证据

每阶段完成后补充真实会话样本、预算分布、重试次数、缓存命中率、工具成功率和回归测试结果；没有这些数据不推进下一阶段。

### P0/P1 现状核验（2026-11-24）

现有 `RequestPolicies::fit` 已在 OpenAI-compatible provider 发送前对最终序列化 payload 计算输入 token，并按输入预算依次省略可选背景、裁剪旧工具结果、截短补充材料和移除可选历史轮；裁剪后重新计算并校验 tool-call/tool-result 配对。`request_budget`、`request_finished` 事件已记录预算报告、provider usage、缓存 token、裁剪数量和请求状态。因此本阶段先完成代码核验与回归门禁，不重复引入第二套闸门，避免两套预算算法互相冲突。

### P2-P5 现状核验（2026-11-24）

- P2：`compress_context_for_model`、摘要管线和旧工具结果裁剪已接入 provider 预算路径。
- P3：`ToolRegistry` 支持 deferred tools，agent 通过 `enable_tools` 按需加载，MCP 工具按启用状态注入。
- P4：agent 有工具轮次、协议修复和空回复上限；failover 使用同一轮上下文，预算错误会在发送前收敛。
- P5：provider 返回并记录 `prompt_cached_tokens`；`usage_underestimate_ratio` 根据真实 usage 校准后续预算，避免估算持续低估。

这些能力均已有专项测试覆盖。本轮完成的是 roadmap 与实现的对齐核验；后续优化应基于真实指标调整参数，而不是重复实现同一机制。

### 参数收紧（2026-11-24）

- 聊天 provider 的工作窗口限制为 32K（仍尊重更小的 provider 配置），避免 128K 模型把输入预算放大到 90K 以上。
- 默认 agent 工具轮次从 4 轮降为 2 轮，减少同一用户请求重复发送历史的机会。
- `cargo check` 通过。真实 prompt 分布和回答质量仍需线上样本继续验证。
