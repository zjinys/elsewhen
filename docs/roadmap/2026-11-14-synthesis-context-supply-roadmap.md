## P1 预算前移与事件按词检索

范围：

- [x] `AiProvider::input_headroom`：按真实发送的同一份序列化请求，量出还剩多少输入预算（OpenAI 兼容与 Ollama 实现；其余 provider 返回 None = 不限制）。
- [x] `ToolRuntime`：代理循环交给工具的运行时信息（当前渠道及名称、本次调用的结果预算）。并入工作区此前未提交的 `ToolContext.provider` 改动。
- [x] 代理循环在分发每轮工具调用前量余量，留出收尾指令的固定余量，在本轮各调用间平分。
- [x] `get_wiki_page` 按预算决定返回多少字符（上限仍是 8000）；余量不足 1500 字符且读不完时返回 `wiki_read_budget_exhausted`，不返回注定被截断的片段。
- [x] `search_knowledge_base` 的事件检索改为按词匹配并按命中词数排序，摘录取命中处。
- [x] 工具说明（中英文）说明预算不足的错误码含义；Prompt 目录升版。

工程验收：64K 口径下连续读页不触发工具结果减半；预算不足时返回指路错误；多词事件查询有命中；没有预算信息时行为不变。

落地记录（2026-11-14）：

- 余量的量法：把「本轮 assistant 调用 + 每个调用一条空结果」拼成下一次请求的形状交给 `input_headroom`（直接拿带未配对调用的上下文去量会被交换校验拒绝）。文本协议下把下一轮要附带的工具清单提示也拼进去。量出的余量先按 `usage_underestimate_ratio` 收紧，再减去 2048 的后续余量（`FOLLOW_UP_RESERVE_TOKENS`：收尾指令、行为清单、协议外衣），最后按本轮调用数平分。量不出来（provider 不报或校验失败）时不限制，行为与之前相同。
- `get_wiki_page` 按结果嵌进请求后的形态计数（JSON 字符串再转义一层），二分找出放得下的最大字符数。
- 只有 `get_wiki_page` 用了预算；其他工具的结果本来就有各自的小上限。`ToolRuntime.provider` 已随上下文传到工具，P2 的子请求直接用。
- 事件检索：词项取全部问法（含改写）的并集，至多 40 个；多取 3 倍候选再过滤不可记录的事件。
- 没改公开 API 与 Dart。
- 验证：新增 5 项测试（provider 余量；工具按预算分段直至读完与不足报错；代理循环把余量交到工具；64K 口径下连续三轮读页后收尾请求原样放得下、没有事后截断；事件多词命中）通过。`cargo test --all-targets --no-fail-fast`：库测试 1242 通过、23 忽略、3 项失败，集成测试通过；失败的是已知的三项回环 HTTP 测试，单独重跑全部通过。未调用真实模型。
- 与设计稿的差别：「预算不足时指路 `synthesize_knowledge`」留到 P2（工具还不存在），现在的说明是「基于已读内容作答并说明哪些部分没读」。

## P2 只读合成工具 `synthesize_knowledge`

范围（接口、流程、返回结构见设计稿 §5.3）：

- [x] 选页（显式 slug 走显式通道，检索页走默认通道）、6000 字符分块（300 字符重叠）、词法选块。
- [x] 分批子请求提取：只经 `generation::tool_request`（带阶段标签），每批块数按输入预算定，至多 6 次请求；批间检查取消；单批失败返回部分结果。
- [x] 逐字校验与定位：`quote` 必须是所在块原文的精确子串；丢弃的计数。
- [x] 确定性装配：同页重叠合并、按子问题轮转、总量封顶；返回 `knowledge_candidates`、`knowledge_reading`（`coverage: "evidence"`）、`evidence`、`coverage`（含未读范围）、`skipped`、`knowledge_warnings`。
- [x] 接线：只读策略、文本协议下的候选识别前缀（中英文）、换渠道重跑的进程内缓存、运行事件（只含计数）。
- [x] 提示词（`synthesis_*` 模板）与工具说明走版本化资源；搜索结果在命中长页或多页时给出确定性提示。
- [x] `get_wiki_page` 预算不足的错误改为指路合成工具。

工程验收：5 万字合成页在 64K 口径下 4 轮内完成、无本地拒绝；全部证据是原文子串且区间正确；伪造引文被丢弃并计数；单批失败返回部分结果；停止运行即时生效；文本协议下证据页可引用；写事务不被持有。

落地记录（2026-11-15）：

- 核心在 `src/knowledge/synthesis.rs`，工具壳在 `read_tools.rs`（`SynthesizeKnowledgeTool`，只读、常驻）。
- 子请求通道：`generation::auxiliary_request` 把阶段写死为 `summarizing`，新增 `generation::tool_request(…, phase)` 走同一条通道（取消、租约、预算、记账，不动答复草稿），合成用 `synthesizing`。界面对未知阶段名按「准备中」显示（`chat_run_status.dart` 只区分 `requesting`），不需要改 Dart。
- 与设计稿不同、以代码为准的地方：
  - 修复重试（输出不是约定 JSON 时带错误重发一次）也计入 6 次上限，`coverage.requests` 报的是实际请求数。
  - 每批块数不是按固定比例算，而是用 `input_headroom` 贪心装批（放得进子请求预算就继续加，至多 3 块）；provider 不报预算时按 3 块装。
  - 引文位置按「在块内逐字找到」换算；模型标错块号时在同批其他块里找，找到仍算原文。入选证据的 `quote` 返回前从页面正文按区间重新切出。
  - 只指定 `page_slugs` 时不另行检索；显式指定的页通读（没有词项命中的块也读，排在最后），检索到的页只读有命中的块。
  - 结果预算低于 4000 估算 token 时一次子请求都不发，直接报 `synthesis_budget_exhausted`；全部批次失败报 `synthesis_extraction_failed`，不返回看似「没有证据」的空结果；连续 2 批失败即收手并标 `stopped_early`；超过 240 秒不再发新请求。
  - 历史否定提醒放不下时先舍掉提醒并在 `coverage.warnings_omitted` 注明，证据优先。
  - 换渠道重跑的缓存键含会话、问题、子问题、各页内容哈希与读法；不完整的提取不缓存。
- 旧运行固定的工具说明里没有新工具：`configure_language` 原来按条数严格相等校验，会让升级时仍在进行的运行失败。改为缺的工具整条取同语言内置资源补上，已有工具的文本不动。
- 追问进展时的兜底文案（`continuity::readable_result`）为合成结果单列分支：汇报逐字证据，而不是空摘录或原始 JSON。
- 搜索结果在命中页超过 8000 字符或合计超过 24000 字符时带 `suggest: "synthesize_knowledge"`，只看结果数据不看用户文本。引用规范（`chat.context`）补了 `coverage=evidence` 的含义。
- 没改公开 API 与 Dart。界面上工具步骤名回落为通用的「处理工具步骤」，展开详情为空——工作区里界面目录正有大量他人未提交的改动，这次没有去动 arb 和 `tool_progress_details.dart`，留作后续小项。
- 验证：新增 9 项测试（逐字与定位、重叠去重、伪造引文丢弃、通读与只读命中块、部分失败与缓存、修复重试计数、全部失败报错、停止即收手、预算封顶与不可引用页跳过、只读且不持写事务、文本协议可引用、5 万字页在 64K 口径两轮对话请求内完成、旧说明补新工具、兜底文案、搜索提示）。`cargo test --all-targets --no-fail-fast`：库测试 1255 通过、0 失败、23 忽略，集成测试通过。未调用真实模型：提取质量、模型是否会主动调用本工具、耗时与用量都未验收。
