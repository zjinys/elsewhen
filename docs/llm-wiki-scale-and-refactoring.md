# LLM Wiki 功能补齐与规模评估

更新：2026-09-30，schema v9。结论：SQLite 和现有事务架构可以继续使用，无需整体重写；目前仍不能把整个应用称为“十万篇资料下全部流畅”。浏览路径已改为分页和按需取正文，全文检索及全库内容检查仍有线性扫描。

## 本次补齐的功能

| 功能 | 使用入口与行为 | 人工边界 |
| --- | --- | --- |
| 主题整理历史与撤销 | 主题 → 产出 → 整理主题结构，查看待审/采纳/拒绝/撤销方案；历史每 50 项加载 | 撤销恢复旧主题状态、归档新主题、解除替代关系；后续编辑/引用会阻止撤销。升级前缺少撤销基准的旧方案可查看但不能整批撤销 |
| 下游自动准备与批量审阅 | 上游变化后后台按依赖顺序准备修订；知识审阅 → 批量审阅修订，每批 1–20 项 | 不自动采纳下游修订。逐项事务，失败保留原文并返回原因；人工拒绝后同一依据不反复提案 |
| 阅读与使用状态 | 页面 → 来源与修订 → 阅读与使用；知识库浏览可按状态筛选 | 待读、已读、值得使用、已采用、归档是用户进度；阅读归档不等于撤销来源认可，也不会更改原文 |
| 产物版本与采用 | 原页 → 产出 → 产物版本，展开正文、选择两项比较、采用一个版本；窄屏纵向对照 | 同一父页/加工类型选择一个明确修订。后续修订不改变旧采用记录；可查看实际采用的修订。采用不自动提升为规则 |
| 建议反馈 | 主对话和页内对话 → 反馈这条建议，选取回复原文后接受、忽略、改写或撤回 | 反馈追加留痕，最近有效反馈进入本会话后续上下文；接受不代表执行行动，也不写成永久个人规则 |

新的派生产物记录本次用户指令、上游返回的模型标识、生成流程版本、时间和版本号；通过工具待确认保存和页内回复保存都接入。旧产物不倒推模型或指令。模型标识是上游报告值，无法验证中转背后的实际模型；记录不包含完整上下文录像，不能承诺逐字重现生成结果。

## 已实施的优化与重构

| Before | After | Why |
| --- | --- | --- |
| 整理队列加载全部来源正文，逐页查状态，Rust 排序分页 | SQLite 汇总元数据，一次查询生成计数与 50 条分页，使用快照长度表和索引 | 避免原文总字节数直接变成 FFI/应用内存开销，也消除重复汇总 |
| 主浏览列表取全部正文，在 Dart 搜索 | 独立 `KnowledgeLibrary` 与 `browse_knowledge`，SQL 筛选、50 条分页、输入防抖、过期请求丢弃 | 浏览首屏只传标题/摘要，按需读页 |
| 产物列表带全部正文 | 版本列表只带元数据，展开和比较时读取明确修订 | 避免后台刷新或原页打开时加载所有产物正文 |
| 依赖状态反复递归读取正文计算哈希 | 事务触发器维护知识版本号，递归 SQL 检查版本；确认仍校验完整依据 | 快速筛查与最终正确性校验各负其责；v8 已知哈希在升级时核对回填，未知基准仍须复核 |
| 一次读取全部待阅读/刷新候选 | 阅读候选最多 32，刷新候选最多 64；未就绪任务延后，下一 tick 继续 | 控制每次后台调度的应用侧内存，并避免队首阻塞 |
| 来源修复下拉读取全库原文 | 仅查询来源标题、版本和有效性；界面最多构建 50 项，可搜索定位 | 降低低频维护入口的内存与布局开销；元数据列表本身仍未服务端分页 |
| 整理方案遍历全表解析 JSON 找所属页 | `knowledge_topic_plan_pages` 关系表与索引，按页分页查询 | 整理次数增长后不再反复解析无关方案 |

实现主要位于 [workflows](../src/knowledge/workflows.rs)、[queue](../src/knowledge/queue.rs)、[dependencies](../src/knowledge/dependencies.rs)、[organization](../src/knowledge/organization.rs)、[刷新调度](../src/knowledge_background/refresh.rs) 和 [v9 迁移](../migrations/09-wiki-workflows/up.sql)。界面组件按浏览、版本、反馈拆分，避免继续扩大页面详情组件。

## 合成数据测量

测试使用独立临时库，不访问个人库，不调用模型。每篇资料 1980 个中文字符，分别生成 1 万/10 万个原料页及来源快照。数据有大量重复文本，队列为尚未处理状态；它测的是指定数据库路径，不是长期真实使用的完整负载。

本机 debug 测试单次耗时，操作系统缓存和并发测试会影响数值。整数毫秒为 0 的记录写作 `<1 ms`。

| 路径 | 1 万篇 | 10 万篇 |
| --- | ---: | ---: |
| 库文件 | 约 129 MB | 约 1.28 GB |
| 优化前队列（本轮初次 SQL 版本） | 363 ms | 3836 ms |
| 最终队列，含全量计数 | 约 215 ms | 约 2200–2700 ms |
| 分区浏览首屏 | <1 ms | <1 ms |
| 常见词匹配到前 51 项即停止 | <1 ms | <1 ms |
| 全文检索并排序候选（供 AI 使用） | 约 370 ms | 约 3900 ms |
| 浏览搜索完全未命中 | 129 ms | 1398 ms |
| 深分页到末尾附近 | 19 ms | 193 ms |

首屏很快不能证明所有搜索很快：常见词前面就命中，而未命中时需扫完整正文。当前队列是数据库侧全量汇总，应用只收到一页，但 SQLite 仍需处理所有任务，十万篇时延迟仍以秒计。

复现：

```bash
cargo test --offline synthetic_wiki_scale -- --ignored --nocapture
ELSEWHEN_SCALE_PAGES=100000 cargo test --offline synthetic_wiki_scale -- --ignored --nocapture
```

尚未覆盖：多年累积的运行日志、深/密集依赖图、百万页、手机低内存设备、多进程并发导入、真实模型响应速度与成本。没有据这些测量承诺容量上限。

## 后续确有必要的优化

1. **全文索引。** `select_knowledge` 仍在正文上 `instr` 匹配并排序，未命中的浏览搜索也扫描全文。需要支持中文词法的倒排/FTS 索引、增量更新和召回回归；仅换数据库不能解决查询算法的问题。语义检索是另一项质量改进，不能拿索引性能替代召回效果。
2. **全库内容检查改为增量任务。** `knowledge_issues(None)` 仍逐页读取和检查；主队列优化不代表审阅页里这块也已优化。应持久化检查结果及页面版本，仅重查变化页，再分页显示。关联来源/产出详情也需按数量分页，防止单一来源挂很多产物时成为热点。
3. **队列状态投影与日志策略。** 若达到十万级且经常打开队列，可持久化当前任务状态和聚合计数，读列表只查索引；结合归档/保留策略控制运行日志增长。当前精确汇总仍是 O(任务数)，不宜靠高频轮询掩盖。
4. **深分页改用游标。** 当前 OFFSET 在靠近末尾时增长；按稳定的时间与 ID 游标加载更适合长期滚动。低频来源选择器及仍使用旧全量列表的实体选择入口也应迁移到统一分页接口。
5. **后台吞吐和资源预算。** 当前应用运行时串行推进有界任务，关闭应用就暂停；吞吐主要受模型延迟、长文分块请求和中转限流影响。未来先补每类任务耗时/积压年龄/调用量指标，再决定配额、优先级和受控并发。不要简单把并发数拉高。

不建议现在整体重写 Rust/Flutter、切换到服务端数据库或引入分布式任务系统。优先保留原始数据不可变、写入事务、版本基准与人工确认契约，逐条替换高频读取和维护路径。

## 验证记录

功能回归、迁移和构建结果在 [缺口核对](llm-wiki-implementation-gaps.md) 中同步。真实知识效果仍未验收；本轮按用户要求以功能补齐和合成规模测试为主。
