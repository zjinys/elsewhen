## 🔴 Blocker（1 项）

### B1 `snapshot-start:{id}` 永不退役 → 无限重投/drop 死循环 + 状态面板永久说谎

五处代码链路（均已人工验证）：

1. `src/sync/engine/snapshot.rs:307` `announce_blob_snapshot` 只 `stage_sync_wire_envelope`，**没有**把 start 行登记进 `sync_snapshot_export_wires`；
2. `due_sync_wire_envelopes`（`src/storage/sync/wire.rs:177`）的 NOT EXISTS 门**只豁免 export_wires 里登记过的 id**，且**不排除 `relay_id` 非空的行**——start 行永远 pending、永远 due；
3. 退休 SQL（`src/storage/sync/delivery.rs:359-362`）只遍历 `sync_snapshot_export_wires` → 永远轮不到 start 行；
4. 接收端 accept snapshot-start 只 `Ok(true)`（`src/sync/engine/snapshot.rs:528-534`），**不排队回执**；回执白名单（`src/sync/engine.rs:659-661`）只认 `provider` / `snapshot-end` / `membership` 前缀；
5. `resend_spacing_ms` 上限 60s → 发送端每分钟重投一次，**永不停止**。

**后果链**：快照发布后接收端每次再收到 start 都报 `sync_snapshot_already_published` → `pull_page` 计拒收 → `client.drop` → 发端再投**新 relay mail id**（拒收计数按 relay mail id 键控，每次重置）→ 无限循环。直接违背 R6 验收「死信 0」；同时该 pending 行让 `deliver_statuses` 对该对端**永远显示 awaiting_receipt**（核实 SQL：`WHERE state='pending'`）。

**为什么 e2e 没爆**：R4-3 的证据「outbox 恰好 2 条（start+end）」其实就是该 bug 的铁证——第二条永远不会被收走；29.5s / 18 拍内重投循环与测试停止时机恰好错开。

**最小修法**：`accept_snapshot` 对 snapshot-start 分支排队回执 + 回执白名单放行 + `acknowledge_snapshot_export` 覆盖它；或复用 `sync_snapshot_export_wires` 登记 start 行让批量退休生效。修完加回归用例：「发布后 N 个 tick 内 outbox start 行 state='acknowledged'」，把「死信 0」验收变成可跑断言。

## 🟠 Major（3 项）

### M1 blob 上传一次网络错误 → 导出 abort → 同 id 重 begin 被拒 → 每 tick 报错死锁

代码口径互相矛盾（**预存矛盾，mail 时代就存在，被 R4 续传叙事掩盖**）：

- `stage_snapshot_inner` 任何 Err 都 `abort_snapshot_export`（`snapshot.rs:197-199`）；
- `begin_snapshot_export` 对非 `building` 状态一律拒（`delivery.rs:159-162`，仅放行 blob+building+clock 一致）；
- 但 `claim_sync_resnapshot`（`src/storage/sync/resnapshot.rs:141`）对 aborted 的决策是「**resume the SAME request id**」（注释原文如此）。

结果：abort 后同 id 每 tick 必炸 `sync_snapshot_export_requires_new_request`，从 `network.rs` 的 `?` 一路撞穿这拍。`blob_index / blob_id / blob_clock` 三列白设计。`resnapshot/tests.rs` 只断言 claim 返回同 id，没有一条用例验证同 id 重 begin 能成功。

**修法方向**：`begin_snapshot_export` 放行 blob 的 `aborted` Resume（与 resnapshot.rs 注释对齐），并补一条「abort → claim → resume 同 id → 续传成功」的 e2e。

### M2 无能力协商：老 relay + `SYNC_SNAPSHOT_TRANSPORT=blob` = 死锁组合

`src/sync/runtime.rs::snapshot_upload` 只读环境变量，**不读 `/status.capabilities:["blob"]`**。R4 plan §2.4 白纸黑字承诺「旧 relay 没有 blob 能力时发送端自动退回 mail（并在 roadmap 写明判定点）」——未实现，roadmap 也无该判定点证据。

后果：对老 relay 打开开关 → `/blob/open` 404 → 报错 → **叠加 M1 变成永久死锁**（既不退回 mail 也不上 `blocked`）。当前默认 `mail` 限损，但开关打开即翻车。

### M3 R6-2 错误映射半数是「文档宣传」：`is_blocking` 是死代码

- 「413 ⇒ `blocked(protocol)` 不重试」：`blocked_reason='protocol'` 无任何生产写入点（全仓只有 quota 一处写 blocked）；
- 「Integrity 累计 3 次升级为 blocked」（`deliver.rs:54` 注释）：对应 `is_blocking`（`deliver.rs:70-73`）全仓 grep 仅测试引用——**死代码**；
- 「409 重放：单次重试、不进状态机」：Replay 实际走通用 `record_sync_wire_attempt`，**进了状态机**（`Backoff{replay}`，1s 封顶，损害有限但与宣称相反）；
- 连带：UI 的 `protocol` 中文文案实际不可达。

**处置二选一**：要么真实现 blocked 升级链，要么改 roadmap 措辞并删 `is_blocking`——别让注释撒谎。
