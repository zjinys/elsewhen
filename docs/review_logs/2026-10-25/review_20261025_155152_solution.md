## 0. 一句话结论

Review 的**机制判断成立**：B1（`snapshot-start` 永不退役）是真 blocker，M1/M2（abort 死锁、无能力协商）是真死锁组合，M3（`is_blocking` 死代码）是真「注释撒谎」。但 review 的**三处技术归因不准**（§1.2），照抄会修错地方。

因此本方案分五批，顺序是「先堵无限循环 → 再解死锁 → 再让状态机名副其实 → 再清行为小刺 → 最后把文档改成事实」，**每批都有自己的门禁与可跑断言**，不靠「29.5 s e2e 绿了」这种间接证据。

### 1.2 Review 归因不准的三处（照抄会修错地方）

| Review 说法 | 实际情况 | 对修复的影响 |
|---|---|---|
| m9：「`404 = 不存在` 实为死分支（relay 返回 200+空 present）」 | **`GET /blob/chunk` 对不存在的 blob 确实回 404**（`blob.mjs:199` `require(blob, 404, 'blob not open')`），所以 `blob_get_window` 的 404 分支（`blob.rs:251-256`）是**活代码**。真正说错话的是 **`blob_state` 的注释**（`blob.rs:166-167`）——`/blob/state` 对不存在的 blob 返回 `200 + present:[]`（`blob.mjs:173-181`），永远不 404 | 改注释，**别删 404 分支**。删了会让「blob 被 TTL 收掉」变成硬错误而不是「从 0 重来」 |
| m9：「片数上限 2560 / 1025 / 4096 三处无互引」 | **只有两处**：客户端 `index < WINDOW_CHUNKS * 256`（=2560，`blob.rs:99`）与 relay `MAX_BLOB_CHUNKS = 4096`（`blob.mjs:33`）。全仓 `grep 1025` 零命中 | 只需给这两处加互引注释 + 说明「客户端上限更严，是防御性收敛」 |
| m8：「`[blob]`/`[pull]` 系列走裸 `eprintln!`」 | 三处**都在 `ELSEWHEN_DEBUG` 门控内**（`snapshot.rs:271`、`snapshot.rs:483`、`flow.rs:361-362 / 415 / 444`）。缺陷不是「没门控」而是「**格式绕开了 `wire_line` 的四字段契约**」 | 修法是**转成 `wire_line`**，不是「删掉调试日志」 |

### 1.3 B1 后果链需要精确化（review 的措辞会误导实现）

Review 说「发端再投**新 relay mail id** → 无限循环」。这句话对，但中间少了一环，写清楚才不会修错：

1. relay 的 `seq_hint` 幂等是**原地替换、保住 id**（`server.mjs:335-349`：内容相同直接 no-op 返回同一 id）；所以**重投在 relay 侧不放大字节**，也**不产生新 id**；
2. 接收端按 **relay mail id** 计拒收（`engine.rs:463` `record_wire_rejection(mailbox, sender_mb, &mail.id, ...)`），同一个 id 累到 3 次 → `client.drop` → 那封信从 relay 上消失（`mark_wire_rejection_dropped`）；
3. 发送端 outbox 行**仍是 pending**（没有任何路径把它标 acknowledged）→ 下一拍 `client.send` 同 `seq_hint` → 因为旧行已被删，relay **插入新行、新 id** → 接收端计数**归零**，再拒 3 次、再 drop……
4. 与此同时 `relay_id` 非空 ⇒ `deliver_statuses` 恒判 `awaiting_receipt`（`deliver.rs:161`）⇒ 面板永久显示「等回执」，永远不 `idle`。

所以：**字节不放大、请求永不停止、面板永久说谎、死信计数永远清零**。这也解释了为什么 R4-3「outbox 恰好 2 条」的证据本身就是 bug 的指纹（第 2 条永远退不掉）。

### 1.4 复核中新增的一条（review 未列）

**N1：blob 在传输中途被 TTL 收掉时，`PUT` 回 404 会被分类成 `Transport`**（`classify_delivery_failure` 无 404 分支，`deliver.rs:78-94`），于是按 5xx 退避到 10 分钟——实际语义是「blob 没了，得重开并从 0 上传」。归入 F2-2（与 M1 同批，因为都属「abort/重建」语义）。

## 2. F1：B1 blocker —— `snapshot-start` 的退役语义

### F1-1 接收端把「已发布」当幂等成功，而不是拒收

**根因**：`begin_blob_snapshot_import` 对非 `staging` 一律 `ensure!(state == "staging", "sync_snapshot_already_published")`（`import.rs:121`）。

**修法**：把「已收口」从错误变成正常返回，而不是用 `ensure` 表达：

```rust
// 落地修订：原本计划返回 BlobImportStart{Started,AlreadyPublished} 三态枚举，
// 实际改成 Result<()> —— 调用侧两个分支后续动作完全一样（回执 + Ok(true)），
// 留着就是新死代码（正是本 review 批 `is_blocking` 的那种形态）。
pub(crate) fn begin_blob_snapshot_import(..) -> Result<()>
```

- `staging` → 记 `transport='blob'`/`blob_id`，返回 `Ok(())`；
- `applied` **且** 同一 `blob_id`（或该行无 `blob_id`）→ 返回 `Ok(())`（不是错误）；
- `applied` 但 `blob_id` 不同 → 仍 `sync_snapshot_blob_conflict`（这是真的身份冲突）；
- `aborted` → 返回 `Ok(())`（对端放弃了，重投也无意义，收口）。
- 所有早退分支仍自己跑一遍 `snapshot_source_authorized`：不能因为走了早退就绕开「发送方必须是活跃成员」。

**理由**：`snapshot-start` 是**通知**不是**数据**。重复收到通知的正确语义是「知道了」，不是「这是第 3 条毒信，丢掉」。这条改动单独就能把 §1.3 的第 2~3 步无限循环掐断（即使 F1-2 因故失效）。

### F1-2 给 `snapshot-start` 排回执（真正让发送端退役）

**修法三处，缺一不可**：

1. `accept_snapshot` 的 start 分支：在 `begin_blob_snapshot_import` 的**同一事务**里 `queue_sync_wire_receipt(sender, &message_id, hash(plaintext))`；
2. 回执白名单（`engine.rs:659-661`）放行 `snapshot-start:`；
3. 回执处理分支（`engine.rs:667`）保持「只有 `snapshot-end:` 走 `acknowledge_snapshot_export`，其余走 `acknowledge_sync_wire`」——`snapshot-start:` 恰好落进 else，把 outbox 里那一行标成 `acknowledged`。

**关键**：**不要**把 start 行登记进 `sync_snapshot_export_wires`。那条路看似更省事，实际有两个坑：①`stage_snapshot_export_wire` 要求 `ensure!(changed == 1)`，同一 id 第二次登记会在「旧 export 不是 aborted」时失败（`delivery.rs:273-276`）；②`due_sync_wire_envelopes` 的豁免条件是 `s.state != 'ready'`（`wire.rs:174`），export 一进 `ready` 就解禁，start 行会在「manifest 已发、接收端还没发布」的窗口里被重新推一遍。走回执没有这两个问题，语义也更准（回执 = 「我记下了分片在哪」）。

### F1-3 `due_sync_wire_envelopes` 的兜底守卫

**修法**：给 `due` 查询加「**已上 relay 的行不再每拍重推**」的守卫——保留 `resend_spacing_ms` 的意义，但把「已经 `relay_id` 非空」的行的最小间隔从当前公式的 60 s 上限**抬到 5 分钟**（`resend_spacing_ms` 只服务「响应丢了」兜底，60 s 对本就不该重发的信令太密）。

不引入新列、不引入新状态机：仍是纯 SQL 推导。

### F1-4 回归用例（把「死信 0」从散文变成可跑断言）

新增 `src/storage/sync/tests/snapshot_start_retirement.rs`（或用现有 blob e2e）：

| 用例 | 断言 | 落地 |
|---|---|---|
| `start_signal_is_retired_after_receipt` | blob 导出成功 → 回执回来后，`sync_wire_outbox` 里 `message_id='snapshot-start:{id}'` 的行 **`state='acknowledged'`**；`deliver_statuses` 对该对端不再有行（= idle） | 存储层 + 引擎层各一例 |
| `duplicate_start_after_publish_is_not_a_rejection` | 手工重投 start → `accept_relay_payload` 返回 `Ok(true)`、`sync_wire_rejections` **0 行**、`report.rejected == 0` | 引擎级：三次重投（staging / 重投 / 已发布）全 `Ok(true)`；拒收计数只在 `pull_page` 里，`accept` 不报错就不可能有计数 |
| `start_signal_stops_resending` | N 拍后该行 `attempts` 不再增长；relay 侧 `count` 归 0 | 以「回执即退」代替（退掉的行不再被 `due_sync_wire_envelopes` 选中），另加 `resend_spacing_is_capped_at_five_minutes` 守兜底 |
| `start_blob_id_conflict_still_rejects` | 同 id 换 `blob_id` 重投 → 仍报 `sync_snapshot_blob_conflict` | `start_with_different_blob_id_still_conflicts`（staging 与 applied 两种状态各一次） |
| （新增）`start_from_non_member_is_rejected` | 非成员 / 版本不符仍要拒 | 守早退分支没绕开授权 |

**总：** 存储层 6 例 + `deliver_state` 2 例 + 引擎级 1 例；真 relay blob e2e 里的「只该有一条回执」改成「start 与 end 各一条」，并已实跑验证。

## 3. F2：两个 major（abort 死锁 / 无能力协商）+ N1

### F2-1 `begin_snapshot_export` 放行 blob 的 `aborted` 续传

**修法**：把放行条件从 `state == "building"` 扩成

```rust
let resumable = matches!(state.as_str(), "building" | "aborted")
    && stored_transport == SnapshotTransport::Blob.as_str();
ensure!(resumable && transport == SnapshotTransport::Blob && blob_clock == logical_clock,
        "sync_snapshot_export_requires_new_request");
```

**为什么安全**（必须写进注释）：
- `abort_snapshot_export` 只作用于 `building`（`delivery.rs:328`），所以 `aborted` 恒等于「这份导出建过但没建成」，不存在「建成后又 abort」的情况；
- `blob_index` / `blob_id` / `blob_clock` 三列在 abort 时**未被触碰**，续传点由 `upload_blob_chunks` 与 relay 事实对齐（`opened.created` → 0，否则 `max(本地 blob_index, relay 的 highest+1)`，`snapshot.rs:234-246`）——所以续传**不会跳过没上传的片**；
- mail 传输**不放开**（旧语义：mail 中断必须换新请求 id）。

### F2-2 新增 `RelayBlobUnavailable`，把「blob 没了/没有这能力」与 5xx 分开

**根因**：`PUT /blob/chunk` 与 `GET /blob/chunk` 对已回收的 blob 回 404（`blob.mjs:128/199/231`）；`/blob/open` 在老 relay 上是路由级 404（`blob.mjs:285`）。现在全部落进 `Transport` 分支，退避 10 分钟，语义错位。

**修法（落地时修订）**：
- `blob.rs`：`blob_open` / `blob_put` 的 404 转 `RelayBlobUnavailable`（辅助函数 `blob_unavailable`，`downcast_ref::<RelayHttpError>()` 且 `is_not_found_status`）；`blob_get_window` 的 404 **保持**「返回空窗」（发送端还没传到就是这种语义）；`blob_state` 不会 404（回 `200 + present:[]`）。
- **`DeliveryFailure::BlobGone` 主动删除**（方案原定第 6 类）：blob 上传路径根本不经 `deliver_statuses` —— 它没有 `sync_wire_outbox` 行（分片不进 outbox）、每拍自己重试、没有 `backoff_ms` 也没有 `blocked_reason`。加一类只进 `classify_delivery_failure` 而永不被调用的枚举，正是本 review 批判 `is_blocking` 的那类死代码（与 P1 删 `BlobImportStart` 同源判据：**没有消费者就不加**）。`classify_delivery_failure` 仍是**五类，一个不多一个不少**，设计稿 §3.5 不用改，F4 不必为此改 R6-2 措辞。
- `RelayBlobUnavailable` 的真实消费者是**能力降级**：`blob_open` 收到 404 就把该 `base_url` 记为「无数据面」（有 blob 面的 relay 上不存在的 blob 会被建成新的，所以这个 404 是**结论性**的，不是抖动）。`blob_put` 的 404 只做「错误文本可辨」，不降级——那是单份 blob 被回收，重开一份就好。

### F2-3 能力协商：探一次 `/status.capabilities`，缺 blob 就退回 mail

**根因**：`snapshot_upload` 只看 env（`runtime.rs:31-33`）；`MailboxStatus` 无 `capabilities` 字段。

**修法**：
1. `MailboxStatus` 加 `#[serde(default)] pub capabilities: Vec<String>`（老 relay 缺字段 → 空 vec → 视为「无 blob」）；
2. `snapshot_upload` 先用 `vault.mailbox_owner()` + `route.local_mailbox` 问**自己信箱**的 `/status`（同一台 relay 实例，能力等价；而且 sender 凭据本来就没权读对端 `/status`——这是 review 没说清的约束），`capabilities` 不含 `"blob"` → 返回 `Ok(None)`（走 mail）；
3. 结果按 `base_url` 缓存（`OnceLock<Mutex<HashMap<String, bool>>>`），避免每拍多一次 HTTP；换 relay URL 自然重新探测；
4. `/status` 请求本身失败 → **不缓存失败**，本拍返回 `Ok(None)` 走 mail（保守：信件路径永远能跑），下一拍再探。

**明确不做**：不做「已在途的 blob 导出中途降级成 mail」。那需要换导出 id，与 F2-1 的「同 id 续传」直接冲突，而且会让 `blob_index` 语义失效。中途失效走 F2-2 的 `BlobGone` + 重开 blob（同 id，从 0 重传）。

### F2-4 回归用例

| 用例 | 断言 |
|---|---|
| `aborted_blob_export_resumes_under_same_id` | abort → `claim_sync_resnapshot` → `begin_snapshot_export` 返回 `Resume{blob_index}` 而不是 Err → 续传成功发布 |
| `aborted_mail_export_still_requires_new_request` | mail 传输行为不变（守住旧语义） |
| `relay_without_blob_capability_falls_back_to_mail` | 假 `/status`（只有 TcpListener 回固定 JSON）无 `capabilities` → 探测判 false，且**只探一次**（缓存生效） |

## 4. F3：让状态机名副其实（M3 + m1/m2/m3）

### F3-1 `blocked` 真的有人写（M3）

**决策**：**真实现**，不删 `is_blocking`。理由：413 是**结构性不可恢复**（两端上限不同步），重试永远不成功；现在它每拍重试、只是没人看——这是毒信循环的温床，与 R5「3 次必表态」同源。

**修法**：
- 新增 `Store::block_sync_wire(peer, message_id, reason, until_ms)`（**取代** `block_sync_wire_on_quota`，理由参数化），507 调用它传 `"relay_quota"` + 15 s；
- `push_due` 的 `Err` 分支：`failure.is_blocking()` ⇒ `block_sync_wire(..., failure.code(), now + backoff_ms(failure, attempts))`；否则照旧 `record_sync_wire_attempt`；
- `backoff_ms(Protocol)` 从 `0` 改成 `10 * 60_000`（原来 `Protocol => 0` 会让 blocked 行 0 ms 后立刻重试，等于没 block）；
- `deliver.rs:54` 那条「Integrity 3 次升级 blocked」改为真话：**Integrity 永远只退避**（摘要不符意味着我们自己发坏了，重发是对的），删掉这句注释与对应预期。

**Replay 的口径修正（不写代码）**：Replay 确实进 `Backoff{replay}`（`backoff_ms` 上限 1 s），不是「不进状态机」。改注释与 roadmap 措辞，**不改行为**——1 s 上限已经足够，为它单开一条旁路不值得。

### F3-2 `last_error` 成功时清空（m1）

**修法**：`record_sync_wire_attempt` 成功路径显式 `last_error=''`：

```sql
last_error=CASE WHEN ?5='' THEN '' ELSE ?5 END
```

即「`?5=''` = 成功 ⇒ 清空」。同时把 `available_at_ms` 在成功路径改由 `resend_spacing_ms` 决定（不变），这样「成功但还没到下次重发」的行 **`last_error=''` ⇒ 推断为 `AwaitingReceipt`**，面板不再假报 backoff。

**回归**：新增用例 `last_error_clears_on_success`（失败 → 退避中出现 backoff → 成功 → 立刻回 `AwaitingReceipt`，且 `last_error=''`）。这是 R6 目前**只有失败方向**的补丁。

### F3-3 507 写 `last_error`、重封清 `blocked_reason`（m2/m3）

- `block_sync_wire` 同时写 `last_error=?`（分类码），这样配额恢复后下一次 5xx 会把 `last_error` 覆盖成 `transport`，`blocked_reason` 仍由「成功才清」的规则保留——但 `deliver_statuses` 的优先级改成：**`blocked_reason` 非空但 `last_error` 是更近的失败 ⇒ 显示 blocked 的原因 + backoff 的 until**。简化实现：把 `blocked` 分支的 `until_ms` 一并取 `available_at_ms`，UI 就能显示「配额满，15 s 后重试」而不是干说「配额满」；
- 重封 UPSERT 加 `blocked_reason=NULL, last_error=''`（新信 = 新事实，旧的阻塞原因不成立）。

**回归**：`quota_then_transport_shows_transport_not_quota`、`restage_clears_blocked_reason`。

### F3 落地修订（2026-10-25 实施）

1. **「`blocked_reason` 只由成功清除」这条规则被推翻**。原文设计成「配额恢复后下一次 5xx 覆盖 `last_error`、`blocked_reason` 保留」，再靠 `deliver_statuses` 的优先级去挑。落地时发现：任何一次进到 `record_sync_wire_attempt` 的失败都是**不阻塞**的失败（阻塞类走 `block_sync_wire`，不经过这里），所以「旧的那条阻塞原因」在这一刻已经**不成立**，保留它就是在报旧账、且 `blocked` 分支优先于一切会把整个对端永久显示成卡住。改成**一律清空**（成功与「这次失败不阻塞」都清），比再加一层优先级判断简单且不会自相矛盾。
2. **`deliver_statuses` 的两个时刻必须分列**，不能共用第 6 列的 `until_ms`：原来 blocked 与 backoff 抢同一个 `MIN(available_at_ms)`，同一对端既被阻塞又有退避时后写的覆盖先写的。现在 `until_ms` 只统计 `blocked_reason IS NULL` 的行，新增第 9 列 `MIN(CASE WHEN blocked_reason IS NOT NULL THEN available_at_ms END)` 作 `blocked_until`。
3. **`DeliverState::Blocked` 带 `until_ms`**（原本只有 `reason`）：阻塞语义是「放慢到人看得见」而不是停摆（507 仍 15 s 再试），面板要能说「配额满，15 秒后再试」。Dart 侧 `_retryHint` 剩 <2 分钟按秒、否则按分钟。
4. **`backoff_ms` 对阻塞类不看 `attempts`**：`Protocol` 若仍按指数算，`attempts=0` 时给 0 ms，配上 `block_sync_wire` 就是「标成阻塞、下一拍立刻重试」，等于没 block。
5. **`push_due` 的阻塞判定扩到 `failure.is_blocking()`**（原来只有 507 那一支），但 **507 单独保留「中止本拍」**（`quota_exhausted`）：413 只影响这一封，507 说明整个信箱满了，再发后面的信只是白撞一次上限。

### 6.1 P4 实施记录（与方案的三处偏离）

1. **m10-a 不用「重建 `sync_snapshots`」，改用触发器**。方案原写「重建表加 CHECK」。实测两条硬阻塞：①`DROP TABLE` 在开着外键时对 `sync_snapshot_chunks` 子表行累加延迟违规计数，重插相同 id 不会减回去，提交时 `FOREIGN KEY constraint failed`（官方 12 步要求先关连接级 `foreign_keys`，而 `PRAGMA foreign_keys` 在事务内是空操作）；②`ALTER TABLE ... RENAME` 会重解析 `sync_background_permission` 视图与八个 `sync_*_claim_*` 触发器中对 `sync_snapshots` 的引用，旧表刚 DROP ⇒ `error in trigger sync_analysis_claim_insert: no such table: main.sync_snapshots`。触发器（BEFORE INSERT + BEFORE UPDATE OF transport，`WHEN NEW.transport NOT IN ('mail','blob')` → `RAISE(ABORT, …)`）给同样的保证：非法值写不进去。`sync_wire_rejections` 没有视图/触发器引用，所以它照方案重建。
2. **m10-c 的触发条件不是 `no such column: seq_hint`**。那是方案笔误：`catch` 包住的是 `CREATE UNIQUE INDEX`，重复行造成的是 `UNIQUE constraint failed: relay_v2_mail.sender_mb, relay_v2_mail.seq_hint`；而「缺列」这个错误用去重**修不了**（两条 DELETE 同样会因缺列失败，只会把真错换成另一个错）。落地只认 UNIQUE，其余原样抛。为此把该逻辑抽成 `schema.mjs` 的 `ensureIdempotencyIndex`，可以直接对假库注入异常做单测。
3. **m4 需要独立的「回收」循环，不能塞进导入循环**。方案说「由下一拍重试」，但发布成功的行状态是 `applied`，`snapshot_import_pending()` 对它恒 false —— 最后一块 blob 永远等不到下一拍。落地新增 `blob_recycle_pending()`/`pending_blob_recycles()`/`mark_snapshot_blob_recycled()` + `recycle_published_blobs()`，由 `network.rs` 每拍在 peer 循环后扫一次（`recycle_swept` 门闩保证一拍只扫一次）。顺序是**先 `blob_close` 后落标记**：反过来会在 close 失败时留下「本地以为回收、relay 还占着」的永久谎言，而正确顺序下的失败只多待一拍。`aborted` 用 `cancel` 关、已发布用 `done` 关（relay 侧语义不同，对空间效果相同），close 幂等 + 30 min TTL 仍是最终兜底。

**m10-d 的两个附带决定**：`isBusy` 按 `errcode` 低 8 位判（5 = `SQLITE_BUSY`、6 = `SQLITE_LOCKED`），这样 `BUSY_SNAPSHOT`(517)/`BUSY_RECOVERY`(261) 等变体一起认；新增 `SQLITE_BUSY_TIMEOUT_MS`（默认 5000）只为让「写锁被占住」这条路径能被测试以 50 ms 确定性触发，生产语义不变。

**不做（明确记录）**：`SnapshotTransport::from_env` 只在新建导出读 env —— review 自己也判定「已被迁移动机注释自证，无缺陷」，**不动**。

## 10. 与 review 建议顺序的差异（说明理由）

| Review 建议 | 本方案 | 理由 |
|---|---|---|
| 1. B1 | **P1（不变）** | 一致 |
| 2. M1+M2 合并 | **P2（不变）** | 一致；但 M2 的能力探测改走**自己信箱**的 `/status`（review 未考虑 sender 无权读对端 status） |
| 3. M3 二选一 | **选「真实现」**，且把 `backoff_ms(Protocol)` 从 0 改 10 min | 只删 `is_blocking` 会让 413 继续每拍重试；「真实现」才是止血 |
| 4. m6/m7 顺手清 | **提到 P0 先做** | 纯文字、零风险，先做能立刻减少后续实现时读错文档的概率 |
| — | **新增 F3-2 提到 P1** | m1 与 B1 同属「outbox 该收口没收口」，同一批改完一次验 |
| — | **新增 N1（404 → BlobGone）** | review 遗漏：404 混进 Transport 会把「重开即可」拖成 10 分钟退避 |
