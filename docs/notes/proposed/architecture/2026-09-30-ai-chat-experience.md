# Agent Note: 借鉴成熟聊天产品，完善 Elsewhen 的 AI 对话体验

Status: proposed

## Problem

Elsewhen 已有事件存储、知识选材、引用校验、工具调用、写入确认和请求预算等能力，但用户面对的对话过程仍以“发送 → 等待 → 收到最终回复”为主。长任务的进度、停止、补充要求、失败恢复和长对话连续性还没有形成统一体验。

本次讨论的目标不是评判两份参考文档的对错，而是借鉴一个已有较多用户使用的聊天产品，把 Elsewhen 从“能调用模型”提升为“过程可见、用户可控、任务连贯”的对话应用。参考实现中的设计值得研究，但用户规模本身不替代本项目的正确性测试和真实模型验收。

## Proposal

保留 Rust + Flutter + SQLite 架构、现有知识证据能力和本地优先边界，分阶段引入成熟对话产品的生成生命周期、上下文管理和交互控制机制。不整体移植 RikkaHub，也不先做一个仅把完整字符串改为流输出的接口。

### 1. 从等待答案改为可见、可控的生成过程

用户应能看到逐步产生的正文以及真实执行阶段，例如检索、读取材料、运行工具、草拟内容；可以停止，切换会话后仍能看到正确状态。失败时保留已完成内容，并说明哪些工作已经完成、哪些尚未执行。

底层建议采用统一的 run 身份、事件协议和状态应用逻辑，同时服务主对话和知识页对话。Provider 负责产生模型事件；编排层负责预算、工具和生命周期；存储负责持久化；Flutter 只展示和提交用户意图。

流式、取消、工具进度、最终回复和恢复应共享一套状态，而不是五套局部布尔变量。展示真实步骤，不伪造百分比，不展示模型私有推理链。

### 2. 从预算裁剪改为长对话连续性管理

“请求不超限”不等于“长对话聊得好”。在保留最终完整请求预算检查的前提下，增加非破坏性的语义摘要与任务状态：

- 较早历史概括用户目标、关键约束、已确认事实、决策和未完成事项；最近几轮保留原文。
- 摘要注明由模型生成，并记录覆盖的消息范围、输入版本和策略版本；不覆盖或删除原始消息。
- 必要时重新读取摘要背后的原文，不能把摘要当逐字来源或用户确认事实。
- 当前问题、当前工具交换、规则与有效证据使用显式保护规则；无法满足预算时诚实拒绝或缩小任务范围。
- 只稳定允许陈旧的前缀段；本轮结果、来源版本、规则变更和问题相关选材仍按各自契约刷新。

现有 `FollowUp` 和空回复恢复行为是起点，不再建设一套与它相冲突的“任务记忆”。

### 3. 主动提供当前时间与历史时间线索

Elsewhen 的“今天、昨天、刚才、明天”有明确业务含义，模型不应自行猜测当前日期。将时间上下文作为独立、优先可交付的小切片，不等待流式或摘要改造。

- 每轮用户请求从应用时钟取得当前时间，包含完整日期、星期、本地时间和 UTC offset；可取得可靠时区标识时同时携带，不能根据语言猜时区。
- 区分本轮当前时间、用户消息发送时间和事件发生时间。排队消息跨午夜后才处理时，不能把发送时的“昨天”按处理时的日期重新解释。
- 历史首条用户消息、相邻用户消息间隔超过 10 分钟、跨本地日期或时区时，可合成简短时间提醒；10 分钟只是初始节奏，不是事实有效期，也不必做成用户设置。
- 当前时间块放在本轮动态上下文区，不放进稳定 system 前缀。每轮只构建一次；重试复用，长任务跨日或时间明显过期时在下一轮模型请求前替换该块，不重复追加。
- 时间提醒是系统提供的合成上下文，不改用户原文、不创建事件，也不作为模型总结出的事实写入记忆。仅有日期不能证明某天发生了什么，回答仍需检索真实记录。

这个机制解决的是时间感知，不代表应用新增定时唤醒或主动推送能力。实施与固定时钟测试见 Roadmap 的 C00a。

### 4. 生成期间仍允许用户表达新意图

先实现本地保存和显式队列，再考虑在工具轮边界接收补充要求：

- 生成期间可以继续输入；排队消息可查看、撤回待生成资格。
- 区分停止当前轮、排队下一问、补充当前任务，不能靠关键词猜用户希望哪一种。
- 记录先进入现有本地提交边界，不能因为 AI 正在回复而阻塞保存。
- 后续 steering 只在可验证的轮边界注入；成功注入才消费队列项，防止同一要求被执行两次。

撤回排队生成不等于删除已保存的不可变事件。停止也不撤销此前已经完成的业务写入。

### 5. 把工具操作做成明确、可审阅的动作

草拟知识页、待办或个人规则时，用户应该看到准备做什么、依据是什么、会改变什么，并能接受、编辑或拒绝具体提议。

确认绑定动作 ID、提议内容版本和必要的目标版本。用户明确选择多项时允许批量确认，但一句没有动作绑定的“好”不批准整个会话积压的操作。编辑提议后旧确认失效；历史草稿可重新打开审核，不静默丢弃。

第一版采用“草拟后持久化，用户审阅，再显式执行”，不要求模型请求一直挂起等确认。主对话、知识页处理和个人规则的确认入口必须遵守同一授权原则，并复用现有受保护页面审阅契约。

### 6. 给知识页对话设计任务相关上下文

同一篇材料上的局部问答、全文总结、跨来源比较、局部修改和全页修订，不应全走“正文加历史一起塞入 system”的通道。

- 局部问答：选择相关段落，保留精确来源。
- 全文总结：复用现有完整阅读和分块缓存，明确覆盖范围。
- 局部修改：绑定选区与当前修订，不改未选中内容。
- 全页修订：保留完整依据和原版，不能把截断输入生成的结果冒充完整修订。
- 后续追问：沿用任务目标、材料身份和有效版本；源内容变化后重新核验。

这项优化把通用聊天运行机制与 Elsewhen 的知识证据系统结合，而不是把知识能力换成普通聊天记忆。

### 实施边界

1. 事件仍经 `Store::insert_event()` 等现有统一事务入口提交，原始事件保持不可变；生成失败不回滚用户输入。
2. 受保护页面、规则强度、来源快照和人工修改仍遵守当前审阅约束；“接受建议”不自动等于执行或创建永久规则。
3. Provider 配置仍由数据库管理；保留完整序列化请求、工具定义与输出预留的最终预算检查。
4. FRB 是当前进程内桥接，不引入 Bun/SSE 服务来复刻参考产品的部署形态。
5. 不新增后台知识整理的手动触发或重试按钮；聊天停止/重试仅作用于相应聊天 run。
6. 日志默认只存元信息和版本标识，不默认保存用户完整 prompt、原文、密钥或工具参数。精确请求重放需要另行定义本地显式诊断及保留策略。

## 参考机制与事实边界

参考版本：本地 `ref/rikkahub-desktop`，本次核查的提交短 SHA 为 `1402bd5`。该目录不随主仓库分发；落地时应把具体不变量和回归用例写入本项目，不依赖外部目录永久可用。

| 值得借鉴 | Elsewhen 的适配方式 | 不作出的承诺 |
|---|---|---|
| GenerationEvent、统一应用器、带原因的取消 | Rust 生成事件、持久化 run、Dart reducer | 只接 StreamSink 就完成生命周期改造 |
| 合帧、增量更新、终态快照和重同步 | 流量有界的 FRB 事件与快照协议 | 照搬 33ms / 200ms 就获得同样性能 |
| 易变记忆段的缓存快照 | 按段定义稳定性与失效版本 | 冻结全部 system，或易失缓存等于逐轮请求审计 |
| 摘要压缩及历史边界 | 独立摘要基底、消息范围和有效性校验 | UI 分割线本身能保护压缩切点 |
| 明确 ID 的工具审批 | 具体动作与版本确认，沿用业务验证 | 所有工具都必须暂停模型等待人工 |
| 队列与 steering | 持久待生成状态，确认注入后消费 | 内存队列足以满足重启恢复 |

本次核查已澄清的基线：当前工具循环 usage 按请求累加；`compress_context` 只改内存且片段分支可达；最终预算已有整轮裁剪与当前工具交换保护；正常 bridge 初始化后开库不重复执行全部迁移回填；RikkaHub 有搜索和引用，SSE 过载有断连重同步。这些不再作为待修 bug。仍然需要优化的是完整交互、连续性和可恢复性，而不是证明哪一方架构全面更强。

## Alternatives considered

### 整体移植参考产品

不选。Flutter 单窗口与 Bun/Web UI 的连接管理、渲染和持久化条件不同；迁移成本高，也容易丢掉本项目的事件、证据和审阅边界。取机制与不变量，不搬整套系统。

### 只加流式输出，其他维持原状

不选为最终方案。能改善首字等待，却不能解决停止、切页状态、工具结果、重启和错误收尾。以一个最小纵向切片实现流式，但它必须落在统一 run 契约上。

### 先扩大上下文窗口或冻结整个上下文

不选。大窗口不能代替任务管理；整段冻结会使来源、规则和执行结果陈旧。先统一选材与预算，后做可测量的稳定前缀优化。

### 压缩时直接替换历史

不选。摘要可能失真，修改期间也可能到来新消息。保留原文、单独保存覆盖范围和摘要版本，更适合本项目的可追溯和可重算要求。

### 立即增加独立的全局事实记忆库

暂缓。Elsewhen 已有规则、实体事实、知识和近期背景；先把这些能力用于连续对话。只有具体用例证明仍缺用户可编辑的轻量偏好层时，再评估新增，避免重复事实源。

### 第一版同时做多助手、多模型协议和完整分支 UI

暂缓。不是本轮主要用户收益。保留现有数据与 API 兼容性；新增摘要、恢复和队列必须明确当前输入路径，但不以此扩展成多分支聊天产品。

## Acceptance criteria

- 对话有应用提供的日期、时间与时区线索；能区分消息时间和事件时间，不改写原始输入，也不冒充已经检索到某日事实。
- 用户能在主对话和知识页对话中看到真实生成进展，并能停止当前 run。
- 切页、失败、正常退出和异常重启后，回复、运行状态与已完成业务动作可解释，不静默重复写入。
- 用户确认的是具体内容和动作；否定句、普通短回复和旧授权不执行其他提议。
- 长对话保留目标、约束和待办事实；摘要有覆盖范围、可追溯原文和失效规则。
- 长材料按任务选择局部证据或完整阅读，不伪装阅读全文，不截断当前用户问题来勉强发请求。
- 生成中记录仍本地保存；后续排队与补充要求至多消费一次，并遵守停止语义。
- 用户体验与模型质量在固定场景中验证；mock/bridge 通过不等于真实模型效果达标。逐项标准见 Roadmap。

## Risks

- **改动扩散：** run、provider、bridge、UI 同时变化。按纵向切片交付，兼容旧调用期间也复用同一生成核心，不长期保留两套实现。
- **流式绕过现有校验：** 工具协议残片、未经核验的引用和虚假的“已保存”不能因为增量展示泄漏成已确认结果；流式草稿与最终结果必须区分。
- **取消与写入竞态：** 用户点击停止时某个事务可能已经提交。停止后不发起新动作，已提交动作如实展示，不能承诺回滚或服务商停止计费。
- **摘要失真：** 不将摘要升级成永久规则或一手证据；允许回读原文，失败时沿用上一个有效基底或明确降级。
- **缓存陈旧与收益不确定：** 有效性优先于命中率；缓存收益依赖实际端点，不预先承诺成本下降比例。
- **过度建设：** 不先复制 Web 连接管理或全局错误中心；可观测性先服务具体对话排障和验收。
