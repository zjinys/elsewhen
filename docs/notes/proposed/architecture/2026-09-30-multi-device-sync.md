## Problem

Elsewhen 需要支持“手机随手记录、电脑继续处理、其他设备查看结果”，同时保留本地优先：断网和 AI 失败不能阻止记录保存，原始事件不可变，人工修改和业务动作不能被后台静默覆盖或重复执行。

2026-10-03 用户认可修订方向：**多端离线记录、加密中继优先、后台加工有归属、修改有版本**；随后明确要求**新设备开箱即用，Provider 全部信息（包括 API Key）也要同步**。本文替换原提案的“单 writer + 软只读 reader + 通用 INSERT OR IGNORE”及“Provider 密钥不同步”规范，首次提出日期与路径保留。方案认可不代表功能已实现。

## Proposal

### 1. 产品边界：可写设备与加工设备是两回事

- 所有已授权设备都可以离线追加个人记录。记录在本地事务提交后立即成功，不等待中继、其他设备或模型。
- 数据集指定一台**后台加工设备**，负责分析、知识消化、来源编译及相关后台维护。它不是唯一能记录的设备。
- 前台聊天由用户在发起设备明确启动，仍绑定已保存输入。同步历史消息不是生成授权，不会让其他设备自动回复或重放工具。
- 首个可用版本同步原始记录、普通对话及必要关联、对话元信息、分析结果和 **Provider 完整配置**。已授权新设备首次同步完成后恢复全部 Provider、API Key、当前激活项和运行参数，不要求再填密钥。Wiki 页面及其证据依赖、待办和规则在后续完整对象切片开放。
- 不承诺任意两份独立历史数据库自动合并。首版配对目标使用新的数据集存储；已有本地数据不得被覆盖或悄悄混入，保留独立数据集并明确切换。已有库合并另做预览、ID/引用检查与确认流程。
- 数据集切换只保存下次启动选择：本机目录册为每次加入预留独立目录，校验已完成快照、签名成员和本机密钥后原子发布选择。当前 `AppConfig::pin` 与已打开连接不改指向；原库/Provider 保留。否决进程内直接改全局路径（会混用旧连接、在途请求和视图状态），也不搬动打开的 SQLite/WAL；代价是切换需要重启。损坏/缺失选中目标明确报错，不能静默打开另一个库。目录册 schema、边界与测试见同步完成记录；选择/修复 UI 尚未接入。
- 同步关闭时保持当前单机行为。开启同步后的设备能力由 Rust 业务边界校验，不能只依赖 UI 隐藏按钮。

首版是“记录/对话同步”，不是“整个知识库已一致”。普通对话所引用、但尚未同步的知识页应显示来源不可用，不把缺失引用显示为可核验来源；知识页专属对话随完整 Wiki 依赖一起开放。

### 2. 身份、顺序与版本

| 身份 | 作用与约束 |
|---|---|
| `dataset_id` | 一组受同一成员授权管理的数据，阻止跨库误导入 |
| `device_id` | 已配对安装实例的身份，关联认证密钥；不是设备显示名称 |
| `origin_stream_id` | 该安装实例的一条不可回退写入序列；恢复备份后不得无条件延用旧流 |
| `origin_seq` | 流内连续序号，与领域事务同时分配；不依赖墙上时钟 |
| `op_id` | 操作的稳定全局身份；重发、转交、快照恢复保留身份与内容哈希 |
| `object_id` / `revision_id` | 业务对象与不可变修订身份；不以本地自增键或 slug 代替 |
| `membership_version` | 有明确授权来源的成员变更版本，不由任意设备自行提高 |

每个可变对象的操作携带 `base_revision` 和新修订身份。因果关系通过操作依赖、基底版本和每来源进度表达，不把 `updated_at` 当冲突胜负或同步游标。

同一对话的消息保留父消息/输入关联；并发追加没有先后因果时使用所有设备一致的稳定键作展示排序。显示时间仍是原始时间，不能为了排序篡改记录时间，也不能继续用本地 `rowid` 打破平局。

**重装与恢复**：设备身份密钥存放在独立于业务库的受保护存储中。受支持的备份恢复流程必须重新登记写入流，或由已授权设备确认新的安装实例；不自动恢复旧执行租约。收到旧流相同序号而内容不同，拒绝并提示修复，不能当重复成功。直接复制正在使用的数据库和密钥不是受支持的多设备安装方式，不能声称协议能自动识别所有私下克隆。

### 3. 同步对象清单，而非复制全部 SQLite 表

| 对象 | 同步规则 |
|---|---|
| 原始事件 | 追加，保留 ID、原始时间、文本和来源；不引入 UPDATE/物理删除原事件的同步指令 |
| 统一输入 | event、message、input_record 及必要父对象引用作为原子业务单元；幂等键携带来源作用域 |
| 普通对话与消息 | 同步创建、消息追加及所需因果关系；重命名、归档、删除也须有版本契约，不能只传新增消息 |
| 分析结果 | 绑定 event、输入版本、分析策略与任务身份；接收结果不重新调用模型，状态从有效结果派生 |
| Wiki/来源/修订 | 后续按完整证据闭包同步：页面、来源快照、修订、引用、依赖与删除状态；不能只传正文 |
| 待办、目标、规则 | 后续按基底版本更新；并发变化进入审阅，不用时间戳最后写入覆盖 |
| 已执行业务结果 | 在该对象已支持同步的阶段传结果及必要溯源；接收结果不是重新执行动作 |
| 待确认提议、授权令牌 | 首版保留在发起设备，不跨设备消费；可见的提示不得变成可点击重放的授权 |
| 分析/生成队列、运行租约、流式草稿 | 本地运行态，不复制到其他设备继续执行；另存稳定任务身份和结果归属 |
| Provider 完整配置 | 首版加密同步全部配置及 API Key、激活项和运行参数；敏感载荷走专用边界，见下节 |
| 配对私钥、设备身份私钥、本地路径、设备偏好、用量统计 | 不进入内容同步包；每台新设备生成自己的身份 |

字段清单按协议版本固定：不接受远端指定任意表名/SQL，不使用 `SELECT *` 或通用 `ATTACH` 导入协议。内容里用户自己输入的路径属于原文，不篡改；系统管理的绝对目录路径、缓存路径和设备身份凭证不得作为可迁移执行配置发送。Provider API Key 是用户明确要求同步的敏感配置，不与设备私钥混为一类。

首版不支持的对象必须在设置与状态中说明。对话包含 Wiki 引用时只传允许的终态文本，不伪造不存在的来源对象。

### 3.1 Provider 开箱即用：配置完整同步，密钥不明文暴露

这属于首版要求，不推迟到完整 Wiki 同步。新设备的配对确认明确说明“将获得此数据集的 Provider 配置和 API Key”；授权加入后默认完整同步，不要求逐个 Provider 重新授权或填写。

当前配置字段依据 `src/storage/provider.rs`、`src/api/provider_config.rs`：

- 全部配置的稳定 `id`、`name`、`provider_type`、`base_url`、`model`；
- 实际 `api_key`，不是设置页返回的空串或“已配置”占位；`api_key_source` 按接收后的数据库来源语义正确恢复；
- `temperature`、`max_tokens`、`context_window`，保留显式空值和默认语义；
- 当前激活配置，以及现有运行时故障切换依赖的顺序；不能因为导入时间不同而换了默认模型或备用顺序；
- 后续新增的运行配置字段必须更新协议/兼容性测试，不能悄悄少传。

推荐把配置集合、激活引用及故障切换顺序作为一个**版本化 Provider bundle** 同步。首个快照完整应用；新增/修改/删除/切换激活项产生新版本，事务内校验引用与单激活约束后整体发布。并发修改保留候选，审阅时掩码显示密钥，不把新地址和另一版本的旧 Key 自动拼接。删除与 Key 轮换同样受版本检查约束。

实现约束：

1. Rust 内部通过受限同步接口读取完整运行配置，保留设置页 DTO 不返回明文 Key 的现有边界；不能直接用 `list_ai_provider_configs()` 的脱敏 DTO 导出。
2. 敏感 bundle 在进入持久 outbox/快照暂存前就加密保护；通用操作日志只记录密文引用/版本，不复制明文 Key。传输再按接收成员认证加密，明文不落临时导出文件、日志、崩溃诊断、测试报告或普通 UI。
3. 解密和校验成功后在受限事务里应用到本机 Provider 存储，数据库仍是运行配置真源；受保护安装已实现本机主密钥 AEAD 封装（v23，见下节），运行读取需解锁，普通设置读取仍脱敏。未启用保护的内部原语测试不代表 App 接收流程；原生平台与完整配对协调仍按 S02/S04 验收。不能把线上加密等同于静态加密，也不能把新写入保护说成历史明文已擦除。
4. 同步解码不能沿用设置编辑的“空串表示保留旧 Key”协议。缺失/保留/替换/清除必须明确，避免 Key 轮换或删除被误当成未修改。当前产品不支持的配置状态应整体拒绝，不能不完整激活。
5. 新设备首次授权完成、敏感配置验证并发布后即具有相同配置；不用再次手工选模型。但不会因为获得配置就自动重放旧消息、启动全部后台任务或发送真实模型探测请求。
6. `localhost`/环回地址、仅旧设备可达的内网服务与硬件限制无法靠复制配置解决：保留原配置，展示“地址需适配/当前不可达”；用户可明确修订为新设备可访问的服务地址，不能静默改地址并把 Key 发往另一个服务。可达性和真实调用验收单列。
7. 新设备已有独立数据时仍使用第 1 节的数据集隔离，不覆盖原库 Provider。支持共享数据集内的配置冲突，但不自动合并两个独立数据集的密钥库。

### 3.2 Provider 静态保护与编辑基底（2026-10-05）

落盘采用独立的 `provider_key_secrets` AEAD 密文列，主密钥来自本机受保护存储，配置与密文仍以数据库为真源。认证上下文绑定数据集、安装、profile ID、URL 与 provider 类型；改写目标地址不能继续解出原 Key。保护策略启用后，SQL 触发器拒绝明文 Key 写入，新增/同步配置先加密再绑定 SQL；普通设置 DTO 只读元数据，锁定时仍可查看，但运行时不能读出 Key，也不以此触发其他 Provider 的兜底调用。

同步入库保留显式空 Key / 缺失 Key 的区别；本机编辑空串仍表示保留，但必须校验用户实际看到的编辑基底。v24 为每个 profile 维护本机随机编辑 token，正文参数和 Key 改动都会失效；编辑、激活、删除在写事务中验证原 token，不能重新读取新 token 再保存旧表单。token 不进入同步 bundle，避免把别的设备的审阅依据当本机确认。

相较于把 Key 移出数据库单独管理，该方案保留完整配置原子发布和空值语义；相较于只靠文件权限，可阻止新接收库或新写入中的 Key 以明文落盘。代价是改动受保护配置需要先解锁本机主密钥。原来已经明文保存的历史页、已有备份，以及用户主动写在 URL/事件正文中的秘密不因此被安全擦除；不以当前字段加密声称能回收这些历史副本。完整恢复/原生平台签收仍按路线图推进。

### 4. 事务日志：outbox / inbox

推荐新增以下逻辑存储，具体 SQL 在 S01 定稿，不修改历史迁移：

- `sync_identity` / `sync_members`：数据集、安装实例、流、成员状态与公钥元信息；设备身份和配对私钥不进入同步表。Provider 敏感配置另走加密载荷。
- `sync_operations`：不可变操作、来源序号、内容哈希、协议版本、依赖与业务载荷。
- `sync_outbox`：每个收件人的待投递状态、重试与投递记录，业务写入产生操作时原子建立。
- `sync_inbox` / `sync_frontiers`：接收、等待依赖、隔离、已应用状态，以及每来源连续应用水位。
- `sync_peer_acks`：每个成员对每来源流的已持久化应用进度，独立于中继信封游标。
- `sync_object_heads` / `sync_conflicts` / `sync_tombstones`：对象头版本、并发修订及删除记录。

`sync_operations` 中的实体载荷与领域数据具有同样隐私级别，使用本地数据库既有保护；禁止原文进入常规诊断日志。

#### 本地提交

```text
校验用户输入与本地写权限
  → 一个事务：领域数据 + 关联 + 待加工资格 + 操作/来源序号 + outbox
  → COMMIT
  → 返回本地保存成功
  → 独立 worker 加密、上传、重试
```

复用并收敛 `Store::insert_event()` 所属的事件提交核心及现有统一输入事务。同步不能另开原始事件 SQL 旁路；公共捕获入口不允许调用者任意伪装远端 ID/时间。受信同步应用在同一存储契约下使用经过验证的原始身份。

仅已支持对象的写路径加入领域操作。不能只给一个 Flutter 按钮挂 outbox，而遗漏 Capture、聊天工具或后台写入。可以在本地使用内部辅助日志，但日志触发器不能代替明确的跨设备业务载荷与事务边界。

#### 远端应用

```text
有界接收 → 校验协议/收件人/成员授权/端到端认证 → 检查来源与依赖
  → 一个事务：去重校验 + 应用完整业务单元或持久保存冲突 + 进度/回执 outbox
  → COMMIT
  → 发送应用回执；随后才可确认删除中继信封
```

- 同一 `op_id` / 流序号、相同哈希：重复投递，无新增消息、任务或再次导出。
- 同一身份、不同内容：协议错误，隔离，不更新成功水位。
- 缺失前序/父对象：等待依赖并请求缺口，不以 `IGNORE` 吞掉外键失败。
- 接收端可以转交已验证操作，但必须保留原始身份，不能生成新的本地操作形成回声。
- 明确拒绝不受支持的版本和越界载荷；隔离包有上限和可诊断状态，不把失败算成功。一个来源阻塞不应阻止其他独立来源。
- 冲突双方已可靠保存后，可确认“操作已持久化”，但对象状态仍是“待审阅”，不能把应用回执等同于业务合并完成。

### 5. 首次快照、缺口与清理

**三个不同的确认**：

1. 中继收下信封：仅投递成功，源设备仍保留待确认操作。
2. 收件设备事务落库：应用回执，允许重复投递安全结束。
3. 所有必要成员确认，或按明确规则退出增量历史：才允许回收操作历史。

每个收件人的网络信封 ID 只用于取件，不代表来源操作序号或业务成功。发送响应丢失、应用回执丢失都通过稳定身份重传，不能因此重存用户消息。

首次同步使用同一一致读快照导出受支持对象、身份/版本/必要 tombstone 与**每来源水位向量**。快照分块、有总量与解压上限、清单哈希；接收端暂存校验完成后原子发布，发布与进度一致。快照之后的操作继续保留，新写入不因“已经开始导出”而丢失。

GC 约束：

- 新成员先完成快照并确认，再进入正常增量集合；初始化期间必须保留其快照之后的操作，不能因“尚未参与 GC”丢掉追赶窗口。
- 所有 active 成员都纳入确认计算，缺失水位按未确认处理；不能通过过滤 NULL 或其他流的记录排除落后设备。
- 长离线保留需要的操作；达到存储上限时明确转为“需要重新快照”的协议状态，不能静默清理。任何旧离线操作重入仍必须接受版本/tombstone 检查。
- 中继 TTL 到期只丢传输副本，源操作未确认就需重发或安排快照；7 天邮箱不是备份。
- tombstone 的回收要考虑离线设备与快照世代；不能只因页面已删除或当前在线设备确认就清掉防复活依据。

### 6. 可变对象：版本检查与明确冲突

基础规则从首版对话元信息开始使用，S05 再扩展到完整 Wiki 等对象：

- `base_revision` 与当前头匹配：在事务中快进。
- 同一个修订重复收到：无操作。
- 基底不同且无法证明是已包含的祖先：保存并发候选，不自动选“时间更新”的一份。
- 人工与 AI 修改相遇：AI 不能覆盖人工修订；人工与人工冲突也不以设备优先级静默裁决。
- 删除和编辑并发：进入冲突处理。删除留 tombstone，旧设备恢复不能无条件复活对象。
- 用户解决冲突产生新的显式修订，记录所处理的候选；审阅绑定显示时的版本，状态变化则重新审阅。

对话删除仍遵循“先归档且不删除知识页专用会话”等现有业务前提，并与消息同步保持一致；同步对话删除不得顺带删除不可变原始事件。

Wiki 的 slug 是可改的定位名，不是全球对象身份。同名 slug、不同对象 ID 不能靠 `INSERT OR IGNORE` 合并；确认改名时需要更新引用映射。来源快照、历史修订与依赖采用精确身份，缺失证据只可标为待补齐，不能推断当前正文就是历史依据。

### 7. 后台加工与前台生成

#### 后台加工

稳定任务身份至少包含 `dataset_id`、任务类型、输入对象/版本、策略版本。指定加工设备在本地唯一约束和事务内认领；结果与任务完成记录一起保存并形成允许范围的同步操作。

- 捕获设备保留待加工资格，但非加工设备不领取分析/知识任务。加工设备收到记录后按任务身份补足本地工作，已有对应结果则不重复执行。
- 既有未完成任务在开启同步时要有迁移/暂停规则；不能只阻止新任务，却让旧队列继续运行。
- 已有不同设备生成的历史结果不能伪装成同一确定结果；保留来源/版本或显式选择，不能为了统一任务 ID 丢弃事实。
- S04 只同步已支持的分析结果。Wiki 维护可在加工设备本地继续，但在 S05 前不宣称其页面成果已同步。

#### 前台聊天和业务操作

用户仍可在设备本地发起聊天，运行绑定输入 ID 与发起设备；收到远端用户消息、终态答复或“已执行”文本不会自动启动新的 run。相同会话的并发问答保留输入/答复归属，不能让最新到达消息抢走旧 run 的目标。

待确认提议与执行租约不复制成可执行授权。远端缺失提议只能展示不可执行的状态说明；需要执行时必须在支持的设备重新建立、展示并确认当前版本的提议。现有 `storage/approvals.rs` 的版本/目标检查与不确定结果策略继续有效。

不能承诺分布式“恰好一次外部副作用”：即使同一设备在网络响应丢失后也可能无法确认远端执行结果。对不支持幂等或结果查询的外部动作保持“需核实”，不盲目重试。

### 8. 加工设备移交不是本地改一个标志

第一版不自动故障转移。正常移交必须完成：

1. 旧加工设备持久化停止领取新任务，结束或标注在途任务；不确定副作用不能视为完成。
2. 旧设备把最后的任务/结果状态和经授权的移交记录送达新设备。
3. 新设备核验完整交接基底后确认接管；旧设备保持停止状态，迟到结果按任务身份/基底核查。
4. 成员逐步收到新的加工归属；尚未同步的记录可以继续本地保存，不能触发第二个处理者。

本地 epoch 用于拒绝**已经知道失效**的结果，不是跨设备互斥锁。旧设备失联时，用户仍可记录，但不自动提升另一台设备接管不确定任务。失联强制接管、恢复旧快照的双主防护如果需要更强保证，必须引入协调仲裁或执行端可验证 fencing，不能凭空从盲中继获得。

### 9. 安全配对与密钥边界

- 配对由现有授权设备发出短期一次性邀请并明确确认，绑定数据集、双方设备公钥、收件地址与协议版本。二维码是带外信任材料，不意味着网络无攻击面。
- 邀请兑换采用 `snow 0.10.0` 的 `Noise_NNpsk0_25519_ChaChaPoly_SHA256`，并用 Ed25519 绑定双方长期身份；预览、明确批准与新端安装确认分离，密钥版本不得回退。2026-10-06 已增加后审批检查点：原始响应、方向密钥、安装证明及消费回执仅入本机加密 vault，每个新修订经原生存储确认才可输出；授权与密钥/回执原子提交。未审批 Noise/邀请 PSK 不序列化，重启后重新邀约/审阅。10 项存储、3 项运行时测试通过；2026-10-07 检查点进一步保存限定方向/到期的临时 relay 能力（不保存邀请 PSK），恢复清单显示撤销。实际 Worker 14 项通过，包含从重开库恢复响应/证明投递，以及授权/撤销丢失响应的精确后态重试。owner 的邀请/指纹预览/原 token 审批与保护修订后投递已接开发预览（新增 Rust 5 项、Flutter 6 项与实际 Worker 流程通过）；新端原生解锁/加入 UI、安装证明与名册/快照自动交接仍未接入。不自创“先裸传 token 再协商加密”的握手。
- mailbox owner 身份与投递凭证分离。只有 owner 能授权/撤销发件设备；投递凭证限制目标邮箱和能力，不能用于 fetch/ack/status 或管理成员。
- owner 首次创建必须证明与邮箱身份的绑定，不能接受任意新密钥在已知邮箱地址上自签抢注。邀请兑换/注册、续期和撤销都有幂等及竞态规则。
- 首个信封实现采用 ring 的 ChaCha20-Poly1305 + Ed25519，随机 nonce、分块上限和固定上下文认证已测试；内容密钥按收发方向分开，绑定数据集、发送/接收设备、用途与密钥版本。收件邮箱身份独立于设备对共享密钥，不能让双方因同一派生式得到同一个邮箱。密钥寿命/持久化与配对协调仍属于 S02 未完成部分。
- AEAD 的认证上下文覆盖协议/数据集/来源/目标/批次身份，内容中包含原始操作来源的可验证证明。转交其他来源操作、快照清单与成员变更也必须可验证，不能只因中继或某个转交者声称可信就提高权限。
- relay HMAC 凭证只解决传输访问控制；持有 HMAC 密钥的中继也能生成相同认证码。它不承担端到端内容/成员授权证明。
- 载荷离开设备前必须已经认证加密。base64 不是加密，不允许把 API 参数名叫 `ciphertext` 当作保证。
- 设备身份私钥/配对密钥使用受保护的本机存储，不复制给新设备、不写普通日志。Provider API Key 按第 3.1 节加密同步；不能为了同步密钥而开放明文设置查询 API。
- 撤销包括成员授权、relay 投递权限与后续内容密钥更新。已被撤销设备拿到过的明文、旧密钥与旧密文无法远程收回；离线设备在收到撤销前仍可能持有旧授权，不能承诺即时全网生效。**撤销同步资格不会吊销已复制的 Provider API Key**；设备丢失后须在 Provider 侧撤销/轮换该 Key，再把新配置同步给剩余设备。

自托管表示用户控制中继部署（relay 只保留 standalone Node 实现，不再有 Cloudflare Worker 版），不表示没有基础设施提供者。运营者可见连接 IP、流量、时间与邮箱关联；内容保密依赖实际端到端加密，而不是邮箱标识被哈希。

### 9.1 成员授权的首版落地选择（2026-10-05）

S02 当前切片采用**固定数据集 owner → 成员的一跳签名授权**。owner 不是唯一记录设备，也不因该角色获得自动接管后台加工的能力。只有 owner 的 Ed25519 身份能发布有界的完整成员名册；每版包含所有既有身份与撤销标记，版本单调递增，同版本异文拒绝。设备 ID、公钥、来源流绑定后不改写；撤销不可在同一身份下重新激活，重新加入生成新安装身份。首版不做授权委派或 owner 轮换。

配对和成员授权分开：Noise 明确确认绑定 owner 身份与当前名册的版本/哈希锚点；新端保存身份密钥后，仍需收到匹配信任根的签名名册才可收发领域内容。将新端私钥自签、普通同步消息、快照里的 `active` 字段当成授权均不可接受。完整名册可跨过未见的中间版本，但必须保留已知身份/撤销，旧快照不能恢复成员权限。名册不携带内容密钥或 Provider Key，投递仍走已配对的方向密钥。

这比委派证书链少了失效传播与多管理端冲突，代价是成员管理需要 owner 在线，且保留撤销历史后的名册有容量上限。仅把每个成员的自签公钥塞进 SQLite 更简单，但不能证明加入资格，因此否决。该选择不解决 owner 私钥泄漏、私下克隆安装、即时全网撤销或加工移交；相关门禁仍保留。代码/测试完成证据见同步路线，当前不开放 App 入口。

### 9.2 本机准备与受保护修订（2026-10-05）

本机准备通过 FRB 的请求/安装/确认三步处理。原生密钥库先保存新安装的主密钥与初始修订 1，再创建数据库 vault，避免首次建库成功但没有受保护修订的窗口。后续解锁读取原生修订下限，验证密文及当前身份；原生修订确认前不恢复同步库的后台工作。缺失修订不从数据库里的数字自行重建，损坏/锁定也不生成替代密钥。

同步会话与后台调用持有工作区文件租约。关闭会话时在途调用仍持有租约，另一进程不能趁机把它的 running 工作重排；普通单机初始化恢复同样不能抢占在途后台。UI 原生写入未结束时不提前释放租约，取消按原请求身份定位，旧回调不能锁住新会话。该租约只约束本机同一工作区，绝不是跨设备加工锁。

设置页区分“本机准备/解锁”和“联网同步”。创建仅在开发预览开放，已配置身份可解锁；没有新增知识后台手动触发按钮。否决在任何钥匙错误后静默重置，以及恢复数据库时用本库数字当作受保护下限。代价是丢失密钥/修订需要恢复流程，而不是省一步确认。当前工程验证为 Rust 555 passed / 11 ignored、Flutter 302 passed；真实 OS 密钥库、App 配对/通道和完整发布门禁仍待签收。

### 9.3 配对路由认证与本机持久化（2026-10-06）

邀请的 relay URL、issuer mailbox 和临时 sender 属于 Noise prologue，joiner mailbox 属于请求及批准的长期身份签名声明。双方逐值确认，拒绝路由缺失/降级和地址碰撞；relay 审批必须附带数据集 owner 授权锚点。收到的路由只是地址，不能代替名册授权或中继 owner 凭证。邮箱由各自本机随机 owner 凭证独立派生，不由共享内容密钥推导。

批准后的方向路由与方向密钥一并放入本机加密 vault；加载校验本机邮箱，重复版本必须内容相同，撤销后拒绝读取通道。旧无路由 vault 仍可解密，但不能凭空猜测网络地址。否决从未认证信封发现路由，也不把 owner 凭证发给对端。持久化增加 CAS/保护修订协调成本；App 的邀请授权、安装确认、名册与 relay grants 尚需可恢复状态机，本切片不开放联网入口。

2026-10-06 验证：Provider 7 项、配对 14 项（新增路由 6 项）；独立 Node/OpenSSL 固定信封向量及 Rust 2 项逐字节验证。全量 Rust 570 passed / 11 ignored（另配置环境 5 passed）、Flutter 302 passed、实际 Worker 13 passed；定向 analyze、桥接重生成/release/Linux build 通过。设置页/隔离 bridge 明确密钥锁定与过期编辑基底的失败行为，真实 OS 密钥与设备签收仍未执行。完整证据、工具暂时失败和剩余边界见同步路线完成记录；本文 `Status: in-progress` 保持与未完成的整体方案一致。

### 10. 中继优先，其他传输后置

首版通过加密邮箱提供异步传递，不要求两台设备同时在线。轮询由应用启动、恢复前台、网络恢复和有界后台调度驱动；移动端休眠时不承诺实时同步。中继失败时记录照常本地保存，显示待同步。

传输统一承载经过认证的协议包，不参与业务冲突解决。P2P 是后续优化，不能把“问中继是否在线”作为读取离线邮箱的前置：对端离线时恰恰需要取件。

`presence/peers` 当前路由未闭合，首版不用它决定能否同步。P2P、NAT 打洞、局域网发现与手工同步文件不进入首版门禁。独立完整备份/恢复另行设计，不能把中继暂存当数据唯一副本。

## Alternatives considered

| 方案 | 取舍 |
|---|---|
| 单 writer、其他设备只读 | 简化内容复制，但不能满足手机随手记录；保留单一后台加工归属，不保留内容只读限制 |
| reader 可编辑但不回传 | 不是真正的多设备一致性，制造不可预期分叉，放弃 |
| SQLite 文件覆盖/网盘同步活动库 | 无法处理并发写入与 WAL 一致性；独立备份可以做，但不能替代同步 |
| 通用表触发器 + INSERT OR IGNORE | 无法表达修改/删除/证据依赖与业务事务；内部日志可辅助，不作为同步语义 |
| 时间戳 LWW / 自动合并所有文本 | 时钟不可信且可能静默覆盖人工修改；先用明确基底与冲突审阅 |
| 所有设备各自重跑后台任务 | 重复成本、结果分叉与副作用风险；先指定加工设备 |
| Provider 不同步或只同步模型名 | 新设备必须重新配置，违背开箱即用要求；改为完整认证加密同步，接受授权设备持有 Key 及丢失后需上游轮换的代价 |
| 上来就引入通用 CRDT | 不能自动解决业务授权、来源证据、删除和外部副作用，成本超过首版必要范围；不排除后续用于合适字段 |
| P2P / 中继 / 文件三线同时实现 | 扩大配对、发现、故障与测试面；先中继形成异步闭环，P2P 后置 |
| 云端保存明文并执行全部业务 | 容易做协调，但扩大隐私和服务依赖；当前不采用，盲中继只负责投递 |
| 失联自动接管 | 单靠各设备本地状态无法保证无双主；首版宁可保留等待，也不盲目重做不确定业务 |

## Acceptance criteria

每项的执行步骤与证据归属见路线图，文档自检不计为以下功能通过：

1. 两/三台隔离设备离线追加、时钟不同步，恢复连接后得到相同支持范围的数据、身份与确定展示顺序。
2. 相同操作重复投递无重复事件/消息/任务；同 ID 异文拒绝；乱序、缺口、未知版本、父对象未到不被静默吞掉。
3. 故障注入覆盖领域写入、outbox、接收应用、游标和回执的所有提交边界，崩溃恢复不丢数据、不先确认成功。
4. 首次快照与同时写入、TTL 过期、满配额、丢失回执、新成员、长离线和需要重新快照的设备均可恢复。
5. 已授权 sender 不能读取/删除收件箱，未授权设备不能注册或投递；实际 Worker 多邮箱、权限竞态和真实 AEAD 测试通过。
6. 修改/删除与离线编辑冲突被保留并可审阅；原始事件不可变；Wiki 源版本/引用/依赖缺失不伪装有效。
7. 非加工设备不领取后台任务；导入终态结果和历史消息不触发模型/业务动作；停止的前台队列不因同步重新开始。
8. 撤销、正常移交、备份恢复和旧设备迟到结果有明确状态；不自动接管结果不确定的任务。
9. 主对话/Capture/知识页既有行为有回归；真实 bridge 全部使用隔离库。协议、真实 Worker、真实设备与模型质量验收分别记录。
10. 新授权空设备首次同步后，全部 Provider、真实合成 Key、参数、当前激活项和备用顺序一致；无需重新填写即可对受控本地服务完成调用。Key 轮换/删除/配置冲突不会丢失或泄露，脱敏 DTO、日志、outbox 和临时文件不出现明文 Key；真实外部端点另经授权验证。

## Risks

- **完整同步不可因 relay 测试通过而直接上线**：旧注册/读删权限、TTL 签名与分页问题已在 relay v2 修复并通过实际 Worker 回归；发现接口明确禁用，不伪装已可用。配对协调、持久密钥、完整快照与 App 生命周期尚未完成，见[中继说明](../../../../relay/README.md)。
- **接入是写入契约工程，不是新增几张表**：必须覆盖现有事务、多种捕获入口、后台结果、级联删除与精确证据关系。原“约 1710 行即可完成”的估算没有验证依据，不再作为交付承诺。
- **只同步一部分数据会有产品边界**：首版 UI 必须明确范围，不能让用户以为另一台设备已有全部 Wiki 和可执行提议。
- **成员与任务归属需要可验证的控制记录**：不能由收到的普通业务操作任意更改，不能用本地唯一索引冒充分布式锁。
- **延迟撤销、元数据暴露和中继可用性仍存在**：端到端加密解决内容保密，不解决所有网络与设备失陷问题。
- **旧安装和备份恢复容易产生身份分叉**：需要受支持的恢复流程；旧客户端不认识协议时明确阻止同步，不能降级成盲目导入。
- **交付证据分层**：本轮已有内部实现，但受控服务、隔离库和配对原语测试不等于真人设备开箱即用。没有修改个人数据库/配置或部署线上中继，不将源码核查、模拟测试或文档认可写成真实设备验收。
