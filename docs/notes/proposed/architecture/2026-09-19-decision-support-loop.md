# Agent Note: 决策辅助闭环（定位补全）

Status: proposed

## Problem

系统定位的终点不是"记录和沉淀"本身。用户的目标是：**使用一段时间后，系统能对用户的决策和做事提供辅助帮助**。在这个补全下，记录的意义是"在下一个决策点把过去的自己叫回来帮忙"——规则触发提醒是最直接的决策/辅助支持；后续进一步结合 LLM + 知识库（LLM wiki）对用户提交的记录/事件给出指导。

除此之外还有一个前提性定位：**系统在与用户对话的过程中必然掌握大量用户数据**——不是刻意搜集，而是必然结果。这些数据应当被整理、分类，为系统维护必要的人际关系、做过的事情/项目等，并以结构化形式存储，作为**理解用户的一个方面**。系统本就是私有部署（本地优先），所以不需要为此考虑隐私约束——这也是它敢这样积累的底气。

落到当前代码，距离这些目标各有缺口：

- **规则只活了"对话"半条腿**：个人规则库（`rules` 表，踩坑/教训 → 可执行准则，`[规则提议]` 确认生效）和 system prompt 的"生成回复前对照规则库"都已就位，但规则只在**对话路径**被触发；**捕获窗记录事件（record_event 直写 events → 分析队列）这条最频繁的输入路径完全不碰规则库**，也没有显式的提醒形态（事件旁标记 / 桌面提醒 / 每日回顾聚合），规则本身是无结构自由文本，难以做可检索的确定性预筛。
- **分析是有"提取"没有"指导"**：事件分析（event-analysis-v1 契约，`trigger_analysis`）对每条新记录做的是孤立的结构化提取（人物/项目/待跟进等），prompt 只传 raw_text、**不检索知识库**，因此不会基于已积累的人/项目/长期认知给出可复用经验与建议。罗盘（insight 引擎，`insight-v2-wiki`）已经会在"最近事件 + 已积累 wiki 页"上挖掘反常识认知并回写 `kind=insight`，但它不是对单条新记录/事件的即时指导。
- **缺一个"持续维护的结构化用户模型"维度**：现状已有雏形（wiki「人物·项目(network)」区、事件分析提取人物/项目字段、人物关系提议工具），但都是分散功能，**没有被当作"理解用户"的统一模型持续维护，也没有在分析/指导路径里被引用**。

## Proposal

在保持既有边界（本地优先；事件真源不可改、派生分层；写类操作草拟确认制）的前提下，按下述方向演进，让系统从"认知复利账本"长成"决策辅助层"：

1. **规则引擎升级为"触发"**：
   - 规则补结构化触发条件（触发场景 / 关键词/条件），支持对新输入做确定性预筛，再交 LLM 确认，避免每轮全量 LLM 判断。
   - **触发面从对话扩展到事件/捕获路径**：新事件入库时也检查规则，命中高置信规则的即时提醒（事件旁标记 / 桌面提醒），其余进**每日回顾**聚合兜底——即时提醒必须分级，防打扰。
2. **分析路径挂上知识库，输出升级为"提取 + 指导"**：
   - 分析新事件/新输入时检索相关 wiki 页、人物关系、历史积累作为上下文。
   - 输出在现有结构化提取之外增加指导维度：关联哪些积累、有哪些可复用经验、细化 follow-ups。
   - 指导属于派生层，原始事件仍不可改，符合"事实与解读分层"。
3. **结构化用户模型作为理解用户的地基**：
   - 把对话/事件的副产品——人物、关系、做过的事/项目——持续整理进一个统一的结构化模型（wiki network 区 + 人物关系 + 项目维度），作为**理解用户的一个方面**，与事件账本、规则、知识积累并列。
   - 该模型是决策辅助的必要地基：分析/指导、insight、规则提醒都以它做上下文，"了解你"的深度直接决定提醒与指导的贴合度；模型随使用时长持续成长。
   - 模型属于派生层，原始记录不可改；系统私有部署、本地持有，无需隐私顾虑。
4. **轻量闭环度量**：
   - 指导/提醒 → 用户是否采纳 → 结果如何（接 todo / follow_ups），逐步让系统知道"哪类提醒真有帮助"，是决策辅助能否长期成立的基础。
5. **与既有两篇提案同源**：
   - 「事件可记录性过滤」（输入质量：账本不混闲聊）与「决策辅助」（输出价值：让积累在决策点生效）是一枚硬币的两面；「归档对话可删除」（清理能力）保证账本干净可检索。三篇合起来是这条产品主线。

## Alternatives considered

1. 只在对话内引用规则、分析不做指导（现状）：不满足"决策/做事辅助"的定位终点，规则对事件记录路径完全失明。
2. 所有命中规则都即时提醒：打扰过载，用户会关掉提醒，反而杀死决策辅助；故选分级（高置信即时 + 其余回顾聚合）。
3. 完全不靠 LLM、纯关键词规则匹配：表达不了规则语义的多样性；选用"可检索预筛 + LLM 确认"折中。
4. 把指导直接写进事件真源：破坏"事实与解读分层"，任何派生都必须进派生层。
5. 把用户模型丢给"以后再说"、先做别的：人物/关系/项目是全部分析与指导的引用上下文，缺了它"懂你"无从谈起，应尽早立起来。

## Consequences

- 规则引擎、分析契约（event-analysis 可能升 v2，与可记录性过滤的契约升级可合并演进）、用户模型（network/人物关系/项目维度）、insight/知识库检索路径都会有改动；具体实现仍沿用「方案 → todo → 实施 → 移到 implemented」流程。
- 分析/指导路径挂知识库与用户模型后单条处理成本上升（检索 + 上下文），需守住本地优先与大模型 Provider 边界不破。
- 存量规则需要补结构化字段（迁移/后续逐条补）；用户模型的维护节奏与粒度需要设计（与事件密度平衡）。
- 本文档是本轮"定位 + 缺口 + 演进方向"的结论留痕（决策记录），落地细节另行展开。

## 可行性评估（2026-09-19，代码核实）

结论：该条定位合理且不是从零开始——现状代码已有接近七成的地基，"用户模型"的作用是把分散能力正名为理解用户的第一等公民。

**已存在的地基（代码事实）**：
- `relations` 表（schema v17，src/storage.rs）：类型化关系边 `from_slug/to_slug/relation/confidence/source_conversation_id/last_seen_at`，`UNIQUE(from_slug,to_slug,relation)` 防重复——即"人物+项目+关系"结构化存储，自带置信度与来源追溯，天然符合事实/解读分层。
- 批量提取器 `propose_people_relations_from_events`（src/wiki.rs，由 `propose_people_relations` 工具驱动）：读事件 → `@/#` 标注（用户写死的权威实体）+ LLM 提取 → WriteConfirm 草拟确认制落地。
- memory.rs 已内置质量门槛：只提对用户重要且信息具体的人物；已建档不重复提议；不确定标「待确认」。
- wiki network 分区（schema v18）：`person/`、`topic/` 页归 network 区；`event-analysis-v1` 每条记录分析出 people/projects。

**两个诚实提醒**：
1. "私有部署无需考虑隐私"要打折扣：数据本地持有为真，但分析/提取需调 LLM Provider——人物关系数据会过第三方 API（与事件本就过 provider 是同一件事，非新风险）。准确表述是"默认本地持有、是否外发由用户配置决定"。
2. 用户模型的"维护"绝不能变成主动劳动（人工/周期整理），否则必然腐坏；合理前提是副产品——新事件进来，模型顺带增量更新。

**剩余四件硬活（按难度排）**：
1. 增量维护闭环（分水岭）：从"全量扫描 + 批量提出（带样本上限）"改为"新事件入库 → 只合并新信息 → 更新 last_seen/confidence"。
2. 实体消歧/归并：事件 people 字符串 vs relations slug 无系统化归一；取 slug 归一 + 别名表 + LLM 确认的务实做法。
3. 确认策略分层：高置信（含 `@/#` 权威标注）自动入库，低置信才草拟确认，防关系这类高频低价值数据刷屏。
4. 引用闭环：模型注入分析/insight/规则路径做上下文——孤立建模是死库；本条与决策辅助闭环是同一件事的两面，需绑定落地。

**scope 边界**：浅而实用——实体 + 类型化关系 + 置信度 + 来源追溯（现有 relations 表结构已是该方向），不做全量社会语义建模/知识图谱。

**落地顺序**：增量维护闭环 → 实体消歧 → 分层确认 → 引用注入。

## 定位与能力边界的校准（2026-09-19）

用户追问："用户模型"这一条合不合理，要从**系统定位与能力边界**看，而非代码可行性。校准结论：合理、必要，是决策辅助定位的必然补齐——决策辅助绕不过"系统得知道用户的世界（人物/项目/关系）"这个前提；它不是扩展边界，而是把"只整理用户已托付的记录（副产品）、不主动索取"这条已存在于核心定位的边界正式化。

**三条能力红线**（防止定位从"工具/辅助"滑向"监控/研究用户"）：

1. **只整理已托付的，绝不主动索取**：模型里只有用户记录过的内容，不做外推式画像补全；一旦"理解用户"从副产品变成主动搜集，就从"工具"滑向"监控"。
2. **模型对用户透明、可看、可改、可删**："私有部署不用考虑隐私"应读作"无需担心外泄/合规"，而非"用户不必知晓"；模型必须是一本用户随时能翻开、修改、撕掉的账，而不是暗账（与草拟确认制、「事件可记录性过滤」、「归档对话可删除」同方向）。
3. **模型服务决策、是理解用户的一个方面，不是目的、不是大一统画像**：人物/项目模型与事件账本、规则库、知识积累平行独立，不做全知型数字分身；一旦模型成为"研究用户"的目的，就从"辅助决策"滑向"静静观察你是谁"。

**一句话定位**：Elsewhen 是一个越用越懂你的决策辅助伙伴——它不打听你的生活，只整理你自愿喂给它的记录；它记住你在乎的人和事，不是为了研究你，而是为了在你做决定、做事的那一刻，把你的过去叫回来帮你。它对你的了解是一本你可以随时翻开、修改、撕掉的账，而不是一份你看不见的档案。

## 定位再校准：从"决策辅助"到"决策辅助 + 情绪陪伴"（2026-09-19）

用户决定：原"明确不做"的四个维度（财务/健康明细、地点/常出没、身份/角色、内容/创作主题线）**都应做**——应用的最终形态是能**承载用户情绪、提供陪伴能力**，而不仅是决策辅助。定位随之扩展。

**四个维度的陪伴语义**（不是因为"决策有用"才要，而是在意一个人才需要知道）：
- 财务/健康明细：不做量化模型，做"知道你最近扛着什么"——事件承载 + 压力/状态感知（配合情绪维度）。
- 地点：情感坐标（对用户有意义的场所），不是地理数据。
- 身份/角色：陪伴的"写作指南"——系统用哪种视角说话，用户才觉得被理解（父亲 / 副业者 / 创作者…）。
- 内容/创作主题线：你在创造什么、系列进展如何——陪伴关心用户的产出（含视频二创方向）。

**陪伴额外要求**：
- **情绪维度**（核心新增，贯穿主线）：近期的情绪状态、对特定人/事的感受、情绪转折点；各维度通过"情绪"连线——对谁、对什么事、在哪里、情绪如何。
- **被记得 / 共同历史**：系统主动回引共同记忆（"你上周说过…"），不只被问才出现；可挂进每日回顾路径。
- **适时主动**：低打扰地出现（情感性回访），沿用分级防打扰原则；主动不是骚扰。

**红线再解读**（边界不变、范围扩展）：
- 红线 1 / 2（只整理已托付、透明可看可改可删）不变，反而更重要——承载情绪是最深层的信任，不透明的陪伴是伪陪伴。
- 红线 3 校准：维度可以多，但每个维度独立维护、对用户可见；系统仍**不得外推/猜测超出用户托付的内容**；**陪伴 ≠ 窥探，情绪承载 ≠ 情绪分析报告**——以用户感受为优先，不以模型完备性为目标。

**理解用户的维度全集**：人物/关系、项目/事情（基础）· 目标、决策与复盘、在途承诺与等待、节奏与周期、偏好与红线（决策辅助）· 健康与状态、财务与压力、地点（情感坐标）、身份/角色、内容/创作主题线（陪伴）· 情绪状态与趋势（贯穿主线）。

**一句话定位（修订）**：Elsewhen 是一个越用越懂你、既能帮你做决定、也能接住你情绪的私人陪伴——它不打听你的生活，只整理你自愿喂给它的记录；它记住你在乎的人和事、你扛着的压力和你正在创造的东西，不是为了研究你，而是为了在你做决定、做事、或只是需要被记得的那一刻，把你的过去叫回来陪你。它对你的了解是一本你可以随时翻开、修改、撕掉的账，而不是一份你看不见的档案。
