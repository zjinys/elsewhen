# Agent Note: LLM Wiki 完整闭环的实施边界

Status: proposed

## Problem

现有 LLM Wiki v1 能手动消化事件、维护知识页、生成洞察和在对话中按需搜索，但可靠触发、统一来源和知识使用的可解释性尚未闭合。直接照旧版来源层路线图实施，会重复现有 URL/文本导入，并忽略后来形成的有界项目盘点及知识搜索工具。

## Proposal

按[产品需求](../../../requirements/product/FR-PES-004-LLM-Wiki知识库闭环.md)与[技术设计](../../../requirements/architecture/FR-PES-ARCH-002-LLM-Wiki知识库闭环技术设计.md)依次实施：可靠事件消化、兼容迁移来源、共享选材、维护审阅。SQLite 仍是真源；现有 `source` 页、搜索工具、四透镜和人工编辑保护均作为演进起点。事件任务以稳定 ID 和成功账本确认，不以时间游标代表已经处理；知识引用必须指回具体事件或材料及其版本。

## Alternatives considered

- 继续靠用户手动执行 `wiki digest`：不需改队列，但知识积累取决于用户记得运行命令，无法成为日常闭环。
- 在每次事件记录时同步调用模型：看似即时，却使原始事件保存依赖网络和 Provider，不符合当前异步分析边界。
- 直接执行旧 `sources` 文档的全套新表和 CLI：会与已落地的 `source` 页和导入流程形成双份来源，也没有解决先前事件遗漏问题。
- 让模型自行挑选所有材料或先引入向量数据库：缺少可解释的适用性与预算边界；现阶段可先利用已有搜索和结构化条件验证质量。

## Acceptance criteria

- 四阶段的独立验收场景和迁移/回滚约束在需求与设计中明确，文档不将规划中的能力标为已实现。
- 实施后，迟到事件和重试不漏不重，人工修订不被静默覆盖，外部材料不被误认作用户事实，回答能定位实际来源。

## Risks

现有 digest 按有限时间窗和时间游标过滤，直接切换进度语义可能漏掉历史事件；必须明确存量回填策略。跨页面原子批次需要调整现有存储 API，若先采用幂等补偿，应如实暴露中间状态。来源实体迁移须避免旧 URL 页重复；多消费端接入可能推高上下文开销，须以预算与不引用的测试约束。
