# Agent Note: 以个人认知主循环重组 Elsewhen

Status: proposed

## Problem

Elsewhen 的根本目标包含三件事：持续记录每天做过和想过的事；从记录中理解正在推进的事情并沉淀项目、人物与长期认识；保存外部内容并把它加工成未来可使用的素材。

当前系统已经具备事件、对话、Wiki、人物关系、待办、外部内容导入和 AI 工具等能力，但这些能力尚未组成单一、清晰的使用闭环：

- Flutter 主界面的对话消息与 Capture 写入的事件属于两套事实入口，用户需要预先判断内容应该“聊天”还是“记录”；
- 事件入库会创建分析任务，但 Flutter 的分析触发仍为空实现，记录后理解不是稳定的主流程；
- 人物、项目、个人洞察、外部原文和 AI 派生产物都以 Wiki 页面呈现，虽然可以用 `kind`、`area` 区分，但生命周期和用户意图不同；
- 侧栏以“对话 / 知识库 / 待办”组织已有功能，却没有直接回答“我今天做了什么、想了什么、接下来要做什么”。

如果继续围绕局部功能扩展，系统会成为能力丰富但日常使用理由不明确的工具集合。

## Proposal

产品围绕“记录 → 理解 → 沉淀 / 加工 → 回顾与行动”的个人认知主循环重组：

```text
个人输入 ──→ 今日记录 ──→ 人物 / 项目 / 主题 / 长期认识
                     └──→ 待办 / 澄清 / 每日回顾

外部内容 ──→ 来源材料 ──→ 摘要 / 观点 / 灵感 / 创作成品
```

### 统一输入，保留不同语义

用户必须可以从一个主要入口输入自然语言、网址或行动请求，不需要先选择数据库类型。系统先可靠保存原始输入，再异步分类和加工。

统一输入不意味着把所有记录强行存成同一种对象：

- `events` 继续作为不可变的个人事实记录；
- `messages` 继续保留对话上下文和 AI 回复；
- 外部原文继续作为来源材料；
- 输入路由必须显式记录“一次用户输入产生了哪些对象”，使事件、消息、来源、待办和知识页面之间可以溯源。

用户在普通对话中陈述自己的经历、想法或决定时，系统应当能够草拟为事件，并在低风险规则明确时自动记录；模糊或可能改变语义的情况需要用户确认。Capture 仍保持最快、离线可靠的直接事件入口。

### “今天”成为最高频视图

一级导航以用户目标而不是存储模型组织，目标形态为：

- **今天**：按时间展示原始记录、重要对话输入、识别结果、跟进项和每日总结；
- **记忆**：人物、项目、主题及长期认识，以及它们随时间发生的变化；
- **素材**：外部原文及其阅读、加工和采用状态；
- **行动**：待办、澄清和需要继续跟进的事项。

对话是贯穿这些对象的操作方式，可以从今天、记忆或素材上下文中发起，而不是与其他信息并列成为唯一主入口。

### 记忆渐进形成

知识沉淀分为三个层次：

1. **原始记录**：用户实际输入，永不被 AI 覆盖；
2. **实体与带时间的事实**：人物、项目、关系、状态变化和对应证据；
3. **长期记忆**：从多条事实中累积出的认识、模式、约束和洞察。

AI 可以提出实体、事实和长期记忆候选，但不得静默覆盖原始记录或未经确定性校验直接改变项目状态。每项沉淀必须可以回到来源记录。

### 素材采用加工流水线

外部内容与个人记忆在产品上分区，保留以下对象关系：

- 原文是不可被派生产物覆盖的来源；
- 摘要、观点、灵感、脚本和文案是带 `based_on` 关系的派生产物；
- 派生产物记录加工类型、版本和采用状态；
- 素材具有待读、已读、值得使用、已采用和归档等工作状态；
- 素材中的观点只有在联系到用户自己的记录或经用户认可后，才进入长期记忆。

### 先完成主循环，再扩展局部能力

实施顺序由 [个人认知主循环 Roadmap](../../../roadmap/2026-09-17-personal-cognition-main-loop-roadmap.md) 约束。标签、视觉和更多 AI 工具仍可演进，但不得替代统一记录、可靠分析、每日回顾和素材加工这些主干能力。

## Invariants

- 原始个人记录和外部原文必须可恢复、可追溯，AI 不得覆盖；
- 保存不等待网络，Provider 不可用不影响记录成功；
- 派生结果必须带来源和生成状态，允许重算；
- AI 不直接执行高影响写操作，继续使用草拟、确定性校验和必要时确认的边界；
- 一个概念只有一个权威事实源，视图可以聚合但不得复制出第二套状态；
- 数据迁移必须兼容现有事件、会话、Wiki、关系和待办数据。

## Alternatives considered

### 继续按“对话 / 知识库 / 待办”增加功能

这能最低成本复用当前界面，但会继续把存储模块暴露为产品结构，无法解决事件与消息分裂，也不能建立每天打开系统的明确入口。

### 所有输入和产物都统一成 Wiki 页面

统一渲染和搜索较简单，但原始事件、人物实体、外部文章和创作成品具有不同的不变性与生命周期。用标签模拟全部语义会使更新、溯源和状态规则越来越隐晦。

### 所有输入都统一成对话消息

交互自然，但聊天记录不适合作为不可变事实、项目状态或来源材料的唯一权威存储。模型回复与用户事实也会混在同一条时间线上。

### 先完善搜索、标签和视觉

这些能改善现有页面，但不能修复核心信息流断点。它们应服务于主循环，而不是决定产品模型。

## Acceptance criteria

- 用户通过主要输入入口记录经历、想法或网址时，无需预先选择“事件 / 对话 / Wiki”；
- 任意个人记录都能在“今天”视图找到，并看到分析状态、来源和产生的实体、事实或待办；
- Flutter 中事件分析可实际执行，失败可见、可重试且不影响原始记录；
- 人物和项目页面能够展示按时间排列的来源事实与状态变化，而非只有静态 Markdown；
- 每日总结由当天事实动态生成，可追溯、可修正、可重算；
- 外部原文与摘要、观点、灵感及创作成品明确分离，并能追踪加工和采用状态；
- 现有事件、消息、Wiki、关系和待办数据在迁移后仍可读取且不会丢失溯源。

## Risks

- 统一输入如果依赖模型做同步分类，会损害记录速度和离线可靠性；因此必须先保存再异步路由。
- 自动把对话陈述转为事件可能制造噪声或重复记录，需要幂等键、置信度和清晰的确认边界。
- “今天”聚合多个对象后容易成为复杂 Dashboard，第一版应只呈现时间流、分析状态、跟进项和日结。
- 对现有 Wiki 数据重新分区可能破坏 slug、关系和页内会话引用，迁移必须采用增量字段和兼容读取。
- 每日总结如果被当成新的事实源，会与原始记录冲突；它只能是可重算的派生视图。
