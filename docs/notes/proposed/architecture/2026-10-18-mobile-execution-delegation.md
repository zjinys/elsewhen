# 移动端执行委托（云端/本地执行选择提案）

**提出**: 2026-10-18
**状态**: **Deferred（搁置，2026-10-18 评估后决定）**——非路线图项，无排期
**关联**: [FR-PES-006 外部工具与技能执行](../../requirements/product/FR-PES-006-外部工具与技能执行.md)、[FR-PES-ARCH-003](../../requirements/architecture/FR-PES-ARCH-003-外部工具执行与信任模型技术设计.md)

## 1. 想法

移动端运行时，工具执行可以二选一：

- **本地**：完全在本机跑。远程 MCP（streamable-http）可以直接连；stdio 与技能脚本不可用（诚实降级）。
- **云端**：把执行委托给一台**同步组里的桌面节点**代跑。手机发起、桌面执行、结果经同步管道回流。

价值：手机上获得桌面的全部执行能力（stdio server、技能脚本、本机文件），而不需要在手机上复刻桌面环境。

## 2. 与平台标签方案的关系（前置已就绪）

迁移 48 的平台标签是本提案的前置：工具的适用平台有了显式元数据，「哪台桌面节点能跑哪个工具」才可判定。委托调度本质上是一次**按 platform 过滤的宿主选择**。

## 3. 设计骨架（供后续细化）

- **委托请求 = 参数封存的执行单**：手机端审批通过后，生成与本地 pending-action 同构的执行单（args 封存），经同步管道发给选定桌面节点。桌面只是跑腿，不再二次审批——用户意图已在手机端表达。
- **宿主声明**：桌面端设置「允许作为执行宿主」开关（默认关），声明后广播能力（在线状态、platform、可用 server/技能清单）。
- **回合模型**：对话轮在手机本地推进；工具结果未回时该轮显式挂起「等待云端执行」，结果以同步 op 回流后续跑。桌面离线 = 显式失败（可重试），不静默超时慢慢等。
- **审计双向**：手机端记「发起委托」，桌面端记「代理执行」（沿用 mcp/skills 的 .audit.log 模型）。
- **信任边界不变**：免审批与否仍由手机端 server/技能的 trusted 决定；桌面宿主开关是运维授权（允许跑腿），不是信任授权。

## 4. 非目标（首批）

- 不做多宿主负载均衡/故障切换（用户手动选节点）。
- 不做桌面端 second-guess 审批（那是双头审批，会把信任语义搅浑）。
- 不做桌面反向委托手机执行。

## 5. 若重新启动：实施顺序建议

### 5.1 优先评估：fire-and-forget 轻量形态

手机发起单向执行单（不等待结果回流），桌面收到即执行，结果留在桌面（或
走已有事件流）。单向 op、无挂起回合、协议增量极小——完整版的三个硬伤
（回合挂起延迟、桌面必须在线、状态机复杂度）回避了两个。

### 5.2 完整形态（仅当 5.1 被证明不够）

1. 同步管道新增 ExecutionRequest / ExecutionResult mutation（协议演进，两端同版本）。
2. 宿主声明与能力广播（挂在成员状态或独立心跳）。
3. 手机端执行选择 UI（本地/云端/仅本地）与挂起回合渲染。
4. 端到端演练：手机发起 stdio 调用 → 桌面执行 → 结果回流进对话。
