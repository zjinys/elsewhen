# Agent Note: 事件可记录性过滤（剔除"对话/闲聊/元对话"误记）

Status: proposed

## Problem

用户反馈的真实场景（对话式记录）：

```
我(1): 这2天把之前买的一些板卡，比如stm32的，rk的都卖了
ai(1): ……这不叫清闲置，这是在关掉硬件这条业务线。……纠正后的背景我补记进事件了：卖板卡是收缩硬件业务的一部分。
我(2): 你这么回答情绪价值不够啊，难道不认为卖掉是要关掉一部分业务的原因吗
ai(2): （与 ai(1) 逐字复读）
```

用户对第二条发言的定性是：**这只是对 AI 回复质量的抱怨，不是需要记录的事件**。但当前行为把它当新内容处理并再次"补记"。拆开看有三个问题：

1. `record_event` 是 `ToolPolicy::WriteDirect`（调用即写入 events 真源，无确认；见 `src/ai/tool/mod.rs`），工具描述只有"把一段经历/事件直接记录"，没有「这值不值得记」的判断标准 → 助手把"对回复的评价"误判为事件。
2. `event-analysis-v1` 契约（`src/api.rs` `EventAnalysisV1`、`process_analysis_queue` 的 prompt）只有自由字符串 `event_type`，没有「可记录性 / 内容类别」维度，分析层无法表达"这条不是事件"。
3. 助手把**自己的解读**（"卖板卡是收缩硬件业务的一部分"）作为新事件原文写入，而非只进 `analysis.summary`——事件真源本应保存用户原话（raw），解读属于派生数据。这直接导致同一信息被复读式重复入库。

补充事实：`conversations` 表已有 `tag CHECK IN ('diary','idea','discussion','general')`（`src/storage.rs`）——"讨论/闲聊"这个桶是现成的，只是从未与事件写入挂钩。

## Proposal

核心：**"可记录性"判断做两层，分别在写入 events 真源之前（对话层）与分析之后（分析层兜底）；"剔除"不等于删除——讨论/闲聊留在 conversations（tag=discussion），只从事件时间线撤出。**

### 1. 内容分两类、进两个桶

- 事件（记）：客观事实、决策、动作、进展——第一人称、可回看的真事 → `events` 真源，占事件时间线。
- 讨论/闲聊/元对话（不记）：对助手回复的评价（"情绪价值不够"）、寒暄、问句、纯情绪表达 → 只留在当前 conversation，打 `tag=discussion`，不触发事件分析。

判断默认值：**判不准时默认"不记"**。个人日记账本里混入闲聊的伤害 > 漏记一条真事的伤害；用户明确说"记一下 / 帮我记 / 存进事件"这类显式意图时放松标准照记。边界案例靠 `confidence` 天然承载。

### 2. 第一层：写入前判断（对话层，治本）

- 在 system prompt（`src/ai/memory.rs`）与 `record_event` 工具描述里加入可记录性判定规则 + few-shot 正反例（用上文真实场景）：
  - 反例："你这么回答情绪价值不够啊"（对回复的评价）→ 不调用 `record_event`，回复正常处理即可。
  - 正例："这2天把之前买的stm32/rk板卡卖了"（陈述客观经历）→ 调用。
- 规则要点：陈述客观经历才算事件；"评价助手 / 聊天过程本身 / 提问"默认不记。

### 3. 第二层：分析后判断（分析层，兜底）

- 契约 `event-analysis-v1 → v2`，**只加字段不破旧**：新增 `recordable: bool` 与 `kind: "event" | "discussion" | "chitchat" | "meta"`；保留 v1 全部字段与解析，旧数据可读。
- 分析 prompt 增加分类指令（同样带反例）；`recordable=false` 时 `kind=discussion/meta`，`summary` 留简短标签即可。
- 作用：第一层漏判/误记入库后，分析阶段仍能标记非事件，UI 时间线据此过滤，从展示上"剔除"。

### 4. 明确"记录什么"（消灭复读式重复入库）

- 事件保持用户原话（raw）；助手的解读只进 `analysis.summary`，不许另起新事件。
- 助手"已记：……"的声明每轮只输出一次，不随后续对话复读。

### 5. 存量处理

- 事件回看界面提供两个操作：
  - **「转为讨论」**：从 events 撤出（软删/移标签），归入原对话并打 `tag=discussion`，原始文本仍可检索。
  - **「重新分析」**：用 v2 prompt 对存量重跑，自动标出 `recordable=false` 的条目供批量清理。
- 复用现有分析队列的 retry / 重新排队机制，无新基建。

## Alternatives considered

1. 只改 prompt 不加契约：实现最快，但分析结果里没有结构化的可记录性维度，UI 无法过滤、存量无法批量重分类——只做半套。
2. 事件一律改为"提议→确认"制：彻底杜绝误记，但破坏"随手记录"的即时闭环，违背产品定位；可作为设置项"严格模式"保留。
3. 直接把这类内容丢弃：对话历史也是可回看资料，物理删除不可取；conversations + tag=discussion 已是现成的收纳桶。

## Consequences

收益：事件时间线只含真实事件；助理解读不再污染 raw 真源；讨论/闲聊可检索但不占账本；存量可一键清理。

代价：需要契约 v2 升级（api.rs 校验、storage analysis 落库、Flutter 渲染过滤）、prompt 与工具描述改动、以及面向用户的两处新操作。落地顺序按性价比：先纯 prompt（几乎零代码）→ 再契约 v2 + UI 过滤 → 最后存量批量重分析。分类依赖模型，边界案例需接受默认"不记"带来的少量漏记。
