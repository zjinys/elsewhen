# Agent Note: 工作项作为知识库一等页面

Status: proposed

## Problem

当前待办以独立记录为主，再通过 `related_wiki_slug` 关联知识页。这样会让待办的讨论、决策和思考过程停留在附属页面，待办本身仍然是孤立对象；点击待办进入弹窗也无法形成持续的知识沉淀。

## Proposal

将工作项/待办建模为知识库中的一种页面类型。页面统一承载标题、状态、优先级、截止日期、说明、讨论、决策、思考过程和完成历史。现有 `todos` 数据可在迁移期间保留为兼容投影，但不再作为最终业务模型。

左侧不再把“对话、知识库、待办”作为三个并列主入口；主界面以对话为中心，通过搜索、快捷入口和最近访问页面进入知识库页面与工作项。

## Alternatives considered

- 继续使用独立待办并按需创建关联知识页：改动较小，但继续保留两个对象和双向同步问题。
- 只把待办内容写入 Markdown 标签：可快速落地，但状态、日期和迁移规则不够明确，难以支撑可靠查询与更新。
- 将待办永久保留为独立模块：与“所有工作项都可聊天、讨论并记录决策”的目标冲突。

## Acceptance criteria

- 新建工作项可以直接进入一个可持续讨论的知识库页面。
- 状态、优先级、截止日期和完成操作不会丢失页面、聊天或历史。
- 历史待办能够安全迁移或兼容读取，且不会重复创建页面。
- 用户不需要通过待办弹窗才能查看或讨论工作项。

## Risks

- 现有 `todos` 表和页面数据可能在迁移期间短暂并存，需要明确唯一来源和同步边界。
- 移除并列导航前需要确认搜索、最近页面和页面详情入口足够可发现。
- AI 创建待办、人工编辑和历史迁移必须共用幂等规则。
