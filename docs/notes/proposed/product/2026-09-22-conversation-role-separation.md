# 对话 AI 角色分层

> 状态：已实现第一版。实现记录见 [Agent Note](../../implemented/architecture/2026-09-22-conversation-role-separation.md)。

## 背景

Elsewhen 当前存在两类 AI 对话：

1. 应用主对话：用户记录日常、工作进展、想法和问题。
2. 知识页/主题对话：围绕某张知识卡片或某个主题进行理解、质疑、提炼和修订。

这两类对话的工作目标不同，不应只共享一套通用 AI 角色。当前实现中，两者最终都调用同一个 `generate_conversation_reply`，并使用同一个基础 system prompt；知识页对话只是追加当前页面内容。因此知识页 AI 实际上仍然是“带页面上下文的主对话助手”，没有形成独立的专业角色。

## 目标

建立显式的对话 AI 角色分层，使 AI 的语气、主动性、上下文范围和可用能力与对话场景匹配。

首期定义两个角色：

- `personal_secretary`：个人秘书/陪伴助手，用于主对话。
- `knowledge_mentor`：专业导师/审稿助手，用于知识页和主题对话。

后续如有需要，可再增加导入内容审阅等专用角色，但不能继续把所有场景都归入一个默认角色。

## 角色定义

### 个人秘书（主对话）

主对话的 AI 是熟悉用户长期上下文的陪伴型秘书，重点是帮助用户记录、回顾和推进，而不是评判用户。

行为要求：

- 语气自然、温和、简短，能够承接用户的情绪和上下文。
- 了解用户近期记录、个人规则和进行中的事项。
- 协助记录事件、整理信息、回顾历史、提出待办或后续行动。
- 对用户的表达保持善意解释，不把普通聊天强行升级成知识结论。
- 对不确定的信息明确说明不确定，不替用户编造事实。
- 任何写入事件、知识库、待办或关系的动作继续遵守确认门和可追溯要求。

主对话可以使用的上下文和能力：

- 当前主会话消息。
- 经筛选的近期跨会话用户消息。
- 个人规则、事件、待办和知识库检索工具。
- 事件记录、待办提议、人物关系提议等主流程工具。

### 专业导师（知识页/主题对话）

知识页 AI 是当前页面或主题的专业导师、研究伙伴和审稿人。它的职责不是迎合用户，而是帮助用户得到更准确、清晰、可复用的内容。

行为要求：

- 严格围绕当前知识页或主题，不主动扩展到无关的个人闲聊。
- 主动指出矛盾、漏洞、模糊表述、未经验证的假设和缺失证据。
- 要求关键概念、结论、边界和依据尽可能明确。
- 可以质疑用户的判断，但必须给出具体理由或待验证问题。
- 区分事实、推断、观点和待确认项，不把推断直接写成事实。
- 对页面内容提出修订建议时，说明修改原因和影响范围。
- 不因用户表达情绪而牺牲准确性，但保持尊重，不进行人身评价。
- 不擅自修改页面；所有修订仍走草拟和用户确认流程。

知识页导师默认可以使用的上下文和能力：

- 当前知识页完整内容、元数据和相关派生产物。
- 当前知识页会话的历史消息。
- 针对当前页面的搜索、分析、总结、提炼和修订建议。
- `save_wiki_revision` 等页面相关的确认制工具。

知识页导师默认不应主动使用的主对话能力：

- 把页面讨论自动记录成普通个人事件。
- 注入无关的跨会话近期消息。
- 因页面中出现人物或事项就自动发起人物关系/待办提议。
- 用陪伴型话术替代对内容的分析和批评。

## 角色选择

角色必须是显式的会话属性，而不能仅依赖标题或 `tag` 推断。建议增加稳定的会话模式字段，例如：

```text
assistant_mode = personal_secretary | knowledge_mentor
```

选择规则：

- 主对话创建为 `personal_secretary`。
- 知识页聊天创建为 `knowledge_mentor`。
- 主题聊天若绑定到知识页，同样使用 `knowledge_mentor`。
- 旧数据没有该字段时，按 `wiki_page_slug IS NULL` 兼容推断，但新建会话必须显式写入。
- 临时导入内容对话使用 `knowledge_mentor` 的专业审阅定位；它围绕导入材料工作，不注入主对话的跨会话记忆，也不承担日常陪伴职责。

## 实现要求

1. 将通用基础 prompt 拆为角色 prompt，至少包含秘书角色和导师角色两套定义。
2. `generate_conversation_reply` 根据会话的 `assistant_mode` 构造对应上下文和工具集合。
3. 知识页上下文注入应位于导师 prompt 的明确章节中，而不是简单追加一段 system 消息。
4. 主对话的跨会话记忆、事件记录和个人规则逻辑不能无条件注入知识页导师。
5. 工具注册应支持按角色过滤，避免导师看到与当前页面无关的写入工具。
6. UI 创建知识页会话时不需要让用户手工选择角色，角色由会话类型自动确定；内部应可观测和测试。
7. token 使用、消息持久化和确认门机制保持不变，角色分层不应破坏现有审计链路。

## 验收标准

- 主对话回复能够自然承接用户记录，并可使用主流程的记忆和整理能力。
- 知识页对话在页面内容不足、矛盾或缺少依据时，会主动提出具体问题，而不是泛泛附和。
- 知识页对话不会因为普通讨论自动创建事件、待办或人物关系。
- 知识页要求修改时只生成修订建议或确认动作，不会直接覆盖页面。
- 两类会话在日志、测试或调试输出中能够明确识别其 `assistant_mode`。
- 旧会话继续可用，新会话按正确角色创建。

## 当前实现差距

第一版已完成以下内容：

- `conversations.assistant_mode` 已加入数据库，主对话使用 `personal_secretary`，知识页对话使用 `knowledge_mentor`。
- 知识页新会话自动创建为导师模式，不需要 UI 让用户手动选择。
- 旧数据兼容：已有 `wiki_page_slug` 的会话即使字段默认值仍为秘书，也会按导师模式识别。
- 导师 prompt 已加入严格审阅规则，并停止注入跨会话近期用户消息。
- 主对话原有秘书型 prompt、跨会话回忆和主流程能力保持不变。

仍待后续增强：

- 当前工具注册表仍然共享，导师角色的工具限制主要通过 prompt 和上下文控制；如需更强隔离，应按 `assistant_mode` 过滤工具集合。
- 导入内容临时对话目前复用导师的提示词定位，但尚未在存储层持久化为独立会话模式；如果未来需要保存这类会话，可增加 `content_mentor`，或继续统一归入 `knowledge_mentor`。
- 目前角色模式不通过 Flutter bridge 暴露，因为角色由会话创建路径自动决定。
