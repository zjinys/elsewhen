# Scout 方向调整：从「预设监测」到「发现 → 周报 → 按需下钻」

- 日期：2026-11-17
- 状态：direction discussion（方向讨论，未批准为实施路线）
- 2026-11-20 部分落地：用户要求修复仍在运行的语言预设与必填 CWS ID。GitHub 合并为不限语言的近 90 天新项目；CWS 改公开发现页自动采集，额外跟踪清单可选且无代码内置 ID。实现与验证见[商机研究工作区](../../implemented/feature/2026-11-17-scout-opportunity-workspace.md)。Gumroad 分类设置、周报和创作者研究仍属后续方向。
- 关联：[商机研究路线 O0–O7](../../roadmap/2026-11-17-scout-opportunity-research-roadmap.md)、[翻译提案](../architecture/2026-11-17-on-demand-translation.md)（其情报侧优先级被本文下调）、Glasser 评估（无独立文档，结论收录本文 §6）
- 触发：用户反馈「数据源单薄，但不想做复杂，且现有数据和功能不足以支撑模块」。经追问确认：每天会打开情报页；要的是「哪个赛道要起来了、哪些没意义」的决策支持；对博主/产品研究有兴趣但自知难。

## Problem

现有 7 源的 994 条 finding 暴露三层结构性问题：

1. **采集端被代码预设绑死**。Gumroad 关键词、CWS 扩展清单写死在 `sources.ts`，GitHub 被限定 `language:dart/rust`。这等于系统替用户预设了赛道——与「帮用户发现赛道」的产品目标矛盾。改预设要动代码重新部署，用户无法自己调方向。
2. **GitHub 现有查询是错的发现形态**。`stars:>100 sort:stars` 返回史前巨兽，排名几乎不动，本来就产不出 finding。发现型信号应该是「90 天内出生、攒到 50 星的新仓库」。
3. **缺综合层**。用户要「赛道升温/降温」的判断，现在只有逐条 diff 的原料流。65% 的 finding 是雷达型（不与用户相关），但没有聚合层时它们只是噪声。

另外两个被推翻的中间方案，记下来防止回潮：

- **「先让用户报赛道关键词再瞄准」**被用户否定：找赛道本身就是产品价值，不能推回给用户。
- **「从现有 payload 归并 seller 建人物索引」**被否定：Gumroad seller 多为一次性匿名开店，归并无信息量。用户想要的「人」是 TikTok/小红书/YouTube 上的**创作者**——内容驱动、正在涨粉的人。

## Proposal

四条方向调整：

### 1. 采集端去预设化（设置驱动）

- Gumroad 从两个写死关键词改为**分类清单**（类目用站点自己的体系，不是我们发明），每分类一个稳定 id 源（`gumroad:{category_slug}`），baseline 独立；可选关键词参数默认空（整类）。
- CWS extensionIds 搬进设置。
- 落点：D1 `scout_source_settings` + `/admin` 编辑区。「泛而不当」的收缩交给周报层，不在采集端硬猜。
- 这同时是 E1（多用户）的前置：将来按 token 分行即可。

### 2. GitHub 发现化

`created:>（滚动90天） stars:>50 sort:stars`，全语言，两源合一。语义：近期诞生的、已被市场初步验证的新仓库。触发 `specHash` bump（纪律）+ baseline 一次性重置（预期内）。

### 3. 周报综合层（AI 的正当场景）

- 每周把本周 findings + delta 按确定性分桶喂给本地 provider（复用既有 digest 管线与频控纪律：每周首开触发，不新增调度器）。
- 分桶是确定性的，用已采字段：GitHub `topics`、App Store `genres_0_name`、Gumroad 分类即桶、PH 标题词。
- 输出固定三档：**升温 / 降温 / 无变化** + 理由 + 证据回链到具体 finding。**模型只归纳不发明**：链不回 finding 的观点不写。
- 产出落知识页（derivative），可跨周对比。
- 周报直接产中文——情报逐条翻译降级为按需动作（读到某条想细看才翻），翻译提案的情报侧优先级相应下调。

### 4. 人物层 = 社媒创作者，按需研究而非监测

- **范围：出海平台**（用户已确认）：TikTok、YouTube、X。小红书暂缓（登录墙+反爬，连付费 API 都不可靠）。
- **发现（谁在冒头）→ 按需研究**：周报给出升温桶后，用户点名某桶，agent 用付费数据（Glasser 聚合的 ScrapeCreators/TikHub，TikTok ~$0.002/次）搜该品类创作者，产出带涨粉数据的名单落知识页。第一期不写代码——直接在对话里做，跑两三次看质量。
- **监测（盯已发现的少数人）→ 研究的输出**：名单里值得盯的 3–5 人进 watchlist（与 CWS watchlist 同构）；YouTube 创作者可走免费 RSS/官方 API 进现有轮询，TikTok/X 按次付费（5 人 × 日一次 ≈ $0.3/月）。**先有名单才有监测，顺序不能反。**
- 平台可行性备忘：YouTube 唯一可免费监测；TikTok/X 只能付费按次；小红书最不可靠。

## 与 O0–O7 路线的关系

不推翻 O0 的工程缺口（续传游标、原子基线、证据契约仍然成立），但**优先级被本讨论改写**：

- 本讨论给出一条轻路径：分桶 → 周报 → 按需下钻，全部不依赖 O1–O3 的重工程（产品归并、观察模型、研究闭环）。轻路径先验证「周报判断是否可用」，再决定 O1–O3 投入。
- O0.1 的「预设商业源样本」表述与去预设化冲突，实施时按本文修订。
- O3 的「发现工作区」与周报层是互补关系：周报是每周一次的蒸馏视图，O3 是逐条阅读的工作区，不合并。

## 明确不做

- **不做**从现有 payload 归并 seller/artistName/developer 的人物索引（无信号价值）。
- **不做**小红书采集或研究通道（连付费 API 都不可靠）。
- **不做**社媒创作者的自动监测（无名单前轮询全网 = 花钱扫描）。
- **不做**博主/产品推荐系统（等周报验证 + watchlist 攒出真实对象后再说）。
- **不做**自动买量/发布/联系客户（沿用 O 路线边界）。

## Alternatives considered

- **保持 O0–O7 原顺序**（先修续传/原子基线再做产品模型）：工程正确但价值后置——修完 O0–O3 用户仍看不到「哪个赛道在升温」。否。
- **直接接 Glasser 做数据源**：采集端按次付费与高频轮询语义冲突，且现有免费源已覆盖同批数据。否；Glasser 定位见下。
- **周报用确定性规则（不加 AI）**：「升温」涉及跨源语义比较（stars 涨 + 榜位跌 + 新竞品涌入），规则版会退化成阈值告警列表，回答不了「赛道」。AI 归纳 + 证据回链是唯一能同时满足可验证与可读的方案。

## Glasser 评估结论（收录）

- 对 scout **采集端无用**：现有源全免费，按次付费是倒退，且按次计费与「挂掉重试下轮再来」的轮询语义冲突。
- 对 **O4/下钻研究有用**：App 评价正文（ScrapeCreators ~$0.002）、公司事件（PredictLeads $0.04/次 vs 直订 $40/月）、Similarweb/BuiltWith/Trustpilot/Keepa，按次计费匹配低频 drill-down。
- 三个警惕：PredictLeads `discover/*` 端点单次上限 $40（agent 自主调用必须设硬预算或逐次确认）；scraped 数据只当线索不当证据；接入形态是 agent 按需调用，不进 scout-cf、不进轮询、不进 `fields`。

## Acceptance criteria

方向讨论无验收。批准后的轻路径首批验收预设为：

1. 源设置化上线，/admin 可改 Gumroad 分类与 CWS 清单，无需改代码部署。
2. GitHub 发现化查询上线，baseline 重置后一周内产生新 finding（证明新形态有效）。
3. 分桶覆盖率：≥80% 的 finding 能落进至少一个桶（确定性映射）。
4. 首份周报产出，每条判断可链回 finding；连续 4 周人工评估「升温/降温」判断是否可信，记录命中率与误判原因。

## Risks

- **周报判断质量未知**：模型归纳可能给出听起来合理但无增量信息的总结。缓解：证据回链硬校验 + 4 周人工评估期，不可信则停，不追加投入。
- **分桶字段稀疏**：PH 只有标题词、Gumroad 分类是站点体系，桶间口径不一。缓解：首版允许「未分桶」，不做强行归一。
- **付费研究通道依赖 Glasser 转售稳定性**：端点可能涨价或失效。缓解：第一期在对话里手动跑，不写代码不建依赖。
- **设置化改造是四项里唯一的工程重头**（源定义从代码常量变设置驱动），若周报验证失败此项投入沉没。缓解：顺序上先做零工程的分桶+周报，验证后再动服务端。

## 待定

- 周报落点：情报页顶部卡片 vs digest 式消息流。
- 周报频率已倾向「每周首开触发 + 复用每日一卡频控纪律」，待确认。
- 轻路径与 O0.2/O0.3（续传/原子基线）谁先：若周报跑在现网上遇到漏数/假基线，则 O0 优先级回升。
