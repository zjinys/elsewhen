# 单流对话 + 议题页：对话信息架构收口设计

Status: proposed（2026-09-20 与用户讨论收敛）

## 背景

所有 GUI 聊天工具都维护一个"对话列表"：每个会话被命名、排序、归档，成为需要长期管理的对象。但用户的实际记忆索引是日期、原话关键字、人物/项目、未完成的议题——不是"会话标题"。自动命名只优化了观感，没有解决"不会回去看 / 找不到"两个病根。

Elsewhen 与这些工具有一个根本差别：AI 掌握全部记忆（事件流 + 分析 + 人物/项目 + 待办 + 知识页），对话不是上下文唯一的持有人。因此可以做出它们不敢做的设计：**让对话成为消耗品，记忆由结构承载。**

核心判断：聊天是"过程"，事件/实体/待办/议题页是"产物"。界面不应把过程当成要长期维护的对象。

## 决策（已收敛）

### D1：对话 tab = 一条永不结束的主对话

对话 tab 不再有列表、新建、改名、归档。只有一条持续流动的主对话窗口，它本身就是个人的日志流。用户在其中的每一条提交已经（Phase 1 统一输入）落成不可变事件 + 分析任务。

存储形态：表面一条流，内部按天分章（可复用 `list_daily_entries` 的日边界逻辑），界面渲染为连续时间线 + 日期分隔条。跳到过去某天 = 时间线锚点 + "回到现在"悬浮按钮。

### D2：定位 = 日期 / 关键字，不翻列表

- 按日期跳：时间线锚点。
- 按关键字跳：**只搜索用户提交的原话**（定位器而非内容索引），命中后展示该句之后的整段往来，并顺带显示该条事件的分析（人物/项目/待办）。候选兜底：用户词无命中时全文搜（含 AI 回复）。
- 移除：对话列表、自动标题、改名、归档、已归档视图、新建对话按钮。

### D3：议题 = topic 知识页，讨论即沉淀

- 用户在聊天中说"我们来讨论一下 XXX"：AI 识别意图 → `find_wiki_page_by_title` 查重：
  - 无 → 新建 kind=topic 议题页，锚定该讨论；
  - 有 → 告知用户上次讨论时间，并把当前讨论接进该页。
- 议题页 = 知识页（标题/标签/关联事件/人物复用现有 wiki 机制）+ 页内聊天。
- **议题聊天不经过统一输入，不产生事件**（复用知识页内聊天机制：`wiki_page_slug` 会话 + 不写 input/event）。
- 议题的结论、想法、决定通过确认门（`save_wiki_revision`，草拟-确认-落库）写进页面内容——"过程"沉淀为"产物"。

### D4：双层上下文 + 沉淀回写

AI 上下文不再加载会话全文，而是组装两层：

| 语境 | 第一层（热消息） | 第二层（LLM wiki 沉淀） |
|---|---|---|
| 主对话流 | 最近 N 条交流 | 当天事件分析（摘要/人物/项目/待办）+ 最近日结 + 相关知识页 |
| 议题页聊天 | 该页最近 N 条讨论 | 议题页内容（标签/结论/想法）+ 关联事件与人物页 |

第二层已有的自动维护部件：`event-analysis-v1/v2`（事件→结构化）、`daily-review-v1`（日结）、知识页（确认后增长）。由此形成闭环：

> **沉淀回写（distill-back）**：议题讨论告一段落时 AI 提议把结论写进议题页，确认后落库；此后旧聊天消息从上下文退场，由页面内容接棒。主对话同理，日结即当天的沉淀回写。

### D5：议题入口与归拢

- **入口**：不进侧栏。知识库主区（右侧内容区）有大量闲置空间（当前导入 tab 占据右侧大部分但实际很轻），议题作为知识库显眼分区/顶部入口，与现有 area 分区（素材库/人物项目/知识沉淀）并列或独立成"议题"区。
- **归拢**：主对话后续再聊到已有议题时，AI 提示"这属于议题 X，接进议题页聊？"，确认后锚定过去并继续在页内聊。
- **形态**：议题页从现有的"知识页 + 底部 AI 处理小面板"演进为"聊天为主、内容为辅"的工作台布局（内容区 + 聊天区 + 沉淀入口），具体布局在 D3 落库后细化。

## 现状映射（大量现成部件）

- 主对话消息 → 事件 + 分析 + input record：Phase 1 已打通（`submit_conversation_input`）。
- 知识页内聊天不记事件：现成（`wiki_page_slug` 会话 + 排除出主列表 + 不走统一输入）。
- 议题意图识别：挂在 Phase 2.5 recordability 分类（event/discussion/chitchat）之上，同一判定动作的延伸。
- 议题查重：`find_wiki_page_by_title` 现成。
- 沉淀回写：`save_wiki_revision` 确认门现成。
- 日期/关键字定位：`list_daily_entries` + `get_daily_overview` + `SearchKnowledgeBase`/`ListEventsByDate` 工具现成。

## 退役的旧能力

- 对话 tab 的：列表、自动标题（首条消息 24 字）、改名对话框、归档/取消归档、已归档视图、"新建对话"按钮。
- 存储层 `conversations` 继续保留（主对话 = 一条持续会话；议题聊天 = 带 `wiki_page_slug` 的会话），但 UI 不再以列表呈现。

## 实施分步（挂 Roadmap 后细化）

1. **后端**：主对话锚定为"持续流"语义（按天分章的读写 API 或沿用现 API + 日边界视图）；确认"议题聊天不进事件"边界已有测试覆盖。
2. **议题页**：topic 页 + 页内聊天工作台化；"我们来讨论 X"意图 → 建/查议题 → 锚定（挂 recordability 分类）。
3. **主流 UI**：对话 tab 改为时间线条 + 日期分隔 + 关键字/日期定位 + "回到现在"；删除列表/改名/归档路径。
4. **归拢**：主对话识别"属于议题 X"并提示接续。
5. **双层上下文**：组装规则落地（每语境定义 hot N + 第二层查询），沉淀回写提议入口。
6. **入口**：知识库主区放议题分区；Today（Phase 3 UI）与主流的合流仍在 Today 上线时再定。

## 门禁与风险

- 保存路径不依赖 AI：议题聊天、主对话提交都不因沉淀失败而丢失。
- 议题聊天不进事件列表是铁律；沉淀必须走确认门，AI 不能直接改页面。
- 旧对话仍可读：存储不迁移重写，只改 UI 信息架构；Phase 6 的"旧对话/知识库入口降级评估"以此为终点之一。
- 上下文瘦身不丢信息：全文逐字记录仍存储，"溶解"的是上下文，不是数据。

## Alternatives considered

- 列表瘦身 + 入口转移（保留最近列表）：仍在维护"对话"对象，未解决根本错位。
- 对话锚定实体（人物/项目页聚合讨论）：实体外的散聊失去回看结构。
- 单一持续流但无议题对象：跨天专注与长推理链丢失，议题页才是承接处。
- 全部聊天进上下文：上下文爆炸，且违背"过程/产物"分离。

## Consequences

对话 tab 从"对象管理"变成"一条记录流 + 两个定位器"；议题从知识页中的普通 kind 升级为高频工作台。职责分离明确：**日常交流进事件日志，刻意讨论进议题页，两者都不需要被"收藏"**。代价是需要实现议题工作台 UI、主流时间线 UI、意图识别接线和双层上下文组装，不能用一个简单列表快速替代。
