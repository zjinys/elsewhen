# 习惯主动问候（按习惯定制问法与按钮）

- 日期：2026-10-22
- 状态：`implemented`（v1 已落地；多设备采用 A 方案：仅主设备写入问候）
- 范围：从已有 `kind='habit'` 知识页推断并确认定时问候；到点把一条真实的 assistant 问候写入主对话历史；打开应用即可看到并处理；v1 不依赖系统通知，也不在每次触发时调用 LLM
- 性质：新增**同步表**保存问候计划 + **设备本地表**保存触发/回答状态 + **`messages.kind/ref`** 标记问候消息；复用现有 5s tick 与主对话
- 已拍板（2026-10-22，用户）：**写入主对话历史**；**从习惯页自动推断时间/问法/按钮，但必须用户确认后才生效**；**不做系统通知，打开应用看到即可**；**按钮随具体习惯变化**（走步 →「走了/没走」，阅读 →「读了/没读」）；**多设备同步时只在主设备写入问候，其他设备只同步展示**
- 已知缺口（后续）：主设备离线时其他设备不接管（A 方案取舍）。确认卡依据展示、问候卡「聊聊」预填、全局限流（每日 2 条）、连续忽略建议卡已于 2026-10-23 补齐
- 关联：[定时提醒](../architecture/2026-10-19-timed-reminders.md)、[每日回顾工作台](2026-09-20-today-daily-review-workbench.md)、[知识页持续更新与关系网](../architecture/2026-10-19-knowledge-page-reconsolidation-and-relations.md)

## 1. 需求（用户原话归纳）

> 对于习惯这一块，能不能按照记录的习惯主动发起询问对话或者建议，比如在某个时间主动发一个对话，问你「今天中午走步了吗」。

拆成三件事：

1. **按习惯**：问候不是通用闹钟，而是引用知识库里已有的 `habit` 页（例如「午饭后散步」）；
2. **按时间**：从习惯页推断出「每天午饭后」这类线索，转成具体时间建议，由用户确认；
3. **主动开口**：到点由应用在主对话里真正发一条消息，而不是等用户先说话；回答后能沉淀为记录，供回顾和习惯页更新。
4. **按钮像这个习惯**：走步用「走了/没走」，阅读用「读了/没读」，喝水用「喝了/没喝」；不能所有习惯都只给「完成/未完成」。按钮和记录正文都应在创建时确认，而不是运行时让模型猜。

## 3. 产品原则（先定边界）

1. **显式确认，不以「AI 觉得你有这个习惯」为由自动打扰。** 习惯页可以推断出「每天午饭后」，但必须展示依据、时间和问法，由用户点「开启」才生效。
2. **触发确定性，措辞可预置。** 到点是否问、问哪一句，由已确认的本地计划决定；不在 12:30 临时调用模型。否则模型失败/超时就会变成「今天没问」。
3. **问候是真实的历史消息，但不是普通 AI 回复。** 用 `messages.kind='habit_nudge'` 标记：进历史、可同步、可回答；不参与普通回复的 typing/重试/重新生成，也不在没有用户输入时触发 chat run。
4. **回答要有落点。** 完成按钮（如「走了」）要生成一条普通事件；未完成按钮（如「没走」）只记回答状态，不制造负罪感时间线；不能只弹个窗就消失。
5. **不羞辱、不追责、不刷屏。** 同一习惯一天最多一次（用户点「晚点再问」可再问一次）；全局每天最多 2 次；夜间静默；连续忽略后降频或建议改时间，不自动改。
6. **不抢系统通知，打开应用可见。** 问候只在应用内主对话出现，不申请通知权限、不发系统 toast；应用没运行时不保证准点，当天再次打开补上，跨天不补（避免「昨天中午走步了吗」）。

## 4. 方案

### 4.1 创建：推断 → 确认

习惯页详情头部增加「定期问我」。点击后不直接保存，先展示一张确认卡：

```
我猜你想要：
  每天 12:30 问「今天中午走步了吗？」
  按钮：[走了] [没走]
  记录为：今天中午走步了
依据：习惯页正文「每天午饭后会出去走一圈」
[改时间] [改问法] [改按钮] [暂不开启] [开启]
```

- **推断来源**：只读当前 `kind='habit'` 页的标题/摘要/正文，不读记事本、不读其他页面。
- **时间推断**：先走确定性短语映射（「午饭后」→ 12:30、「睡前」→ 22:00、「早上」→ 08:00 等）；映射不了再让后台 AI 给出结构化建议，仍要用户确认。
- **按钮推断**：先走常见动词映射（走/散步 →「走了/没走」、读 →「读了/没读」、喝/水 →「喝了/没喝」、跑 →「跑了/没跑」、冥想/练 →「做了/没做」）；映射不了再让 AI 根据习惯页给 `done_label`/`missed_label`，并同时给出完整记录句 `done_text`/`missed_text`。
- **按钮约束**：`done_label`/`missed_label` 要短（建议 ≤4 个汉字，最多 6），否则 UI 用「完成了/还没」兜底并提示改短；`done_text`/`missed_text` 是完整句子，用于时间线回答和事件正文，例如按钮「走了」但记录为「今天中午走步了」。
- **结构化输出**：`question`、`local_time`、`weekdays`、`done_label`、`done_text`、`missed_label`、`missed_text`、`basis_excerpt`、`confidence`；任何一项不合法都回到手动表单，不静默采用。
- **默认值**：问法默认「今天<时间描述>了吗？」；重复默认每天；时间限制在 07:00–22:00，避免半夜问候；推断失败则给空白表单，不阻塞手动设置。
- **AI 调用失败**：显示手动表单，不弹错误后静默关闭；推断不是开启的前置条件。
- 保存后显示下一次触发时间，可随时暂停、改时间、改问法、改按钮、删除。
- **集中维护**：设置 → 「习惯」tab 汇总所有未归档习惯页，显示运行中/已暂停/未设置、时间与按钮；可直接切换暂停/恢复，或打开同一确认对话框调整。列表仍以习惯页为唯一真源，不新增计划总表。
- **避免重复页**：digest 提议的习惯页 slug 必须是 `habit/<简短名>`；模型漏写前缀时自动补全，命中既有页就走更新而不是新建。历史重复页仍需人工合并/删除（2026-10-22 已清理 `after-lunch-walk` 与 `habit/after-lunch-walk` 的重复，保留内容更全的后者并并入「家庭」标签）。
- 改时间时，如果问法/记录句里含旧时间词（「中午」「早上」），提示是否一起改；不静默自动改。
- 只在 `kind='habit'` 页面显示入口；`memo` 记事本页永不参与，其他 kind 也不开放。
- v1 只支持「完成/未完成」两个主按钮；不做到多按钮打卡（如「喝了 1/2/3 杯」），那属于后续计数型习惯。

### 4.2 数据

**同步表 `habit_nudges`**（计划随多设备同步）：

```sql
CREATE TABLE habit_nudges (
  id            TEXT PRIMARY KEY,
  page_slug     TEXT NOT NULL,          -- wiki_pages.slug, kind='habit'
  question      TEXT NOT NULL,          -- 用户确认过的问法
  done_label    TEXT NOT NULL,          -- 按钮，如「走了」「读了」「喝了」
  done_text     TEXT NOT NULL,          -- 完整记录句，如「今天中午走步了」
  missed_label  TEXT NOT NULL,          -- 按钮，如「没走」「没读」「没喝」
  missed_text   TEXT NOT NULL,          -- 如「今天中午还没走」
  weekdays      INTEGER NOT NULL,       -- 位掩码，周一=1 … 周日=64
  local_time    TEXT NOT NULL,          -- 'HH:MM'，设备本地墙钟
  enabled       INTEGER NOT NULL DEFAULT 1,
  created_at    TEXT NOT NULL,
  updated_at    TEXT NOT NULL
);
CREATE INDEX idx_habit_nudges_enabled ON habit_nudges(enabled);
```

- v1 一个习惯页最多一条计划（UI 只暴露一条；是否加唯一约束可在实现时定）。
- 时间存**本地墙钟**，不存 UTC：多设备同步时只有 owner（主设备）在本机到点触发，其他设备只同步消息，避免同一天各自插入问候；夏令时由主设备本地日期计算处理。
- 不存整页 markdown，只存确认过的问法、按钮和记录句；推断依据只在确认卡里展示，不落库。
- 按钮/记录句属于计划数据，随同步；用户改文案不影响已经回答的历史消息（历史显示当时的回答正文），未回答的问候按最新文案渲染。

**消息标记**（`messages` 加两列，随消息同步）：

```sql
ALTER TABLE messages ADD COLUMN kind TEXT NOT NULL DEFAULT 'chat'; -- chat | habit_nudge | habit_checkin
ALTER TABLE messages ADD COLUMN ref  TEXT;                         -- 'nudge_id:YYYY-MM-DD'
```

- 问候消息：`role='assistant'`、`kind='habit_nudge'`、`ref='<nudge_id>:<local_date>'`、`content=question`；**没有 chat_run**。
- 用户回答：`role='user'`、`kind='habit_checkin'`、`ref` 同上、`parent_message_id=问候消息 id`；正文用 `done_text`/`missed_text`（如「今天中午走步了」「今天中午还没走」）或用户原话。
- 同一 `ref` 只应有一条 nudge、一条 checkin；应用层先查重，必要时再加部分唯一索引（需先确认同步冲突策略）。
- 旧消息默认 `kind='chat'`，行为不变。

**设备本地表 `habit_nudge_fires`**（不进快照，只有主设备写）：

```sql
CREATE TABLE habit_nudge_fires (
  nudge_id     TEXT NOT NULL,
  local_date   TEXT NOT NULL,          -- 'YYYY-MM-DD'，本地日
  fired_at     TEXT NOT NULL,
  ask_count    INTEGER NOT NULL DEFAULT 1,
  snooze_until TEXT,                   -- 用户点「晚点再问」后的下一次触发时刻
  response     TEXT,                   -- 'done' | 'missed' | 'dismissed' | NULL
  device_id    TEXT NOT NULL,
  PRIMARY KEY (nudge_id, local_date)
);
```

- `(nudge_id, local_date)` 保证每天只有一行；重启、重复 tick 都幂等。
- 「晚点再问」只在主设备更新 `snooze_until = now + 60min` 且 `ask_count < 2`；到点再问一次，之后当天不再问。`snooze_until` 与 `ask_count` 必须同一事务写入。加入设备没有本机 fire 行，因此不显示「晚点再问」；它仍可直接回答，回答消息会同步。
- 触发状态进 `SNAPSHOT_EXCLUDED_TABLES`，理由沿用 `local-event-reminders`。

### 4.3 触发与写入历史

- 挂在 `_tickDueReminders` 之后、分析/消化之前：提醒延迟敏感，习惯问候是分钟级；整个问候 tick 独立 try/catch，失败不影响分析。
- **触发设备**：多设备同步时只有 owner（设置页的「主设备」）执行触发；单机没有同步权威时本机就是主设备。非主设备的 tick 直接返回，不写 fire、不插入消息。
- 每拍做本地时间判断：今天星期几、`now >= local_time`、是否仍在当天可补问时段（07:00–22:00，不做跨天补问）、今天是否已有 fire（无行则到点；有 `snooze_until <= now` 且 `ask_count < 2` 且未回答则再问一次）。
- 到期后：
  1. 写 `habit_nudge_fires`（主设备本地去重锚点）；
  2. 在主对话插入一条 `kind='habit_nudge'` 的 assistant 消息；若同 `ref` 已存在（例如同步恢复或历史竞态），不重复插入；
  3. 广播给 UI：主对话默认是启动页，打开应用即可看到；如果用户停在知识库/回顾等 tab，只在侧边栏「对话」加未读点，**不自动切 tab、不抢焦点**。
- 应用启动时若已过点但仍是当天 22:00 前，补插入一次；22:00 后或跨天不补，也不写 fire（时段外查询自然不命中，次日重新计算）。
- 同一拍多条到期时排队，一次只问一条；用户回答/关闭后再问下一条。
- **不发系统通知**：不初始化通知权限、不调用 OS toast/通知中心；用户打开应用后自然在对话里看到。

### 4.4 交互与回答

问候消息在时间线里渲染成一张带操作的消息卡：

```
[习惯] 今天中午走步了吗？
依据：午饭后散步 · 每天 12:30
[走了] [没走] [晚点再问] [聊聊] [今天不问]
```

- 主按钮文案来自计划：走步是「走了/没走」，阅读是「读了/没读」，喝水是「喝了/没喝」；推断不出来才用「完成了/还没」。
- **done 按钮（如「走了」）**：插入 `kind='habit_checkin'` 的 user 消息，正文用 `done_text`（如「今天中午走步了」，不是只写「走了」），创建一条 `events` 记录（`source='habit_nudge'`），写 fire.response='done'；**不自动跑 AI**，消息卡显示「已记录」。这样历史里是一问一答，跨设备也能看到回答，事件也能被正常分析。
- **missed 按钮（如「没走」）**：插入 user 消息，正文用 `missed_text`（如「今天中午还没走」），写 fire.response='missed'；**不自动创建事件**，卡片提供「聊聊原因 / 晚点再问」。
- **晚点再问**：不写消息，只更新本机 snooze；卡片显示「已推迟到 13:30」。这是设备侧行为，不要求跨设备一致。
- **聊聊**：把主对话输入框预填为 `done_text` +「，……」或 `missed_text` +「，因为……」，用户发送后走正常对话与 AI 管线；不替用户自动发送。
- **今天不问**：写 fire.response='dismissed'，当天不再问，不改变计划；连续忽略达到阈值时，下一次改为建议卡（「要不要把时间改到晚上？」），不自动改计划。
- 快速回答不触发 AI，因此不会出现 typing、重试、重新生成；普通输入框里的自由回复仍走正常 AI 回合。
- 按钮文案只是 UI；事件正文始终用完整句子，避免时间线里出现一堆孤立的「走了」。
- **没有系统通知**：应用最小化/关闭时不会弹 toast。再次打开应用、切回主对话时，未处理的问候仍在时间线里并显示未读点；这是 v1 明确接受的产品边界。

### 4.5 回答如何沉淀

- done 按钮用 `done_text` 创建普通 `events` 行（如「今天中午走步了」），进入既有分析 → 消化 → 习惯页证据更新链路；不直接改 `wiki_pages`。
- 不新增「打卡表」作为事实源：事件才是可分析、可同步、可回顾的原始记录；`habit_nudge_fires` 只负责本机去重和回答状态。
- 事件正文优先用已确认的完整句；需要时可带习惯页标题或标签（如「午饭后散步：今天中午走步了」）帮助分析/检索关联。v1 不给 `events` 加 `related_wiki_slug` 列，避免动事件同步表；若后续关联不稳定，再单独立项。
- 回顾页/周报可以看到「习惯问候 → 完成/未完成」的次数，但首版不强制做 streak UI。

### 4.6 AI 的边界

- **创建时**：推断时间/问法可调用一次后台 AI；结果必须经确认卡确认。
- **触发时**：不调用 LLM；问法来自 `habit_nudges.question`。
- **回答后**：走正常事件分析/消化，AI 可能更新习惯页；不因一次回答就改写习惯结论。
- **建议时**：连续多次没做/忽略，生成一张确定性建议卡（改时间/降低频率/暂停），用户确认才落库；不让 AI 自动改计划。

### 4.7 上下文与多设备

- `context_for_input` 需要把 `habit_nudge` 当作一个独立的 assistant 回合，后接 `habit_checkin` 用户回答；不能把问候归进上一条 user turn。
- 摘要可以包含这条简短问候/回答；若后续发现占用明显，再按 `kind` 排除（先测量再决定）。
- 计划随同步；触发/晚点状态只在主设备。问候消息和回答消息随 `messages` 同步，因此其他设备能看到「问过且已答」。
- 其他设备没有本机 fire 行：卡片用同 `ref` 的 `habit_checkin` 消息判断已回答；未回答时仍可直接回答，回答也会同步。非主设备不显示「晚点再问」，避免只改本机状态而主设备不会补问。
- A 方案（2026-10-22 用户拍板）：只有 owner 主设备执行插入，其他设备不参与触发；主设备关闭时当天不补问。这样不再依赖「两台设备同时插入后再收敛」。

## 6. 验收

1. 在 `habit/午饭后散步` 页点「定期问我」，系统给出 12:30 + 问法 +「走了/没走」+ 记录句「今天中午走步了」+ 依据；不点「开启」不落库；手动改时间/按钮后按新配置生效。
2. 重启应用后计划仍在；另一台设备同步到同一计划，但只有主设备触发；同一天不重复插入问候消息。主设备关闭时其他设备不会代为触发（A 方案取舍）。
3. 12:30（或当天再次打开应用）主对话时间线出现一条 `habit_nudge` assistant 消息；重复 tick、重启、热重载不重复。
4. 点「走了」：时间线出现 user 回答「今天中午走步了」，且只生成一条同文事件；分析/消化后习惯页证据计数增加；没有 AI typing/重试。
5. 点「没走」：出现 user 回答「今天中午还没走」，但不生成事件，当天不再追问；「晚点再问」在 +60 分钟且当天上限内再问一次。
6. 「阅读」习惯推断出「读了/没读」，「喝水」推断出「喝了/没喝」；推断失败回退「完成了/还没」；按钮文案可改，且改完同步。
7. 关闭/暂停后不再触发；删除习惯页或改 kind 后计划失效（外键/校验二选一，取不产生幽灵问候的方案）。
8. 不请求系统通知权限、不产生 OS 通知；用户停在知识库/回顾 tab 时，侧边栏「对话」出现未读点，不自动切 tab。
9. 应用完全退出：当天 22:00 前再次打开补插入一次；22:00 后或跨天不补，不出现「昨天」问候。
10. 记事本 `memo` 页永远没有该入口，也不会被问候 tick 读取；问候消息不会破坏上一轮上下文（`context_for_input` 单测）。
11. 设置 →「习惯」tab 列出所有未归档习惯页：有计划的显示运行状态、时间与按钮，可直接暂停/恢复或打开确认框调整；未设置的显示入口。改动后习惯页头部同步更新。

## 7. 非目标（v1）

- 不做任意 cron/复杂 RRULE、不做日历集成；
- 不做「AI 每天自动生成一句新问法」；
- 不做 streak/排行榜/惩罚机制；
- 不做应用退出后的守护进程或开机自启；
- 不做系统通知/推送/通知权限，也不做点击通知回到消息；
- 不做多按钮/计数型习惯（「喝了 1/2/3 杯」），v1 只有完成/未完成两个主按钮；
- 不把问候做成独立的会话/会话列表；
- 不做基于位置/传感器的自动判断（「你是否已经在走路」）。

## 8. 开放问题（需要拍板）

1. **未完成按钮（如「没走」）要不要也生成事件？**
   - 推荐不生成，只写 user 消息 + 本地 response；否则每天都可能多一条负面事件，时间线噪音大。若用户主动「聊聊」，再由对话里的 `record_event` 决定是否落库。
2. **两台设备同时在线时的去重策略？**
   - 已拍板（2026-10-22）：A 方案，只有 owner 主设备触发并写入；其他设备只同步消息，不再各自插入。主设备关闭时当天不补问，换设备接管留到后续。
3. **一个习惯页允许多个时间点吗？**
   - v1 建议一条；多条可在后续把 `habit_nudges` 的 UI 做成列表，不改造表结构。
4. **计划是否跟随习惯页删除/归档？**
   - 建议归档即暂停、删除即级联清理；不留下指向不存在页面的幽灵问候。
5. **问候消息要不要进入摘要/上下文？**
   - 推荐进入（它是一问一答，能帮助后续对话理解）；若 token 压力明显，再按 `kind` 排除。

## 9. 分期

- **P0（本提案 v1）**：习惯页推断确认（含问法、时间、完成/未完成按钮与记录句）+ `habit_nudges`/`habit_nudge_fires` + `messages.kind/ref` + 5s tick + 主对话问候消息 + 侧边栏未读点 + 自定义按钮/晚点/关闭 + 事件落点 + 本机去重 + 同步基础 + 设置页集中提醒列表。
- **P1**：连续忽略后的「改时间/降频/暂停」建议卡；回顾页统计；主设备离线时是否由其他设备接管触发（需要新的设备租约/同步状态）。
- **P2**：AI 根据近期事件调整问法/建议（仍需用户确认）；更复杂的重复规则；多按钮/计数型习惯。
