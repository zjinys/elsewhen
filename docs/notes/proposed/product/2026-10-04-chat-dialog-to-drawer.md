# 对话界面「对话框 → 侧边抽屉」改造报告

- 日期：2026-10-04
- 状态：proposed（调研完成，待定方案与范围）
- 范围：对话主界面（`message_area.dart`）及相邻的审阅/历史/待办/目标入口
- 性质：交互与信息架构调整，不涉及业务逻辑、SQL 或同步语义

## 1. 背景与问题

对话界面当前把「待办 / 目标 / 草稿 / 审阅提议 / 生成历史」这些**需要在聊天过程中随时参考或操作的内容**，都用模态 `Dialog` 弹出。由此产生三个体验问题：

1. **遮挡对话**：弹窗把正在进行的对话整个遮住，用户看完必须关闭才能继续聊，无法「边聊边看」。
2. **空间局促**：待办列表塞在 620×560 的 `Dialog` 里需要滚动；审阅提议涉及多个提议 + 批量操作，弹窗里层级深。
3. **心智割裂**：这些内容本质是「侧边可参考的工作区」，却被做成「临时打断的浮层」。

目标：把这些**非模态内容面板**从 `Dialog` 中解放出来，同时保留真正需要「当场决策 / 短暂聚焦」的确认与编辑弹窗。

## 3. 分类原则

判定「改抽屉」还是「保留 Dialog」，只问两个问题：

1. **是否阻断主流程？** 确认、冲突三选、删除这类「必须当场给答案」的交互，模态是正确语义；改成非模态抽屉会让用户走开留下悬而未决状态。
2. **是否需要边对话边操作？** 待办勾选、草稿处理、审阅提议是「伴随对话进行」的工作，非模态面板更合适。

据此：

- **改抽屉（非模态内容面板）**：#1 草稿、#2 待办、#3 目标、#7 审阅提议（及其二级 #8/#9）、#10 生成历史（可选）。
- **保留 Dialog**：#5 删除确认、#6 歧义选择、#11 任务范围、#12/#13 编辑表单。

### 3.1 既有 Dialog 又有抽屉，会不会「乱」？

不会，前提是划分规则一致、可预期。

- **现状本就是混合的**：左侧导航栏（非模态常驻）+ 右侧 wiki 面板（非模态工作区）+ 各种 Dialog（模态打断），三者长期并存且体验自然。混合本身不是问题，「无规律地混用」才是。
- **成熟桌面应用同理**：VS Code、Notion、Slack 都是 Dialog + 侧边面板并存，靠的是语义一致——同一类操作永远用同一种形态。

统一判断原则（用户可预期）：

> 必须当场回答的 → 模态 Dialog；边做边看的 → 右侧面板。

| 动作 | 形态 | 理由 |
|---|---|---|
| 看/勾待办、处理草稿、审阅提议 | 右侧面板 | 边聊边做，可随时关 |
| 删除草稿、冲突三选、关闭脏 tab | Dialog | 必须当场决定，不可溜走 |
| 编辑某条待办/目标 | 面板内嵌展开 | 不套娃 |

**防套娃规则**：二级内容（单草稿详情、单提议详情、编辑表单）在面板内部内嵌展开，绝不从面板再弹二级 Dialog；只有「确认删除 / 确认冲突」这类纯确认才用 Dialog，且永远是小确认框。

## 4. 推荐方案

### 4.1 三种候选形态对比

| 方案 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| A. `Scaffold.endDrawer` | 外层 `Scaffold` 加右侧抽屉 | 标准组件、手势/遮罩现成 | `MessageArea` 嵌套在 `Row` 内无独立 Scaffold，需跨层用 provider 控制；与窄屏 `drawer`（左导航）语义重叠；默认是模态遮罩，与「不阻断」目标相悖 |
| **B. 自定义右侧滑出面板（推荐）** | `MessageArea` 内 `Stack` + `SlideTransition`/`AnimatedPositioned`，复用现有右侧 wiki 面板心智 | 集中在 `MessageArea`，可控；非模态、对话始终可见；空间可按需 320–420px；不碰 `Scaffold` | 需自管打开/关闭动画与焦点；多一个「面板内容切换」状态 |
| C. 底部非模态 `showBottomSheet` | 标准 bottom sheet（非 modal） | 改动最小 | 纵向空间受限，与「右侧工作区」心智不符；桌面端体验偏移动 |

**推荐 B**：把「待办 / 草稿 / 目标 / 审阅提议 / 生成历史」统一为一个**右侧滑出面板**，面板内用 `TabBar` 或分段切换内容。理由：

- 复用现有「右 wiki 面板」的布局心智，用户已习惯右侧工作区；
- 非模态，聊天列表始终可见，可边聊边勾待办、处理草稿；
- 改动收敛在 `MessageArea`（及一个新增 `chat_side_panel.dart`），不触及 `main_screen.dart` 的 `Scaffold.drawer`（该抽屉已用于窄屏导航）。

### 4.2 目标结构

```
ui/lib/widgets/
├── chat_side_panel.dart          # 新增：右侧滑出面板容器（SlideTransition + 分段切换）
├── message_area.dart             # 「今天」栏四个入口改为打开面板，不再 showDialog
├── chat_proposal_review.dart     # ChatProposalReview 由 Dialog 改为面板内的一段
├── chat_run_history.dart         # 生成历史改为面板内的一段（可选）
└── （todo_view / goal_view 的编辑 Dialog 保持不变）
```

面板内容按需惰性构建（打开对应分段时才实例化 `TodoListView` 等），避免常驻订阅。

### 4.3 状态与行为

- 打开状态用一个 `StateProvider<bool>`（或 `Enum` 表示当前分段）管理，`MessageArea` 与面板共享；
- 关闭方式：再点一次入口、点面板外空白、`Esc`；不引入模态遮罩；
- 面板打开时输入框仍可用（这是与 Dialog 的核心差异，也是改造的意义）；
- 二级内容（单草稿详情、单提议详情）在面板内**内嵌展开**，不再弹二级 Dialog；只有「删除草稿确认」等纯确认仍用 `AlertDialog`。

## 6. 风险与权衡

1. **焦点/键盘**：面板非模态后，输入框焦点与面板操作可能冲突，需明确焦点策略（面板打开不抢占输入焦点）。
2. **窄屏**：`<700px` 时右侧空间有限，面板可能与 wiki 面板抢宽；窄屏可降级为全宽覆盖或底部 sheet。
3. **状态常驻**：若面板内容改为常驻订阅，会引入不必要的重建；必须惰性构建（见 4.2）。
4. **测试成本**：现有测试有 `find.text` 定位 Dialog 内容，迁移后需同步更新定位方式（面板内容仍以相同文案出现，影响可控）。
5. **确认语义不丢**：所有「是否执行 / 冲突 / 删除」的模态确认必须保留，改造只针对「浏览 + 操作」类内容。
6. **套娃风险**：从面板再弹二级 Dialog（或反向）会造成层级混乱；二级内容必须面板内嵌展开，仅纯确认用 Dialog（见 3.1）。
