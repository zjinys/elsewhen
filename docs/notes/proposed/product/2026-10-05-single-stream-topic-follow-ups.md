# Agent Note: 单流对话对 LLM Wiki 的支撑

Status: proposed

## Problem

[单流对话与显式主题入口](../../implemented/feature/2026-09-21-single-stream-topic-implementation.md)已经完成基础信息架构。2026-11-09用户明确：主题后续演进主要看它如何支撑LLM Wiki，价值应体现为知识积累、更新与复用。

原方案把主题生命周期、“今天”排序、分析状态、同名确认和建议归拢放在一起，容易变成另一套需要维护的主题管理界面。显式主题入口按精确标题复用，否则创建的行为仍需考虑重复页，但相似标题本身不能证明两页属于同一知识主题。

现有LLM Wiki已有全文检索、来源与修订、依赖更新、主题合并／拆分、冲突／重复／过时提示、处理历史及整理队列，详见[交付与边界](../../../llm-wiki-implementation-gaps.md)。本提案需要先核验这些已有路径在真实对话中是否有效，不能把它们重新作为待开发能力。

## Proposal

围绕“对话读取已有知识 → 新事实／新结论沉淀 → 知识更新 → 后续回答复用”的链路收紧范围。优先用真实模型场景定位缺口，已有路径可用则只补验证；只有发现失败才登记和实现对应增量。

1. **对话前召回合适的已有知识**：检索相关知识页、适用条件与有效依据；允许继续原有讨论，不能只凭标题相似切换话题。区分原始材料、个人记录、模型归纳和已确认规则，不让过时或失效知识冒充当前依据。
2. **新内容补入合适的页面**：有可沉淀的新事实、经验或结论时，比较补充现有页、修订现有结论、另建页面或不写入。使用真实页标识和来源证据，避免重复页和无价值改写。涉及人工页、既有审阅或规则升级时，沿用现有审批边界；普通聊天不逐条强迫用户选择归属。
3. **让变化进入已有维护流程**：发现矛盾、新限制或旧结论失效时，关联具体页、修订和来源，复用现有维护提示、修订、依赖复核及主题整理。不能单凭相似标题合并页面，也不能自动裁定冲突或覆盖人工知识。
4. **验证后续确实能用上**：用户之后换个问法，仍能找到已沉淀或已修订的知识；回答使用当前有效结论并能展示出处。明确区分“已经保存”“已经更新”“仅提出待审建议”，不能只以页面数量增长判成功。
5. **必要状态服务于这条链路**：只有处理延迟或失败影响知识可用性时，提供简短状态和现有队列入口；不复制完整诊断界面。主题状态／排序只有在能改善召回或知识维护时才另行论证，暂不单独排期。

### 真实场景与实施边界

例如：已有“客户访谈方法”页，包含旧经验及出处；今天的对话补充“先问愿不愿买得到的承诺不可靠，应询问最近一次实际行为”。系统应先找到已有页，在有依据且符合写入权限时补充或准备修订，保留新旧出处；下周用户问“第一次找客户该怎么聊”，能引用更新后的方法。若两次经验的适用对象不同，应保留条件差异，不能把它们简单合并成一个普遍结论。

这一例子是拟验收场景，不表示当前实现已验证失败。开发前逐项对照现有 `knowledge/authoring`、检索、维护与后台整合路径，把缺口分为既有能力待验收、明确工程缺陷或必要新增能力；继续复用[主线](../../../roadmap/2026-09-17-personal-cognition-main-loop-roadmap.md)。

## Alternatives considered

- 先做主题进行中／搁置／收尾及侧栏排序：方便管理，但没有直接证明知识更准确、更容易复用，暂不作为本项核心。
- 只做标题去重：无法区分同名异义、同义不同名和知识适用条件，只能辅助候选发现。
- 让用户对每段对话手动选择知识归属：增加录入负担，也未利用现有自动消化能力。
- 普通讨论立即自动建页、合并或升级规则：会积累低价值页面并越过现有保护边界。
- 另建主题整理／冲突／队列体系：重复LLM Wiki已有能力，造成多个事实来源。

## Acceptance criteria

- 真实模型端到端场景覆盖已有知识召回、同义提问、新内容补充、没有增量时不写入、矛盾与适用条件、用户纠正后的再复用。
- 每次保存／修订使用真实页标识、实际提供的来源和当前版本；人工内容、待审决定及规则升级边界保持。
- 同一输入或重复执行不会重复建页、重复追加相同知识；同名不同义和不同名同义均有验证。
- 新知识确认入库后，后续独立提问能够召回；过时／失效结论不被当成当前有效知识引用，能查看实际依据。
- 只提出待审建议时不能声称已更新；没有足够材料时允许不写入或明确证据不足。
- 记录正确召回／漏召回、错误归属、重复写入、知识遗漏、引用有效性、调用量与等待成本；存储／回环测试和真实模型质量证据分别记录。
- 已有能力通过验收就不重复开发；新增UI或主题状态必须对应上述链路中的可复现问题。

## Risks

- 相似度不能替代知识归属与条件判断；模型可能把互补经验误判为冲突或混合不同场景。
- 过度归拢会抹掉条件、反例和来源，过度建页则制造重复知识。
- “保存成功”不代表后续能召回，更不代表知识正确，必须跨独立提问核验。
- 后台复核与检索可能增加成本，需有界候选、固定输入去重和完整预算；具体工程增量以复核结果为准。

## 2026-11-09 工程交付与用户验收

用户指定“先补功能，再制定测试计划，由用户测试”。本批在 `feat/llm-wiki-conversation-support` 补上原查询＋最多3种语义改写的候选融合、移除适用条件词面硬筛、修订追加已提供来源／知识依赖／当前输入事件、中英文新增依据预览、相近内容复用提示、精确无变化及相同待审修订去重。所有知识写入沿用确认制，失效／过时依据继续过滤；不新增主题管理界面、向量库或后台自动裁决。

工程全量Rust1212项单元＋2项集成、Flutter612项、Release及静态分析／本地化门禁通过。实现与边界见[决定](../../implemented/architecture/2026-11-09-wiki-conversation-evidence.md)及[路线](../../../roadmap/2026-11-09-llm-wiki-conversation-support-roadmap.md)。用户按[测试计划T1–T10](../../../testing/2026-11-09-wiki-conversation-support-manual-test.md)执行真实召回、增量归属、去重与再次复用；前述质量标准尚未验收，保留proposed生命周期作为待验收范围，不能用工程通过替代真实效果。
