# Agent Note: 外部目录项目导入的信息边界仍需重新设计

Status: superseded

Superseded by [有界项目盘点与 AI 综合评估](../../implemented/architecture/2026-09-23-bounded-project-assessment-synthesis.md). This proposal records the original problem and rejected alternatives; its open questions were resolved by the implemented decision.

## Problem

当前外部目录导入的项目模式会把大量文件扫描结果拼成一张 Markdown 文件地图，并写入一张项目知识页。`anvil` 目录约 18 万个文件，生成的正文约 3.2MB，打开页面时 AppFlowy 同步解析整篇文档，导致界面长时间无帧并出现 OpenGL frame timeout。

当前已经增加文件地图数量上限，但这只是止血措施，不能证明“截断后的文件地图”就是正确的知识表示。简单照搬 Codex 的 bounded snapshot 也还不足以确定 Elsewhen 的项目导入语义。

补充观察：用户在 Codex 中要求“看看这个项目，总结主要功能和完成情况”时，系统采用只读盘点流程：先梳理目录结构、review 文档、关键配置和代码统计，再由模型输出主要功能、已完成部分、未完成项、门禁状态和总体判断。输出是短报告，不是目录镜像。这种“项目盘点报告”比直接生成大体量项目知识页更符合当前需求。

## Proposal

项目模式不保存完整或截断文件地图，而是先进行只读项目盘点，围绕主要功能、完成情况、未完成线索、验证依据和总体状态生成短报告。用户明确发起“导入”时，系统在预览阶段生成报告并创建待确认动作；此时不写知识页。用户确认后才将预览中的同一份报告沉淀为项目知识页，不重新扫描或调用 AI。未明确要求导入时，工具不应被调用。

可以参考 Codex 的分层扫描、忽略噪声目录、优先读取入口文件和按需展开，但不能直接把目录镜像或大文件快照写入知识页。任何实现都必须先保证单页正文有明确大小上限，并在扫描阶段拒绝或降级超大目录。

## Alternatives considered

- **完整文件地图**：实现简单，但已被 `anvil` 实例证明会阻塞阅读界面。
- **限制为 2000 条文件地图**：可防止再次生成数 MB 页面，但仍然是错误的信息模型，只保留了截断后的目录镜像。
- **直接采用 Codex 式 bounded snapshot**：方向上更合理，但当前尚未回答项目事实与临时扫描上下文的边界，不能直接作为最终设计。
- **只读项目盘点报告**：采用确定性目录统计和有界文件样本，优先读取项目说明、元文档、技术栈 manifest、review/检查记录、入口与测试线索；可用 AI Provider 时生成短报告。预算、脱敏边界和确认保存入口由后续实现决策明确。
- **每个文件生成一张 source 页**：适合明确的“逐文件导入”意图，不适合作为项目模式默认行为。

## Consequences

- 当前超大项目页需要压缩或重新生成，避免继续阻塞 AppFlowy。
- 项目模式后续应优先形成短小、可阅读、可引用的项目摘要，而不是保存目录副本。
- 原方案曾将项目模式与完整/截断文件地图绑定；该方向已由后续实现决策取代。新的扫描预算与 AI 综合流程见实现记录。
- 在新方案确定前，文件数量、单文件大小、总正文大小限制仍必须保留，作为安全和性能底线。
