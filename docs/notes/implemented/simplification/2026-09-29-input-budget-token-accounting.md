## Problem

`compress_context` 用 4096 的预算裁剪上下文，但这个预算既低估了中文，又完全看不见工具定义。
结果是代码全程认为自己合规，实际发出的请求约为预算的两倍。

这是排查「AI 对话空回复」时顺带发现的。**它不是那次故障的原因**（见「为什么不是本次断链的原因」），
但它让输入预算失去了防护作用。

## 实测数据

全部数字来自向当前活跃 provider（`hub.oaifree.com` + `gpt-4o`）真实发请求读取
`usage.prompt_tokens`，不是估算。

### 系统提示的真实体积

把 `SYSTEM_PROMPT_BASE`（`src/ai/memory.rs:57`）的原文原样发出去：

| | 值 | 来源 |
| --- | --- | --- |
| 运行时字符数 | 4797 | 代码 |
| `estimate_tokens` 的估算 | **2091** | 代码 |
| **中转报告的 `prompt_tokens`** | **3195** | 实测 |
| **低估倍数** | **1.53×** | |

> 注：`estimate_tokens` 把**所有非 ASCII 字符**（含中文标点）都按 `wide/2` 计。
> 早先一版这里写成 1812 / 1.76×，是用正则只数 CJK 汉字、漏掉标点算错的。代码实测为 2091。

### 19 个工具定义的真实成本

同一个请求加上 19 个真实工具 schema（`provider_specs_for(false)`）：

| | 值 |
| --- | --- |
| 系统提示 + 19 个工具 | 5096 |
| 系统提示单独 | 3195 |
| **19 个工具的真实成本** | **1901** |

### 叠加后的算术

```
真实固定开销 = 系统提示 3195 + 工具定义 1901 = 5096 token
                                          ↑ 已经超过 4096 预算本身（超 24%）
                                          ↑ 此时对话历史还没算进去

代码看到的   = 系统提示 2091 + 工具定义   0 = 2091 token
```

也就是说：**光固定开销就超预算 1000 token，而压缩逻辑看到的数只占预算的 51%。**

实测的应用行为印证了这一点：闲聊轮的 `prompt_tokens` 稳定在 8008–8170，
正好是 5096 固定开销 + 约 3000 的历史与动态注入——
**也就是说应用已经站在裁剪触发线上。**

### 为什么预算会「看起来合规」

`compress_context`（`src/ai/memory.rs`）的判定是：

```rust
let total: usize = context.iter().map(|m| estimate_tokens(&m.content)).sum();
if total <= max_tokens { return; }   // 只看消息正文
```

两处失真叠加：

1. **`estimate_tokens` 假设中文 2 字 1 token**（`ascii/4 + wide/2`），实际约 0.66 字 1 token
   （自然中文测得 0.662）。在当前代码返回的 2091 vs 实测 3195 的差异下，
   同一段内容被估成真实值的 65% 左右。
2. **工具定义根本不在 `context` 里**，所以那 1901 token 从未被计入，`total` 永远偏低。

结果：`total` 轻松低于 4096，函数直接 `return`，**很多时候一次都不裁**。

## 一个把我带偏的测量（留给以后的自己）

第一次校准时我用「同一个中文字重复 N 次」构造样本，测出 **1.0 token/字**，
据此以为系统提示是 3184 token，并用「中文 1 字 1 token」去论证问题。

**这个测量是错的。** 单字重复无法被 BPE 合成词，而真实中文常用双字词会合并成单个 token：

| 样本 | 字符数 | `prompt_tokens` | 每字 |
| --- | --- | --- | --- |
| 「中」× 14000（无标点） | 14000 | 14103 | 1.007 |
| 一句带标点的自然中文重复 | 14000 | 9759 | 0.697 |
| **系统提示原文（直接测量）** | 4831 | **3195** | **0.662** |

> 注：系统提示的 3195 是把还原后的字符串整体发出去测的；这 0.662 是**混合文本**的
> 平均值，不能拆成「中文 0.662 / ASCII 某个值」——那需要分开测，本文件没做。

**结论：校准必须用真实文本，不能用重复字符合成。**
本文件所有数字都来自真实文本的直接测量。

## 4096 这个预算到底在做什么（实测代码路径）

预算用在两层，两层都是「**压缩**」而不是「截断」：

1. **`SlidingWindowMemory::prepare_context`**（`src/ai/memory.rs`）从库里拉历史，
   从最新往回累加，超 4096 est 就停。系统提示后插到 `context[0]`，**不计入这个预算**。
2. **`compress_context(context, 4096)`**（`src/ai/conversation.rs:249`）在最终边界再压一次：
   主系统提示永不丢、最新 user 轮永不丢（`rposition` + `split_off`）、
   动态 system 消息最多拿剩余预算的一半、其余历史折成一条
   `（自动压缩的较早对话，仅供回忆）` 摘要（每条 ≤160 字）。

设计意图是「老对话变成紧凑转录，而不是从中间消失」。

### 但触发线比想象的高

| | 值 |
| --- | --- |
| 系统提示 est | 2091（占预算 **51%**） |
| 留给历史 + 动态注入 | ~2005 est |
| 触发裁剪所需历史 | ≈ 4000 中文字 |
| 触发时的真实 token | 3195 + 1901 + ~2600 ≈ **7700** |
| 应用实测闲聊轮 | **8008–8170** |

**应用已经站在裁剪触发线上了。**

### 实测撞出的两个额外缺陷

在验证上述行为时（临时 `#[cfg(test)]` 探针，验完已删）撞到两处代码路径问题，
它们跟 token 口径无关，是独立缺陷：

**(1) 没有 user 消息时完全不裁。**
`compress_context` 里 `context.iter().rposition(|m| m.role == "user")` 返回 `None`
就直接 `return`。实测：一条 est=3000 的 assistant 消息 + 2091 系统提示
（合计 5091 > 4096）进去，出来原样 5091，一个字没动。
按设计意图（老消息压成摘要）这里应该也走压缩分支。

**(2) 最新 user 消息过长时，全部历史被静默丢弃，连摘要都没有。**
`remaining` 用 `saturating_sub`，当前 user 轮一大就归零；随后历史循环第一次判断
`cost > remaining(0)` 立刻 break，`kept` 为空；摘要分支的条件是
`!history.is_empty() && remaining >= 24`，0 不满足 → 什么都不加。
实测 6 条消息（4 轮历史）进去，剩 2 条，历史凭空消失且无任何标记。

`bound_model_context` 允许最新消息到 24000 字符，**这条路径在应用里可达**。

## 已知取舍 vs 缺陷

`estimate_tokens` 的 2× 低估**不是疏忽**——代码注释里写明了：

> `2× 低估已是压缩预算下可接受的折中，避免请求体硬超 provider 上限。`

也就是说作者**主动**用低估换「绝不硬超上限」的保守性。问题在于这个折中
在 128k 窗口的 gpt-4o 下偏松（真到 7700 token 才动手），
但它的原始理由本身是对的。所以本文件把它记作
**「在当前 provider 窗口下已不再成立的已知取舍」**，而不是「作者搞错了」。

（工具成本同理：占位工具测出 2561，真实工具测出 1901，差 35%。）

## 为什么不是本次断链的原因

拿真实的 19 个工具表，扫 4 档上下文大小、每档 3 次，共 12 次请求，覆盖
`prompt_tokens` 872 / 4803 / 7562 / 11699，**12/12 全部正常返回**。

gpt-4o 标称上下文 128k，8100 离上限很远。所以上下文大小不构成那次空回复的故障条件
（那次的真因见
[空回复根因调查](../../implemented/bug-fix/2026-09-29-empty-reply-root-cause-investigation.md)）。

## 真实风险

1. **历史得不到有效裁剪**，对话变长后请求线性膨胀。实测触发线在真实 ~7700 token。
2. **撞上 provider 硬上限时没有任何预警**。中转标称的窗口常常与实际不符，
   而这套预算对真实请求量一无所知——它在按 2091 做决策，真实固定开销是 5096。
3. 系统提示占预算的**实际** 78%（3195/4096），代码以为是 51%（2091/4096）。
4. **长消息会静默吃掉全部历史**（上文缺陷 2）——这条跟 token 口径无关，
   换小窗口模型时更容易撞上，且**无任何提示**，模型会像失忆一样重新开始。

## 修的话要动五处

前三处是 token 口径，后两处是本次顺带撞出的代码路径缺陷。

| # | 改动 | 影响面 |
| --- | --- | --- |
| 1 | `estimate_tokens` 权重改成实测值（混合中文约 0.66 字/token） | 全局估算变化，会触发更多压缩，可能改变现有行为；需跑全量 + 变异验证 |
| 2 | `compress_context` 把工具定义的 token 计入 `total` | 需把 tool specs 传进函数，改签名；所有调用点（含 `memory.rs` 内 4 处单测）都要跟 |
| 3 | `max_tokens: 4096`（`src/ai/conversation.rs:48` 硬编码）重新定值 | 系统提示一项就 3195，4096 留给历史的只有约 900 |
| 4 | 无 user 消息时也走压缩分支（去掉 `rposition` 的 `None` 早退） | 行为变化：以前完全不动，现在会压。需确认这是期望行为 |
| 5 | `remaining` 归零时至少给历史留一条摘要，或明确标记「历史已省略」 | 行为变化：以前静默丢弃，现在会留痕。需产品决策 |

第 2 条要改公开签名、第 1 条改变全局估算，影响面比同期的诊断类改动大一个量级。
**建议 1–3 单独一轮做，不要和别的修复混在一起**；4、5 涉及行为语义变化，
应该先确认「静默丢历史」到底是不是有意为之（目前没有任何注释或测试表明这是设计）。

## 演进方向：4096 不该写死，应由模型参数决定

2026-09-29 讨论补充。核心问题：`max_tokens: 4096` 是「记忆意愿」还是「输入护栏」？
答案是两头都不是——它缺一个决定的依据，而「依据」应该来自模型的上下文窗口。

### 先探测了当前 provider 的真实窗口

同一中转（`hub.oaifree.com`）、同一标称 gpt-4o：

| 构造的 prompt | 结果 |
| --- | --- |
| 16k / 32k / 64k token | ✅ 全部正常（`prompt_tokens` 如实报告 16103/32103/64103） |
| 100k / 128k token | ❌ curl 超时（90s 无响应，**不是** `context_length_exceeded` 明确拒绝） |

两个结论：

1. 该中转下的 gpt-4o **至少 64k 窗口**，远高于 4096；「4096 太紧」这个直觉本身是对的。
2. 但「参数表里写 gpt-4o=128k」是**想当然**——100k 就已然失联。中转实际映射的窗口，
   **探测才知道，写死不等于保证**。

### 三层数值、三种来源

现在 `max_tokens: 4096` 把三个东西糊成了一个数：

| 数值 | 是什么 | 正确来源 |
| --- | --- | --- |
| **上下文窗口**（context window） | 模型能力上限，是 `model` 的属性 | ✅ 做成 **provider 级参数**，每个模型存一个 |
| **输入预算**（4096 想做的事） | 每轮请求保留多少历史的**克制决策** | 推算值：**窗口 − 固定开销 − 输出预留**，不是常数 |
| **输出上限**（现有 `OpenAiCompatibleConfig.max_tokens`） | 输出侧 | 已有字段，不要与输入混用 |

用推算式替代魔数：`输入预算 = context_window − SYSTEM_PROMPT − 工具定义 − output预留`。
按本文件实测数字，gpt-4o 若窗口 128k：`131072 − 3195 − 1901 − 4096 ≈ 122k`，
历史几乎永远不用压——那才符合「直觉上不该裁」。

### 提案：参数化 + 推算 + 失败降级

1. `ai_provider_configs` 加 `context_window` 字段（每模型一个保守实测值）
2. `ConversationConfig` 默认值改为从活跃 provider 的窗口推算，不再写死 4096
3. **失败降级**：请求被拒（`context_length_exceeded`）时，把该 provider 的窗口
   记小一档并重试——因为中转标称和实际不符，只有运行时才拿得到真相

### 与「收窄模型名单」的关系

只保留 `deepseek-v4.1-flash` / `glm-5.3-flash` / `gpt-4o` 三个模型，
是参数化的**前提**：支持面小，每个模型的窗口参数才维护得起。
落地参数化前需要给这三个模型各做一次本文件「复现」节的窗口探测，
把各自保守值写进参数表（当前只有 gpt-4o@oaifree 探过：≥64k）。

### 顺序依赖

```
1. 修估算口径（中文权重 + 工具计入 total）   ← 预算第一次看见真实用量
2. 加 provider 级 context_window 字段         ← 参数化开始
3. 预算改为「窗口 − 固定 − 输出」推算          ← 4096 魔数消失
4. 失败降级重试                               ← 防御中转标称 ≠ 实际
```

**别急着「调大 4096」**：那只是把触发线往后挪，防撞上限的数学保证一点没多——
必须先做第 1 步，否则参数化后预算依然按失真的 `estimate_tokens` 做决策，
只是把一个盲常数换成一个「看着更懂行」但同样盲的值。

## 待决

- 权重是否直接换成实测值，还是保守取整（如中文 0.75）以避免过度压缩？
- 工具定义的 token 是否该计入同一个预算，还是给它们单独一份额度？
  （现有 provider 每轮都全量发送工具，不随对话变化。）
- `4096` 是历史遗留值还是有依据的？需要确认它在引入时的意图
  （演进方向一节建议直接废弃它，改为窗口推算）。
- 演进方向是否采纳：加 `context_window` 字段 + 推算式预算 + 失败降级？
  若采纳，模型名单收窄到哪三个需要一并拍板。
- 「最新消息过长 → 历史全部静默丢弃」是**已知取舍**还是**遗漏**？
  代码里没有注释说明，现有测试也没覆盖这条路径。
- 无 user 消息时不压缩，同样需要确认意图。
