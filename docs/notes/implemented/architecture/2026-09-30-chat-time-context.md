# Agent Note: 为聊天注入可追溯的时间上下文

Status: implemented

## Problem

主对话和知识页对话原先在装配消息时丢弃 `created_at`，模型缺少可靠的当前日期与历史发送时间。“昨天”可能被按生成时的日期重解，跨午夜或延迟处理时尤其明显。优化方向见 [AI 对话体验方案](../../proposed/architecture/2026-09-30-ai-chat-experience.md)，任务归属为 [Roadmap C00a](../../../roadmap/2026-09-30-ai-chat-experience-roadmap.md)。

## Decision

- `ai/time_context.rs` 提供可注入时钟和历史时区转换；生产使用 chrono 的系统本地时区，测试使用固定时钟。输出完整日期、星期、本地时间与 UTC offset，不猜测原发送地时区。
- `ContextMessage` 保留原消息时间及内部合成标识，两种 memory 实现均复用 `from_record`；元数据不作为字段发送给 Provider，也不写入 messages/events。
- `generate_conversation_reply` 装配一个当前时间块，区分当前采样时间与本轮消息发送时间。普通重试复用，跨日、offset 变化、超过 10 分钟或时钟回拨时替换，不重复追加。写入核验的 `turn_start` 不变。
- Provider 编码前按选中的历史生成时间提醒：首条、超过 10 分钟或日期/offset 变化时添加；当前时间块已经覆盖最新消息发送时间时不再重复添加该消息提醒。
- `RequestPolicies` 用独立元信息跟随请求消息的删改和缩窗重试。旧轮时间提醒随所属轮移除；新暴露的首条历史消息补自己的时间锚点，而不是继承上一条的日期。必要证据和当前工具交换继续受保护。
- 提醒只用于定位相对时间，不是事件证据、永久记忆或定时任务承诺。历史提醒在初步 memory 选材之后生成，不作为摘要中的独立事实保存。

## Alternatives considered

### 直接在主 system 开头放每次刷新的当前时间

不采用。会扰动稳定前缀，也不能区分旧消息与当前时刻。当前块置于本轮动态上下文，历史时间另按消息关联。

### 把所有时间提醒当不可裁剪的 system 消息

不采用。旧用户轮省略后会留下失去所属消息的日期，还会永久挤占预算。独立策略元信息区分必要 system 与随轮次移除的提示，不向模型泄漏内部字段。

### 修改用户原文或存成新的聊天/事件记录

不采用。时间由应用在请求时合成，原始输入保持不变；用户不应在历史里看到额外“系统记录”。

### 依靠扩大默认模型窗口适配新增内容

不采用。提示使用简短标签并避免最新消息的重复锚点，仍完整计入预算。默认 32K 请求回归保持原上限；历史恢复测试单独配置短答案所需的 512 输出预留，验证其原本的历史恢复职责，不修改生产窗口或默认输出上限。

## Consequences

收益是模型可区分当前时间、消息发送时间与未知的事件发生时间；日期锚点在裁剪和重试后仍有正确归属。代价是请求增加少量时间文本和内部策略元信息，仍可能让本已贴近上限的请求被明确拒绝；后续 C05 继续完善选材，而非绕过预算。

验证：新增 12 项时间上下文测试和 2 项预算元信息测试，覆盖短间隔、跨日、DST、延迟处理、回拨、重复注入、缩窗、工具交换与原始数据不变；HTTP 请求测试验证时间块存在、内部元数据不外发、用户问题保持原文。全量 `cargo test --all-targets` 为 **341 passed / 2 ignored / 0 failed**，`cargo build --release` 通过，`git diff --check` 通过。保留 3 条既有测试编译 warning。

测试环境的代理曾将 localhost HTTP 转发到外部端点；重跑使用 `NO_PROXY=127.0.0.1,localhost` 与对应小写变量，仅连接临时本机服务。没有使用个人数据库或真实模型端点。公开 Rust API/schema 未改变，因此此切片不需要重生成 FRB。

**验收边界：** 工程实现与离线/本机 HTTP 测试已完成；真实模型对日期问答、按日检索和截止时间的理解尚未验收，Roadmap 的 C00a 整体验收仍保留待完成。测试通过不等同于真实模型质量达标。
