# Agent Note: 统一知识写入依据与持续维护

Status: implemented

## Problem

LLM Wiki 主链路已经存在，但对话保存丢失结构化出处，对话修订与知识提案的规则确认语义不同。长原文只读开头，来源更新缺少逐目标完成记录，后台结果不够可解释。审阅、策略重算和主题收敛仍有未完成环节，详见 [缺口核对](../../../llm-wiki-implementation-gaps.md)。

## Decision

对话写入与知识提案采用同一证据和确认契约。让对话草稿固定实际提供或历史实际引用的来源，确认时重验并原子保存正文、来源、适用条件与人工状态；无出处笔记允许保存但不伪造依据。规则修订统一显式确认语义，固定草拟时的正文、来源和元数据，拒绝过期确认。

长资料采用有覆盖记录的分块处理，复用版本缓存以控制请求成本；检索改为全文候选和命中片段，仍保留出处核验。背景任务明确输入、策略版本、进度与失败退避，对受影响页面逐一登记。审阅提供差异、修订恢复和问题处理记录；主题合并拆分先给可核对的方案，经确认后原子执行。

## Storage and runtime contract

schema v7 增加全文阅读节点、逐页面更新任务、来源任务解释字段、策略版本、提案基准状态、审阅决定、主题整理方案与替代关系、Provider 上下文窗口。读写均通过现有 Rust/FRB 路径，原始 events 和 knowledge_snapshots 不可变。

- 对话草稿固定实际选择的来源，确认时再验证；只有 URL 的项目报告不能被伪装成已继承原料的知识。
- 每 6000 字形成一个阅读块，最多四块逐层归纳；快照与策略版本确定缓存，根节点覆盖全篇。摘要明确标注 AI 归纳，逐字摘录单独核验。
- 来源更新给全部非原料知识页建 generation 任务；普通参考可自动更新，人工页准备待确认修订。来源再次变化或租约失效后旧任务不得提交。
- 来源编译和整合以 fulltext-maintenance-v2 区分旧成功记录；人工待审、拒绝和定稿依然优先。
- 段落差异采用有界 LCS；选择结果、原提案、已解决提示与实际修订 ID 一起记录。元数据及正文基准都参与过期检查。
- 主题合并限 2–8 页，拆分产出 2–8 页；每个输出最多 8 份原料和 100 个事件，整批必须覆盖所有输入依据。确认后归档旧主题，保存替代链接。
- 请求预算包含消息结构、工具 schema、参数、reasoning 和输出预留；压缩早期会话时保留说明及完整当前工具交换。当前请求本身超限则报明原因，不截断知识原料后冒充完整处理。

## Schema v8 repair and review

- 来源修复显式选择当前有效原料，复用正文提案和确认事务。生成前后及确认时核验页面、来源和知识依赖；拒绝空证据修复，普通参考的这类显式修复也需要确认。
- 刷新器每个 tick 重新评估 skipped 且仍过期的依赖，不依赖评价操作恰好发生在运行中的进程内。恢复时增加 generation，既有提案拒绝决定保留。
- `knowledge_dependencies` 保存中间知识的基准，原料仍由不可变快照表达。通过递归依赖检查使直接和间接下游待复核，并停止有效引用；检查更新提供当前上游正文与适用条件。新的派生产物和有引用的对话草稿写入依赖，v7 旧 `based_on` 产物以未知基准迁移。
- 跨页解决只接受覆盖提示全部精确来源的当前知识修订，要求用户解释如何处理分歧。历史表补提示正文、处理说明、目标页以及修改前/实际保存正文；查询按 50 条分页。
- 只读队列从当前来源、阅读状态、运行账本、刷新任务及依赖状态汇总，显示尚无运行记录的等待项。按任务计数，分页展示；刷新视图不是手动调度。

### UI review

| Before | After | Why |
| --- | --- | --- |
| 来源失效后只报错 | 原页面选择保留/替代依据并就地审阅 | 让修复操作与证据在同一处可核对 |
| 原料冲突只能忽略 | 提示下展开关联知识修订和处理说明 | 不改原料，同时保留处理责任与出处 |
| 历史只有标题和状态 | 展开原建议、选择及实际保存内容 | 可解释当时的决定，不以当前正文代替历史 |
| 只有最近运行日志 | 队列计数、状态筛选和分页 | 未开始或等待阅读的任务也能解释；不增加运行按钮 |

## Alternatives considered

- 将当前对话全部材料直接绑到每份草稿：会将没有实际采用的内容伪装成依据，拒绝。
- 只补提示词：存储契约仍有两套，必须统一确认时的确定性校验。
- 放大字符截断上限代替全文处理：仍可能漏掉尾部且成本不可控，采用分块与覆盖记录。
- 为后台任务增加人工启动或重试按钮：用户已要求自动积累，继续采用自动调度和只读状态。
- 直接自动合并重复主题：容易破坏人工判断，保留可审阅的结构调整。
- 否定来源后直接删掉来源关系而保留正文：会把不再受支持的结论伪装成有效知识，采用基于所选依据的整篇修订。
- 将旧产物绑定当前上游版本：没有证据证明它基于这一版本生成，迁移保留未知并请求复核。
- 任意修订均可解决任意提示：会产生虚假的处理关联，仅接受覆盖全部提示依据的当前修订。

## Validation

首版 v7 的历史验证：

- Rust 全量回归 305 项通过；额外的现有数据副本迁移测试通过。
- Flutter 全量 215 项通过，含真实 Bridge 的来源版本、规则确认、差异与恢复、后台状态验证。
- Linux release 构建通过。桥接生成脚本为 libclang 提供完整资源头，同时隔离 C 编译器的 CPATH，避免 stddef.h 缺失造成半成品绑定。
- 当前个人库仅做只读统计并备份到临时目录。副本由 v5 升到 v7，104 条原始事件、32 份原料快照正文逐条一致，integrity_check 为 ok；没有外部模型调用。

v8 本次验证：Rust 全量 312 项通过；默认忽略的现有数据副本测试单独通过，v7→v8 保留 104 条事件和 32 份快照正文。Flutter 全量 219 项通过，含四项新交互测试及扩展的隔离真实 Bridge。Rust 与 Linux release 构建通过；全量 Flutter analyze 无 error，77 条既有 info/warning。测试没有调用真实外部模型，也没有修改个人原库。

## Consequences

再次审查发现的 R01–R06 已补充实现，具体行为见 [缺口核对](../../../llm-wiki-implementation-gaps.md)。历史上缺少中间知识版本的旧产物需要复核；没有明确依赖关系的旧页面不能通过猜测补齐。上游被归档或依据失效时须先处理上游，不将旧产物自动判为有效。

全文处理与逐目标维护增加模型调用；分段缓存、策略版本和失败退避降低重复成本。所有原文块进入阅读不代表模型归纳必然保留所有细节，真实材料的尾部条件、反例、召回和冲突提示仍要评分。

审阅保留明确边界：来源发生变化的提案必须完整确认；历史恢复恢复正文，并重新确认当前出处及适用条件，不倒退原料版本或规则强度。共享主题合并/拆分必须由用户预览确认，旧主题归档并保留关联，原文不变。

预算在 Provider 请求边界统一处理。识别的模型使用本地 BPE；未知模型采用 UTF-8 字节数的保守估算，可能过早拒绝，应按实际 Provider 设置窗口。序列化请求计数加安全余量仍不等同中转内部计数；只有明确 context_length_exceeded 会缩小本次预算重试一次，不自动改写用户的配置。保留用户的输入预算提案原文件。
