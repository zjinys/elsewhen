# Agent Note: 最终上下文预算与历史压缩

Status: implemented

## Problem

`SlidingWindowMemory` 只在读取已落库消息时限制 token。知识页正文、规则、工具结果等动态 system 消息随后追加，导致配置为 4096 的上下文实际发送到 provider 时可超过 6700 token。历史过长时，模型可能响应异常或上下文超限，而调用层缺少稳定的最终预算边界。

## Decision

在首次模型调用前、动态上下文注入完成后，再按 `MemoryType::SlidingWindow` 的预算压缩一次。第一条 system 消息（基础指令、工具协议及其中拼接的个人规则等）原样保留，最近的用户问题也原样保留。后续 system 消息是知识页、直查数据等动态资料，最多占其余估算预算的一半，过长时截取开头；较早对话按时间顺序拼成带标记的有限摘录，最近对话尽量原样保留。这里的“摘录”不是模型生成的语义摘要。

## Alternatives considered

- 只提高 token 上限：不能解决不同 provider 的上下文差异，也会持续增加请求成本。
- 直接丢弃最早消息：实现简单，但会静默丢失决策背景，且中间历史可能比最早历史更重要。
- 每轮调用模型生成摘要并持久化：摘要质量更高，但增加额外模型调用、失败路径和数据库迁移；当前先采用确定性的本地压缩，后续可在需要时增加持久化摘要。

## Consequences

首次请求中的动态资料和旧历史受估算预算约束，基础提示词和当前问题不会被压缩；代价是长知识页可能只留下开头，早期对话摘录也可能不完整。估算采用字符数除以四，并非模型 tokenizer；基础提示词加当前问题超过预算时仍保留两者，因此不保证硬上限。工具调用产生的后续轮次目前不在这次压缩边界内，也不能宣称所有请求都有严格预算。压缩不新增 provider 调用，质量低于模型生成的语义摘要。
