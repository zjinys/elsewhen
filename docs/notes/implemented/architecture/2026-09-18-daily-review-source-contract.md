# Agent Note: 每日回顾版本与来源契约

Status: implemented

## Problem

每日回顾会随 Prompt、模型和用户修订变化。如果只在日期上保存一段可覆盖文本，后续无法判断结论来自哪些记录，也无法在重算后保留历史结果。界面尚未形成稳定场景，数据层仍需先提供无 AI 可用的事实降级路径。

## Decision

每日回顾使用 `daily_reviews` 追加版本，不覆盖同一天的旧版本。每个版本记录日期、Prompt 版本、结构化 JSON 和创建时间；`daily_review_sources` 显式连接该版本与原始事件。

`daily-review-v1` 将内容分为做过的事、想法与决定、人物与项目、后续行动。每条结论必须包含非空文本及至少一个 `source_event_ids`，且引用只能来自该回顾版本声明的来源集合。存储层进一步要求所有来源事件属于目标本地日期。

`get_daily_overview` 始终返回当天事实列表；没有 Provider 或尚未生成回顾时，`review` 为 `None`。存在回顾时只返回通过 schema 与来源校验的最新版本。当前不向 Flutter 开放任意回顾写入接口，生成器和用户修订流程必须在后续确定写入边界后复用同一存储方法。

## Alternatives considered

- 在事件或日期记录上覆盖一段 Markdown：实现简单，但失去版本历史和逐条来源，无法可靠重算。
- 只把来源 ID 放进 JSON：读取方便，但数据库无法维护事件引用关系，也难以验证跨日期来源。
- 先做 Today 页面再补数据结构：能更快看到界面，但会让尚未明确的布局反向固化不可靠的数据契约。

## Consequences

收益是每日回顾可重算、可追溯，并能在无 AI 时退化为事实列表；原始事件始终不被修改。代价是每次生成会增加一个版本和来源关联行，后续需要明确历史版本清理策略，并为用户修订增加独立类型或修订字段。
