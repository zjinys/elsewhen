# Agent Note: 安全轮边界的显式补充

Status: implemented

## Problem

生成期间的输入已经可以保存和排队，但用户还需要明确要求正在进行的任务改变范围。直接读最新消息会破坏 run 的输入截止点；只在内存标记已采纳会在重启后重复生成，附件只取文本还会丢失上下文。

## Decision

对应[对话路线 C09](../../../roadmap/2026-09-30-ai-chat-experience-roadmap.md)。补充由用户单独选择，绑定已保存输入、目标 run、输入内容基底和上下文信封。仅在完整工具交换结束后、下一次模型请求之前做预算预检，事务内重新核验取消、撤回和版本，然后将队列消费与不含正文的注入回执共同提交。实际请求仍过 provider 最终预算闸门。

普通输入从不隐式转成补充。预算不足或不可合并材料保留队列资格及原材料；停止冻结派发。注入回执仅证明加入下一请求上下文，不证明模型已经理解、网络送达或执行业务。恢复保留此区别，显式重试原任务可读取原有补充，不把补充再次当独立输入派发。两入口显示待补充、未能补充和已加入上下文的不同状态。

## Alternatives considered

- 每次请求读取最新用户消息：破坏固定截止点，也把记录和下一问误作当前任务要求。
- 收到补充立刻取消并重启：会重复工具与输出，不能解释已完成操作。
- 消费与回执分别提交：崩溃窗口使同一条输入既注入又排队。
- 将所有信封降成纯文本：无声丢失附件或页面版本，不采用。
- 注入后允许作为独立输入启动：使一条输入被两次消费，不采用。

## Verification

真实工具轮后的下一请求包含补充，普通回复不注入。撤回、取消、崩溃事务回滚、输入修改、预算拒绝和附件均保留明确状态。注入不执行草稿；原提议仍需版本审阅。两个入口在隔离 Bridge 和 widget 测试中可操作；真实模型指令遵从独立评价。

## 集成边界（2026-10-02）

- 目标完成、失败、取消或租约恢复为中断时，仍未消费的补充保留 `pending`，与终态同事务记录 `target_closed` 并暂停队列。继续必须明确授权；已注入和已撤回项不回到队列，附件/输入/材料变化的具体原因保留。否则界面会永远等待一个已经结束的工具轮，或在用户理解为补充原任务时自动启动下一问。
- 知识页补充仅在其持久 `task_json` 与目标输入完全相同时允许只注入新文字，页面、修订和选区均不丢失。不同任务或缺少旧任务基底时记为 `context_changed` 并保留下一问资格；入队与消费事务均复核。不采用“只要同一 slug 就合并”，因为同页不同版本或选区仍是不同材料。
- `chat_supplements` 存储与工具轮定向回归：10 passed / 1 ignored / 0 failed。覆盖四类终态、显式继续、已消费/撤回项不复活、终态提交失败回滚、相同/不同/legacy 页面任务与预检后任务变化。只使用临时数据库。
- 新增 `acceptance_controls.rs` 两项显式 ignored 验收：真实模型读工具后的双入口范围补充；实际正文流中取消、重开库保持队列冻结、使用原输入显式重试。与 `acceptance_workflows.rs` 一并使用现有 `PageTask`/`save_page_task_input` 契约。2026-10-03 双入口真实补充已通过，当前全量 Rust/Flutter 集成门禁通过；具体请求、用量与质量边界见路线图完成记录。

## Consequences

网络发送与 SQLite 无法原子提交，因此回执不承诺送达。辅助上下文可能使更小窗口的后备 provider 拒绝请求；不能以裁剪补充来掩盖。首版无法安全合并的附件仍需用户另行处理。
