# Agent Note: 对话提议绑定具体版本与执行回执

Status: implemented

## Problem

聊天生成原先会把会话最后一条短回复识别为确认，然后执行该会话全部待确认操作或转正全部规则。审批意图没有绑定具体提议，短句前缀还可能把含否定意思的输入识别为肯定。旧草稿预览只携带 ID，也无法保证接受的内容就是刚显示的版本。

本切片落实 [AI 对话体验方案](../../proposed/architecture/2026-09-30-ai-chat-experience.md)与 [Roadmap C01](../../../roadmap/2026-09-30-ai-chat-experience-roadmap.md)，覆盖主对话、知识页对话、知识草稿兼容入口及历史未归属规则。

## Decision

### 明确审阅，而非聊天关键词授权

- `api/chat_proposals.rs` 提供按会话分页列出提议/处理记录、编辑具体版本、接受或拒绝具体版本的业务接口。
- 审阅请求携带提议种类、ID、会话、版本和目标依据 token；token 绑定提议内容与当时的目标身份/版本，不是模型可使用的写权限工具。
- `pending_actions` 和 `rules` 增加 `review_version`。数据库触发器使内容编辑和改回原内容均递增版本，旧授权不能重新生效。
- 聊天生成只读取有界审阅上下文，不执行或删除待审提议。普通“好”“嗯”、否定句与进度追问均不批准积压动作。确认分类器只用于解释对话，不授予写权限。
- 旧知识草稿 FRB 接口也要求已显示的版本/token，不能在点击保存时重新读一个新 token 并绑定到旧显示内容。

### 目标校验与本地写入同事务

确认先持久化唯一 claim；实际写入时重新核验审阅目标，关闭 claim 提交后到执行之间的竞态窗口。

待办、规则、知识草稿、页内修订/派生、改名、联系人关系、归档和已抓取 URL 内容导入，在同一个本地事务内完成目标校验、业务写入与成功回执。相关存储函数可参与调用方拥有的事务，单独调用时仍自行开启并提交事务。改名和派生产物的初始读取也移到写事务内。

失败并确认整体回滚时记录 `failed`，不把它说成部分成功。目录导入及历史 `record_event` 动作继续使用各自既有提交边界；无法确认全部提交结果时记录 `uncertain`，保留操作快照并要求核对，不自动重放。

### 联系人消歧与来源保护

- token 包含 `from_slug` / `to_slug`，以及按名称/别名查到的候选身份集合和页面版本。匹配集合变化同样使旧审阅失效。
- 明确选中的 slug 失效时拒绝执行，不按名称静默换成另一个实体。
- 编辑白名单按动作定义；联系人关系允许修改用于消歧的 people/relations，仍禁止修改 `source_event_id` 等来源身份。
- 人物、目标与关系的组合写入具有共同事务；后续步骤失败不留下前面新建的半批页面。

### 执行所有权与恢复

`chat_proposal_decisions` 保存动作快照、决定、版本/token、状态和回执；同一决定的重复请求返回原回执，不重复执行业务操作。

执行 claim 有进程身份和五分钟租约，独立心跳在执行期间续约。重复 bridge 初始化及另一个活进程的未过期 claim 不被恢复逻辑抢占。只有过期 claim 才转为 `uncertain`；完成写回检查执行者、有效租约与预期状态，并检查实际更新行数，迟到结果不能改写已失效回执。

异常退出后不承诺立刻判断执行结果：租约到期前可能显示等待回执，到期后在启动或查询/确认边界收敛为待核实。它不等价于模型生成任务的完整恢复；C02 另行实现 run 生命周期。

### 共用审阅界面

`chat_proposal_review.dart` 用同一个组件承载主对话和知识页提议：查看完整正文、参数/来源与目标版本，编辑后先返回新预览，再独立接受或拒绝。

用户可以显式选中多个提议后审阅。批量执行是逐项操作，不是整批原子事务；界面预先说明部分成功的可能，并分别呈现成功、失败、拒绝及待核实结果。未选中的提议不参与。

历史未归属规则只在 Settings 的专门入口审阅，不自动归入当前会话。坏格式提议仍可显示和拒绝，不阻塞其他提议，也不能直接接受。

## Alternatives considered

### 扩充确认词表或只加一个过期时间

不采用。短句语义仍然歧义，也没有动作绑定。时效不是版本确认的替代品。

### 点击时加载最新提议并执行

不采用。会把新版本的授权附到旧预览上。目标或内容变化时请求失败，用户重新打开审阅，而不是自动重试最新版本。

### 仅在领取 claim 时检查目标

不采用。领取事务提交后仍可能发生人工改动；实际业务事务必须再次核验，知识写入仍沿用现有证据和保护验证。

### 所有失败都直接重试

不采用。断线或进程退出不能证明业务没有提交。已成功返回回执，明确回滚与无法确定分别展示；不确定的操作先核对。

### 第一版要求整批原子确认或挂起模型等待人工

不采用。用户决定可以跨多种业务动作，目录导入还包含自己的分批边界。逐项版本授权、逐项回执更清楚；草稿独立持久化，模型不需要一直占着请求等待用户。

## Consequences

收益是用户批准的内容、版本和副作用范围明确；原文和已有人工修改不会因为模糊回复或迟到授权被覆盖。代价是用户需要操作审阅卡，已处理但失败的提议需查看记录后重新草拟；不能继续依赖旧“回复好就保存”的交互。

验证覆盖：版本编辑与回退、跨会话、重复和并发确认、确认后目标改变、联系人名称解析变化、失效显式 slug、编辑白名单、坏格式提议、健康租约与失效完成、v9 迁移保留原消息和未批准草稿。完整 Rust 回归 354 passed / 3 ignored / 0 failed；Flutter 新审阅与旧知识草稿 10 项 widget 回归通过；隔离真实 Bridge 覆盖两个对话入口、规则、编辑失效、重复确认和旧草稿兼容接口。旧连续性桥接用例已改为先验证“好”不执行，再明确接受具体提议；完整 Flutter 233 项通过。

`fvm flutter analyze` 已运行，没有编译错误，但未修改的页详情和设置测试文件仍有 4 条既有 warning，因此全量静态检查退出码为 1，没有将它记为全绿。

`scripts/regen.sh` 已运行，生成绑定与 release 动态库一致；测试使用临时数据库和 loopback HTTP，不访问个人记录或真实模型。真实模型质量、生成取消/恢复及工具进度不由这组测试证明，继续按 C02–C09 和阶段出口独立验收。
