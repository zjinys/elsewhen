# Agent Note: 原料与知识产出的同页工作流

Status: implemented

## Problem

原料提炼的来源版本已保存，但关联区和产出区只读取旧的 based_on 字段；采纳后直接跳转到近似标题的新页，造成原文被替换的错觉。提炼与审阅主要依赖逐页操作和多层弹窗，不能承担日常知识积累。

## Decision

按用户确认的默认行为，已保存原料由后台自动整理为参考知识，原文保留；升级个人规则仍需显式确认。复用持久化后台运行记录，以来源版本去重、10 分钟租约恢复、指数退避（五次失败后冷却 6 小时），每次只处理一份原料。失败冷却在选取候选前过滤，不阻塞后续新材料。尊重人工编辑、人工设置的适用条件与强度、已拒绝建议，不自动采用用户正在审阅的建议。v5 迁移增加提案 origin，旧提案均保留 manual 身份；后台只应用自己生成的 automatic 提案。

页面按原文/内容、产出、关联、来源与修订组织；建议、来源对照、历史在页面内展开。采纳后停留当前原料，结果有类型标记和双向来源入口。关联从已存在的快照关系查询，旧提炼页无需再次生成就能找回来源。

后续 [参考知识自动保存与跨来源维护](2026-09-29-wiki-automatic-integration.md) 统一按需提炼的新参考产出自动保存，增加共享主题和带证据的内容检查；本页记录的原文保护与工作区组织继续有效。

生成严格校验结构与内容，格式不合法时仅修复一次，失败不保存半成品；每次响应在校验前记录上游用量。比较版本在模型调用前固定，不能接受生成期间新增的人工编辑。历史首次报错缺少错误轨迹，不能把修复方向当作历史根因。现有数据库一致性副本确认 IP 原料和已采纳方法分别存在，方法引用原料 v1；关联直接来自快照，不依赖 based_on。

## Alternatives considered

- 每份材料都人工点击并确认：用户明确否定，无法作为默认积累方式。
- 直接覆盖原料或自动升级规则：混淆原文与推论，也改变了用户确认边界。
- 复制来源关系到旧 based_on：不能表达多个来源和历史版本，会产生两个关系真源。
- 新建一套独立任务框架：现有后台运行记录已有租约与重试所需字段，优先复用。

## Verification

- 历史方法页可从原料产出区找到并反向打开来源，采纳不跳走、不改原文。
- 无人工点击也能后台生成参考知识；重启、重复 tick、失败、来源变动和人工保护有隔离回归。
- 规则升级保留确认，后台不调用公开确认端点，不自动接受人工待审建议。
- 操作按钮等高、垂直居中、均有图标；页内提炼和审阅无需嵌套弹窗。
- Rust 全量 277 项、Flutter 全量 212 项通过；真实 Bridge 覆盖默认自动整理、每版本去重、来源双向导航。静态检查无 error，保留既有 77 条 info/warning。
- 页内测试覆盖原位采纳、展开原料对照、提炼失败重试和按钮对齐。实际数据副本查询验证了 IP 原料 → 既有方法 → 原料 v1 的关系；未调用真实外部模型。
- 代码：[后台整理](../../../../src/knowledge_background/sources.rs)、[提案应用与来源关系](../../../../src/storage/knowledge.rs)、[页面工作区](../../../../ui/lib/widgets/knowledge_panel.dart)。操作验证见 [现有数据测试指南](../../../testing/llm-wiki-real-world-testing.md)。

## Consequences

默认自动整理减少逐页操作，但会增加模型调用；旧原料也按版本处理。每版本去重、有界输入和失败退避控制消耗，用户确认前不会成为个人规则。自动参考知识仍可能有理解偏差，适用性要用现有材料做真实模型评估；未覆盖的长原文部分不能据此宣称已完整理解。原始来源与人工定稿保留，可核对和纠错。
