# Agent Note: Linux debug 内存分类与源码持有路径验证

Status: implemented

## Problem

用户对窗口打开和隐藏到托盘分别做了 20 秒采样，观察到 debug 进程仍驻留数百 MiB。总 RSS 不能说明这些内存来自业务缓存、Dart 调试运行时还是原生分配，需先分类，再决定优化方向。仅凭 RSS 偏高就判断正式产品的业务内存偏高，证据不足。

## Decision

对用户正在运行的 Linux debug 进程进行诊断，不修改生产代码、不重启用户窗口、不读取个人数据库正文。使用本机 Dart VM Service 的 `getProcessMemoryUsage`、`getMemoryUsage`、`getAllocationProfile`、`getInstances`、`getObject` 和 `getRetainingPath`，配合 `/proc/<pid>/smaps` 分类。输出仅保留类型、字节数、数量、长度和引用路径元数据；不展示或保存字符串文本，也不生成完整堆转储。VM 端点的认证信息不写入仓库。

分析期间应用多次重启，各进程分开记录。最终主堆、图片缓存及字符串引用路径来自同一个 debug 进程；另一个进程的一次 GC 对照单独保留，不能和最终进程做前后差值。原始统计 JSON 只保存在 `/tmp`，本记录保留方法与结论。

## Verification

- 最终 Dart 主 isolate 堆使用约 **207.38 MiB**，容量约 **225.80 MiB**。VM 内存树在随后请求中略有变化，服务端序列化和诊断本身也会临时分配内存，不能将相邻请求视为同一冻结快照。
- 主堆内两类字符串合计约 **93.29 MiB**；普通 `_List` 约 **28.72 MiB**。`Instructions`、`Function`、`ICData`、`Code`、`Class` 等显式 VM 代码与元数据类合计至少约 **57.38 MiB**。这些是主堆的内部分类，不能与主堆总量重复相加，也不能把列表和字符串全部归为聊天数据。
- 在最终进程中枚举双字节字符串、对单字节字符串做有界采样，再各选取样本内最大的四条检查引用路径。**八条均由 `@Script.source_` 持有**，路径包含 `loaded_scripts_`、`libraries_cache_` 或代码对象。此结果证明大字符串中存在明确的源码调试数据；它不证明所有 93 MiB 字符串都属于源码，也不是业务正文的保留大小测量。
- `kernel_blob.bin` 在活跃采样时实际 RSS 约 **135.57 MiB**，通过 VM 内存树和 Linux smaps 交叉核对。另一进程闲置时此文件映射的 RSS 曾降至约 2.4 MiB，说明文件驻留页会回收；不能将其文件大小当作固定常驻成本，更不能承诺 release 必然等量减少。
- VM Profiler 约 **18.77 MiB**、Timeline 约 **3.52 MiB**，VM Service 堆容量约 **13.64 MiB**。这些与业务主堆分别记录，仍需注意容量与实际常驻页口径不同。
- 最终进程的 Flutter `ImageCache` 已完成、待加载、live 条目数及 `_currentSizeBytes` 均为 **0**。这排除了该时刻标准图片缓存为大头，但不代表引擎绘制表面、驱动分配或显存占用为零。
- Linux `[heap]` 映射实际 RSS 约 **102.04 MiB**，其余匿名映射还包含 Dart、原生分配和图形相关内存。没有原生分配栈证据，不能将这些内存直接记在 Rust、SQLite 或 Flutter 任意一方名下。Rust 动态库文件映射大小也不等于 Rust 堆占用。
- 在另一个独立进程中请求一次 GC 后，主堆仍在约 207 MiB 量级，未出现显著收缩。这不构成泄漏证明；缓存、源码和运行时元数据仍被正常持有也会产生同样现象。

## Alternatives considered

- 仅用 RSS 或 RSS 下降判断释放：文件页驻留和 Swap 都会变化，且分析期间有进程重启，无法据此定位所有权或比较同一生命周期。
- 将全部开销归咎于 debug：已有源码和 VM 元数据的明确证据，但尚未获得 release 同条件对照，也未拆分原生分配栈，不能承诺固定降幅。
- 先清理图片缓存、聊天缓存或重建隐藏窗口：标准图片缓存当前为空，大字符串样本指向源码；没有证据支持先改业务逻辑。
- 保存完整堆转储或输出字符串内容：会包含不必要的私人正文，分类和引用路径元数据已经能支持当前判断。

## Consequences

本轮确认 debug 源码、代码元数据和调试服务是明确的大项，不能把数百 MiB 全部解释为聊天、知识或图片缓存。后续产品态基线应采用同数据、同页面、相同等待条件的 release 对照；如果原生占用仍高，再以原生分配采样区分 Rust、数据库、引擎和驱动。

代价是 VM 类分配统计和引用路径扫描会短时分配内存、触及冷页并影响 RSS，因此本次剖析结果用于分类，不代替此前 20 秒空闲采样，也不用于推断长期增长或泄漏。没有为本次测试增加任何常驻诊断、后台轮询或生产缓存清理。
