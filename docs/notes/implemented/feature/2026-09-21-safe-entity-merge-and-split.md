# Agent Note: 安全实体合并与拆分

Status: implemented

## Problem

同名人物、重复项目或主题需要由用户合并，但实体事实、别名、关系和关联待办都可能引用旧实体。直接改 slug 无法解释迁移历史，也无法在合并错误时安全恢复；粗暴撤销又可能覆盖合并后新增或人工修改的数据。

## Decision

实体合并只接受用户从同类型真实知识页中选择的目标。事务在写入前验证来源、目标、类型和活跃状态，并把来源实体涉及的事实、别名、关系和关联待办按原始行 ID 保存到 `entity_merge_snapshots`。重复事实、别名和关系先标记为 `deduplicated`，其余行迁移到目标实体；来源页保留并标记为 `merged`，原始事件从不修改。

撤销合并逐行核对目标侧数据是否仍与快照一致。完全一致时，事务恢复迁移行和去重行、待办引用及来源页状态，并为审计记录写入 `undone_at`。任一迁移行被修改或删除时，整笔撤销拒绝并回滚，避免覆盖合并后的新事实。撤销后允许再次合并，同时保留每一次历史记录。

Flutter 实体详情页只列出同类型、未合并的目标实体。旧实体页显示合并目标、目标页入口和撤销操作；目标页与旧页的事实、别名、关系和待办 provider 在操作后立即失效重载。实体页同时展示由 `related_wiki_slug` 关联的待办，并允许直接完成或恢复。

## AI authority boundary

AI 分析、普通文本识别以及 `@/#` 确定性标注都只能生成候选。确认、忽略、同名消歧、合并、拆分和事实纠正均由用户在应用界面触发；候选不得自动写入长期实体记忆。

## Alternatives considered

- 删除旧实体页：会破坏历史链接和人工解释路径，因此保留旧页并显示合并状态。
- 只记录来源和目标 slug：无法区分本次迁移数据与目标实体后来新增的数据，因此保存逐行快照。
- 撤销时把目标实体全部搬回来源：会误伤目标原有和合并后新增内容，因此只处理快照中的行，并在变化时原子拒绝。
- 用自由文本输入目标 slug：容易产生不存在或类型错误的目标，因此界面只允许选择真实的同类型页面。

## Consequences

用户可以从知识页完成可解释的合并、目标回看和安全撤销，相关事实、关系、别名和待办引用保持一致，原始事件持续作为不可变来源。代价是撤销采取保守策略：一旦迁移内容后来被修改，用户必须先人工处理冲突，系统不会猜测如何拆分。

隔离验证覆盖正常迁移与恢复、重复项去重、再次合并、无效目标拒绝、合并后修改导致原子拒绝、事件保留和 Flutter Bridge 往返。
