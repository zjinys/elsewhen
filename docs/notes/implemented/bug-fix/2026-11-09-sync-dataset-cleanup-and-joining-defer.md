# Agent Note: 旧数据集副本清理与加入期业务消息等待

Status: implemented

## Problem

同步重加入坚持创建唯一目录，已经 ready、后来退出或不再选中的副本缺少清理入口（D6）。清理时“下次启动选中”与“当前进程使用”可能不同。只查 catalog 的 selected_id 会删除仍被打开的 SQLite/WAL。原有放弃入口只处理 staging，不能扩大为删除任意副本。

加入端先钉住经配对批准的 owner，随后安装其签名名册。两步之间提前到达的 op/provider 业务消息被普通成员门禁拒收，进入三次拒绝后的 drop。原 snapshot-start 的早退又在完整验证之前（D7）。

## Decision

清理只处理 ready、非当前进程、非下次启动选中的副本。预览绑定 catalog 修订和文件清单摘要；确认时重验。默认库和 staging 不进入清理。路径按 UUID 定位，拒绝目录树里的符号链接。每个被进程 pin 的导入副本持有共享文件锁，跨进程清理必须拿到独占锁；选择下一次启动的数据集不释放当前使用锁。清理还需要独占工作区同步锁，用户需先锁定同步并结束占用它的加入会话。

安装目录的 catalog 从 v1 迁移为 v2，独立于业务数据库 schema。确认先原子写入 dataset_cleanup_jobs、移除目录条目并推进修订，再删除文件。崩溃或删除失败留下已确认待办，绝不会让残缺目录重新成为可选数据库。安装身份一直保留到文件与系统密钥均清理完成。Dart 只删除 Rust 返回的已提交待办对应的安装密钥和修订记录，读取确认删除后再确认完成。密钥失败时可跨重启继续，其他安装密钥、远端数据和成员名册不受影响。

加入期的等待只对 op-（包含分片）、provider:、snapshot-start: 开放，且本机必须尚未装过首份签名名册、尚未激活、发送方和公钥精确匹配配对钉住的 owner。数据集、发送方、接收方、密钥版本、签名和密文验证全部成功后才返回 Waiting。普通收信与 enrollment 收信共用此结果；Waiting 不 ack、不进入拒绝计数、不 drop。名册控制照常推进，安装后回到既有处理路径；初始快照未发布时的业务等待仍生效。已有签名名册的已撤销成员不会被重新判为首次加入。

## Validation

工程与变异结果以[同步生命周期路线 C13–C17](../../../roadmap/2026-10-27-sync-lifecycle-boundaries-roadmap.md#2026-11-09-d6d7实施批次)为准；[人工测试步骤](../../../testing/2026-11-10-sync-d6-d7-manual-test.md)区分自动验证和两端真人验收。测试全部使用临时工作区、合成身份/密钥与 loopback relay，未操作个人数据。

## Alternatives considered

- 自动删除未选中目录：可能误删当前进程或另一进程正在使用的副本，也丢失用户未同步的数据。
- 复用同 dataset_id 的旧目录：破坏新加入永不收养旧目录的边界。
- 文件删除后才登记，或密钥失败后仍宣布完成：崩溃会留下不可恢复的半库或无法重试的安装密钥。
- 吞掉所有 sync_local_membership_inactive：会把撤销、陌生人及错误签名也变为永久等待。
- 在验证前直接等待所有业务前缀：不可信信封可以借前缀逃过验证。

## Consequences

用户能够显式释放旧副本空间，并能识别与继续中断清理；当前数据路径和业务原文保持稳定。catalog v2 会让只认识 v1 的旧构建拒绝打开该安装目录，回退需要匹配版本的整份备份。进程使用锁要求占用副本的进程运行支持此锁的构建，升级前应退出旧版实例。代价是小型持久清理表、每个导入副本的使用锁文件，以及跨 Rust/系统密钥存储的两步确认。无法把文件和 OS 密钥操作合并成单一原子事务，因此待办恢复是必要契约。已被旧版本 drop 的历史业务消息不会由这次修复自动恢复；真实设备的到达时序和系统密钥平台行为仍需人工验收。
