# Agent Note: 空回复根因调查与代码复核

Status: implemented

## Problem

页内会话先给出未来动作预告，随后出现两次空回复兜底。历史用量有非零生成消耗，但缺少逐请求轨迹，需要区分真实故障原因、程序可复现缺陷和仍待验证的假设。

## Decision

> **2026-09-29 复核结论：历史空回复的确切原因仍未确定。** 下文第二轮原始调查中的“工具被拒烧完四轮”链条不符合当前确认流程；`token_usage` 是多轮累计值，不能直接用于算单请求预算偏差。已在隔离环境复现中间正文丢失、成功工具轮数耗尽后仍为空，以及兼容重试漏记用量。详见文末“复核结果与优化顺序”；原调查保留作推理记录，其中被复核推翻的解释不再作为实施依据。

**当前状态**：历史故障的逐请求原因仍未确定；本次已修复可复现的收尾缺失、空头承诺放行、短追问断链和原生工具正文丢失。此前三处修复见
[backlog 的断链节](2026-09-26-deep-review-remaining-todo.md#对话断链空头承诺被当成最终答案2026-09-29已实现)。下方“触发”至“待办”保留第二轮调查当时的推断，准确性以“复核结果与优化顺序”和本节当前实现为准。

### 本次落地：交付结果与任务连续性

用户可见的契约是：本轮交付成果、展示待确认草稿，或说明原任务实际未完成；不能以“我去做，一会给你回复”结束。用户发 `？`、`搞定了吗` 等短追问时，从同一会话的持久化消息恢复上一项实质要求，回应它的进度；不能只报告模型空回复或要求重发已有任务。

- 工具循环仍最多四轮，最后一轮只组织答复，运行时禁止原生和文本协议派发新工具。重复预告、空回复或无信息错误话术会提前进入收尾；收尾仍失败时，按实际工具结果、确认执行结果和待确认草稿生成可读答复，不再返回未核验的 `last_raw`。
- 原生 assistant 的正文、tool_calls 和必要的 reasoning 字段原样回传下一轮。正文帮助模型继续完成任务；推理字段不展示给用户，中间预告也不直接当成最终成果。
- 短追问跨旧失败消息和应用重启恢复原要求；恢复信息在记忆压缩后追加，仍受每轮字符上限约束。未完成请求使用原要求检索。已完成答复或已有待确认操作时仅允许查询；问号不会确认保存、重复创建草稿或通过工具记录成新事件。已保存声明按原要求时间核对数据库；已取消任务和新话题不恢复旧工作。
- 页内提示按原料/派生产物与可编辑知识区分允许动作。受保护页的非法 revision 在草拟时即拒绝，并提示生成 derivative；确认执行仍保留校验，原文不被覆盖。
- 兼容重试替换响应前累计首次请求用量；只有 reasoning 的响应不再直接判为工具协议不支持。逐请求持久化诊断、finish_reason 和完整请求 token 预算尚未实现。

代码与可重复场景见 [连续性与兜底](../../../../src/ai/conversation/continuity.rs)、[Rust 回归](../../../../src/ai/conversation/continuity_tests.rs) 和 [真实 Bridge 回归](../../../../ui/test/conversation_continuity_bridge_test.dart)。测试使用临时数据库和脚本化 HTTP Provider，不读取个人数据库或调用外部模型。

验证：`cargo test --all-targets` **260 项通过**，`cargo build --release` 通过；新增连续性、既有知识来源和基础 Bridge 三组真实桥接测试 **3 项通过**。覆盖持续预告 → 未完成答复 → 问号接回原要求，以及空回复时展示草稿 → 问进度不保存 → 明确确认后只保存一次。现有真实模型的历史故障重放尚未验收。

### 原调查当时提出的三个判断（后文已有复核纠正）

1. 记忆压缩层与空回复**无因果**，已用真实数据排除；
2. 但记忆层**另有一个真缺陷**——4096 的 token 预算形同虚设，请求稳定超支 1/3；
3. 空回复的机制线索指向一条**上一轮修复完全没覆盖**的代码路径。

## 触发：一句我上一轮没测过的反问

上一轮我把「上游返回空」写进文档时标的是「未能确证，不猜」——理由是
`debug_eprintln!` 不落盘、工具调用不持久化，无证可查。用户不接受这个「查不出来」，
直接给了个我没排除过的具体假设：**记忆层**。

这个质疑是对的，因为它指向的是**本仓库自己写的、会改写请求体的代码**
（`SlidingWindowMemory` + `compress_context`），而我上一轮压根没量过上下文体积，
只凭「上游返回空」就把它当成了外部问题。

**教训：把机制缺失归给外部之前，先量自己这侧的实际输入。**

## 结论一：记忆压缩层是清白的

`compress_context(&mut context, 4096)` 判 `est_before = 3820 ≤ 4096`，**直接 return，
一条消息都没裁**（`dropped_msgs = 0`）。

对话本身也极小——最长的一条是用户贴的英文 prompt，1891 字符 ≈ 472 估算 token；
页面正文（`note-106bf538` 的 `content_md`）只有 580 字符。

**压缩层在这场对话里从未生效，因此不可能是空回复的成因。** 这条不是推理，是量出来的。

---

## 结论二：但记忆层确实有个真 bug——4096 的预算形同虚设

量到估算值之后第一件事是去查**真实的** `prompt_tokens`。`token_usage` 表记的是
provider 自己上报的数字，属于地面真值，不需要我估：

| 时间 | 估算 | **provider 实收** | 预算 | 超出 |
|---|---|---|---|---|
| 02:13:32 | ~4300 | **7254** | 4096 | +77% |
| 02:15:31 | 3820 | **5452** | 4096 | **+33%** |
| 02:16:45 | 3820 | **5497** | 4096 | +34% |

根因在 `estimate_tokens`（`memory.rs:269`）：

```rust
ascii / 4 + wide / 2
```

系统提示 7082 字符里绝大多数是中文，真实 tokenizer 下汉字约 1 字 1 token，代码按
2 字 1 token 算——**单是系统提示就少算约 1300**。实测低估比 **1.43×**（5452 / 3820）。

代码注释里承认了「2× 低估是可接受的折中」，所以 1.43× 落在自认容忍范围内。**但后果
是结构性的**：

- 估算永远够不到 4096 → `compress_context` 永远提前 return；
- 每次请求实际都比预算**多带三分之一**的 token；
- 而系统提示单独就占掉估算预算的 **74%**（3043 / 4096），留给真实对话的余量极小。

也就是说，**这个预算是软的，从来没真正约束过任何东西**。它现在的作用仅止于
「上下文大到离谱时兜个底」。

附带查到：全部 5 个 provider 配置的 `max_tokens` **都是 NULL**，所以请求根本不带
输出上限——输出侧也完全没设防。

**这个缺陷与空回复无因果**（超预算不等于返回空），但它是真的，且会放大其他症状。

## 结论三：空回复的线索不在「上游返回空」

同一张 `token_usage` 表还记了 `completion_tokens`：

| 时间 | prompt | **completion** | 用户实际看到的 |
|---|---|---|---|
| 02:13:32 | 7254 | **611** | 那句「稍等片刻」（129 字符） |
| 02:15:31 | 5452 | **218** | 「抱歉，模型没有返回内容」（18 字符） |
| 02:16:45 | 5497 | **104** | 同上 |

**`completion_tokens` 是 218 和 104，不是 0。** 而入库的兜底只有 18 字符（≈9 token）。

且代码路径排除了「正文被解析器吃掉」的可能：循环末尾有
`if content.is_empty() { content = parse_tool_call_envelope(&last_raw).0; }`，
`last_raw` 非空就不会走兜底。所以**最终那一轮 `reply.content` 确实是空的**。

合起来就是：**provider 报告生成了约 200 token，但其中没有一行进入 `content`。**
上一轮「上游返回空」的说法太粗——不是「什么都没生成」，是**生成了但没走到 `content`**。

## 最吻合的解释（**未证实**）

读完循环代码，`conversation.rs:683` 这一段是唯一能吞掉正文的地方：

```rust
// 原生 tool-calls：回传 assistant(tool_calls) + 工具结果
if !reply.tool_calls.is_empty() {
    protocol = Some(ToolProtocol::Native);
    context.push(ContextMessage::assistant_with_tool_calls(
        reply.tool_calls.clone(),
        reply.reasoning_content.clone(),   // ← reply.content 一个字都没进来
    ));
    for call in &reply.tool_calls { ... dispatch(...) ... }
    continue;                              // ← 只有最后一轮的 content 会返回
}
```

**模型在同一条回复里同时给了正文和 `tool_calls` 时，正文被整个丢弃，只有最后一轮的
`content` 会返回给用户。** 而 `continue` 意味着中间轮次的正文全都进了上下文、用户永远
看不到。

把它和这页的处境拼起来：

- 该页 `area = imported`（素材原文，三层锁），`save_wiki_revision` 走 `revision` 会被
  `tool/mod.rs:1716` 的 `force_derivative` 直接 `bail`；
- `dispatch`（`tool/mod.rs:294`）把它包成 `ToolResultMsg::err` **继续循环**，不中断；
- 于是：工具被拒 → 模型再试 → 再被拒 → 4 轮预算烧完 → `content` 仍空 → 兜底道歉；
- **全程零写入**，所以 `wiki_log` / `wiki_revisions` 干干净净——与第一轮观察完全吻合；
- 200 token 花在反复构造工具参数上，也解释了 `completion_tokens` 为何不为 0。

02:13 那条能正常显示，是因为最后一轮模型放弃了工具、只回文字；而那句「稍等片刻」
是**第 0 轮的正文，被这一段吞了**。

**这条没能证实。** 工具调用不落库，`debug_eprintln!` 也不落盘。同样无法排除的还有：
推理 token 计入 `completion_tokens`、正文落在 provider 响应的其他字段里。

## 这暴露了上一轮修复的缺口

上一轮治了三处，**这一处不在其中**：

| 上一轮治的 | 本轮发现的漏网 |
|---|---|
| 空头预告（零工具调用时）被当成答案 | **正文与 `tool_calls` 同回时，正文被吞** |
| 空回复不重试、直接收敛 | 工具持续被拒时，重试仍会被同样地吞 |
| 兜底文案污染上下文 | （这条仍成立） |

更糟的是**修复会失效**：`future_promise_detected` 是在「本轮零工具调用」的前提下才
触发的回炉。模型一旦同回正文 + 工具，承诺检测根本不会被执行——被吞掉的正文里哪怕
写着「稍等片刻」，也没人看。

而且现有手段救不回来：`MAX_EMPTY_RETRIES = 1` 只是把同一条请求原样重发一遍，工具照样
被拒、正文照样被吞。**这类场景需要的是「把本轮正文透给用户」，而不是「再问一次」。**

## 附带发现：共享工作树把两个 agent 的提交混在了一起

调查过程中撞上一件与 AI 无关但更值得记的事。

另一个 AI agent（codex，分支 `codex/llm-wiki-completion`，worktree 在
`/tmp/elsewhen-llm-wiki`）**与本 agent 共用同一个工作树**。事故实录：

1. `11:59:59` 对方把 `codex/llm-wiki-completion` fast-forward 合并进 `main`（`1817f1f`），
   带来 `migrations/04-knowledge/`，活库 `user_version` 随之从 3 升到 4；
2. 我在 12:2x 用 `git mv` 把 5 个 `.sh` 移进 `scripts/`；
3. 对方在 `12:31:32` 提交 `e25ec25`（`test(wiki): 对齐 v4 迁移断言并完成闭环验收记录`），
   **用的是 `git add -A` 式全量暂存，把我这 5 个重命名一并卷了进去**：

```
e25ec25  test(wiki): 对齐 v4 迁移断言并完成闭环验收记录
  R100  elsewhen-capture.sh → scripts/elsewhen-capture.sh   ← 本 agent 的
  R100  elsewhen.sh         → scripts/elsewhen.sh           ← 本 agent 的
  R100  flutter-wrapper.sh  → scripts/flutter-wrapper.sh    ← 本 agent 的
  R100  regen.sh            → scripts/regen.sh              ← 本 agent 的
  R100  test_bridge.sh      → scripts/test_bridge.sh        ← 本 agent 的
  M     src/storage/new_migrations.rs                        ← 对方的
  + 4 个 wiki 文档                                            ← 对方的
```

**提交信息一个字没提文件搬家。**半年后没人查得清这 5 个文件为什么在这条提交里。

本 agent 随后的两次提交改为**逐个显式 `git add` 具体路径**，不再用 `-A`，未再卷入。

**教训**：共享工作树下，`git add -A` / `git commit -a` 是不可控的——它提交的不只是
「我改的」，而是「此刻工作区里全部未提交的东西」。两个 agent 各写各的，最终会被
彼此的提交信息错误归因。

## 复核结果与优化顺序（2026-09-29）

复核基于 `7e2b6c9`，使用独立工作区 `/tmp/elsewhen-empty-reply-review` 与临时数据库。三个脚本化 Provider 探针验证程序路径，不调用真实 Provider；探针只留在该工作区，未改主分支运行时代码。日志为 `/tmp/elsewhen-empty-reply-audit.log`，三项全部通过，含以下复现。

### 哪些推断需要撤回

| 原调查解释 | 代码和实验结果 | 现在能得出的结论 |
| --- | --- | --- |
| provider 实收 5452，与估算 3820 相比，说明单请求低估 1.43 倍 | `run_agent_loop_inner` 对多轮 usage 累加，外层一次落库；兼容重试还可能漏记被替换的第一次回复用量 | 这组数字不是同一请求的可靠对照，不能据此量化 tokenizer 误差 |
| `completion_tokens > 0` 说明最终回复有正文被吞 | 累计数可能含之前轮次的工具参数或推理消耗，provider 也未暴露推理用量明细 | 只能说明被记账的生成有消耗，不能判断最后一次生成了什么 |
| imported 页的 revision 在 dispatch 中不断被拒，直到四轮用尽 | `SaveWikiRevisionTool::run` 先成功写入 pending；`force_derivative` 在后续用户确认的 `execute_pending_action` 中才检查。实验复现“草拟成功 → 确认执行时报拒绝” | 该具体拒绝链条被推翻；其他工具错误仍可能消耗轮数 |
| 原生工具轮次的正文全进入上下文，只是用户看不到 | `assistant_with_tool_calls` 将 content 设为空，原正文既没回传给模型，也没保存为中间结果 | 中间上下文信息丢失是真缺陷；最后一轮若有正文，循环末尾 `last_raw` 仍可能把它返回 |
| 记忆层已完全排除 | 只测 `prepare_context` 没有覆盖随后追加的页面、引用说明和选材，也没有重建历史请求；工具定义等也不计入该估算 | 只能说原测量点的压缩没有裁消息，不能把整个记忆/上下文层宣告无关 |

### 已确认的程序缺陷

1. **缺少保证完成答复的收尾阶段。** 连续四轮原生 `list_rules` 全部成功、没有任何工具错误，最后仍返回空正文。预算只限制模型轮数，没有为“向用户总结工具结果”留出阶段。
2. **原生工具轮次丢失正文。** 第一轮同时返回有效分析和工具调用，后续回复为空时，原分析既不在回传上下文，也不在最终答复。这里确实存在可修复的信息损失，但不能直接断言历史故障走过此路径。
3. **空回复被过早当成协议不支持。** 首次 content 和 tool_calls 均空就去掉 tools 重试，没有依据区分推理输出、长度耗尽、内容拒绝或网关异常。重试前的回复被覆盖，usage 和该请求的诊断也随之遗漏。探针给两次请求分别配置 200/20 与 300/30 token，结果只记 300/30；正常两轮则累计为 500/50。
4. **上下文预算没有覆盖完整请求。** 估算只看 content，未覆盖工具定义、tool_calls 参数、reasoning_content 和消息协议开销；压缩保留系统主提示和最新用户消息，即使二者本身已超预算也不会强制拒绝。每轮另有 24,000 字符上限，但它不是 4096 token 的等价保证。中文粗估存在偏差风险，不能只调一个权重就宣称预算准确。
5. **页内意图与权限说明不一致。** 动态页内提示要求“在旧内容基础上修订”，没有按 `area` 明确区分原料和可编辑知识；工具描述却要求原料加工保存派生页，执行阶段才拒绝直接覆盖。这个矛盾会诱导生成最终无法确认的草稿。

关键实现位置：[对话循环](../../../../src/ai/conversation.rs)、[上下文消息和压缩](../../../../src/ai/memory.rs)、[Provider 解析](../../../../src/ai/provider.rs)、[工具草拟与确认执行](../../../../src/ai/tool/mod.rs)。

### 优化顺序

以下是复核时的优先级；当前收尾、协议正文保真、页内权限一致性已实现。逐请求诊断一项仅完成兼容重试用量补记，其余诊断和完整请求预算仍待后续处理。

| 优先级 | 改动 | 验证标准 |
| --- | --- | --- |
| P1 | 在工具轮数预算内预留最终答复阶段；总结时禁止新动作，若模型仍空则按已记录的工具成功/失败/待确认状态给确定性结果 | 工具成功、工具失败、草稿待确认、达到上限均有准确可读答复，不能把待确认说成已保存 |
| P1 | 原样回传原生 assistant 的 content、tool_calls 与必要的 reasoning 字段；正文作为中间记录保留 | 下一轮能看到已有分析；进度预告不会自动变成最终答案，也不把推理内容展示给用户 |
| P1 | 每次 HTTP 请求记录关联 ID、轮次/重试类型、finish_reason、content/reasoning 长度、工具名/成功状态和用量；兼容重试之前就记账 | 能分辨“上游空正文”“只有推理”“工具未收敛”“协议转换”，累计账目包含所有请求；默认不落完整正文或密钥 |
| P1 | 页内提示按 area 给出允许动作，草拟阶段提前验证目标操作；确认时仍重复校验，处理期间权限或内容变化必须拒绝 | imported 页能形成合法派生草稿，可编辑页走修订；不等用户确认后才发现动作从一开始就不允许 |
| P2 | 以最终序列化请求为预算入口，计入工具 schema 与协议开销；按模型配置上下文/输出预算，保留输出空间，并给无法压缩的请求明确错误 | 中文、长原料、大量工具参数和长最新消息都不靠截断协议对象来过预算；记录实际 usage 校准估算 |

不优先增加重试次数。相同失败会花更多钱，且更容易耗尽预算。也不直接把任意中间正文返回为最终答案：它可能只是“稍等片刻”，也可能含未经工具结果证实的保存声明。保留正文与确保最终状态准确，需要同时做。

Provider 配置中 `max_tokens = NULL` 只表示客户端没有显式设置，不能推出上游没有默认上限。应先采集 finish_reason 和模型预算语义，再决定默认值；思考型模型的输出预算不能一律设得很小。

### 历史故障还缺什么证据

现有库副本可以复核该页的历史消息长度和 usage 值，但没有当时每次请求的响应/工具轨迹；本次也未发现可用的历史 `agent-debug.log`。因此“历史故障就是工具正文被吞”仍未证实。应在副本中重放原请求，保留逐请求诊断，且把旧会话续聊与新会话对照分开。操作步骤见 [现有数据效果测试指南](../../../testing/llm-wiki-real-world-testing.md)。

### 共享暂存区事故的事实修正

`e25ec25` 确实包含另一工作流已暂存的五个脚本重命名，但本轮可见工具记录使用的是显式 `git add` 路径，未使用 `git add -A`。原因是随后普通 `git commit` 提交了整个共享 index，包含原本已暂存的变更。单靠“按路径 add”不足以隔离。应使用独立 worktree，或提交前核对 index 并用 `git commit --only -- <本任务路径>`；不能由提交内容反推必然执行过 `-A`。

## Alternatives considered

- 直接采用原调查的“工具被拒导致空回复”解释：确认执行发生在另一阶段，隔离实验与该具体链条相矛盾。
- 立即透出所有中间正文或增加重试次数：可能展示未执行的承诺和未核验的保存声明，也不能保证最终收敛。
- 只调整中文 token 权重：能改善部分估算，但无法补上工具定义、协议开销和系统主提示超预算时的处理。
- 只改兜底提示词：无法阻止修复预算耗尽后返回原预告，也无法在历史压缩后找回原任务；因此同时恢复持久化上下文、限制收尾工具派发并按实际状态兜底。
- 为每次对话另建后台任务队列：当前任务在一次生成调用内完成，不存在回复结束后自动续跑的契约；本次明确说明实际未完成状态，不伪造后台进展。

## Consequences

收尾和短追问恢复已落地，程序能在模型持续空回复或只给预告时交付基于实际状态的答复，并保留确认边界。代价是最多四轮中预留了一轮收尾，连续工具探索最多三轮；若模型仍不能完成，用户会得到明确未完成状态，而不是伪造结果或无限重试。短追问和空头承诺识别采用有限中文表达，不能保证覆盖所有语言和措辞。

历史故障仍缺逐请求轨迹，真实模型回答质量需在现有数据库副本重放验证；自动化通过不等于所有实际回答都合格。完整请求预算和逐请求诊断保留为独立后续工作。
