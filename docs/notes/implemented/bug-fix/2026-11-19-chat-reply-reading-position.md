# Agent Note: 三处对话的长回复与连续回复阅读位置

Status: implemented

## Problem

主对话的新消息监听不断追踪列表底部，知识页和目标讨论也在生成结束后强制滚到底部。长回复到达后用户只能先看到结尾，需要手动找回开头。一次返回多条回复、队列回复插入到后续输入前、先短后长以及回复继续增长时，单纯定位最后一条仍会漏过前面的内容。

## Decision

`ui/lib/widgets/chat_reading_controller.dart` 的 `ChatReadingController` 统一管理主对话、知识页对话和目标讨论的滚动策略；每个会话实例保有独立控制器。

- 首次历史加载和切换会话定位到最新；loading 不消费首次有效数据的定位。
- 用消息 ID 识别新增内容，按实际展示顺序选择第一条新增普通 assistant 回复；不以列表长度增加或最后一条作为判断条件。
- 接近底部时，短回复尽量完整展示，长回复定位到开头。以实际布局和稳定消息锚点定位，懒加载按可见窗口逐步寻找，包括向前插入的队列回复。
- 第一条回复建立本轮阅读锚点，后续连续回复、同一消息正文增长及重复刷新不自动推进。显式发送新输入或回到最新开始下一轮。
- 用户阅读历史时保持位置；拖动和滚轮使已经排队的自动定位失效。切换会话及卸载使旧定位回调失效。
- 主对话阅读期间保留显示窗口起点，新增回复不把正在读的消息挤出默认 20 条窗口；“显示更早”从实际窗口起点向前扩展。
- 知识页和目标讨论的 durable 与兼容生成路径均采用同一规则，不在生成结束的 finally 中强制滚动。主对话显式发送通过本地回调定位新输入。

## Alternatives considered

始终滚到底部：适合盯住生成末尾，却让长回复的开头和连续回复的第一条离开视口。

只定位最后一条 AI 回复：仍会跳过批量返回的前几条，也不能处理回复插入在后续用户输入之前。

按字符数判断长短并估算滚动距离：Markdown、代码、字体和视口宽度都会改变高度，使用实际渲染布局更可靠。

三处分别修补：生成结束、加载和 provider 更新各有不同入口，独立维护容易再次产生行为差异，因此共享策略和锚点逻辑。

## Consequences

用户可以从第一条新回复的开头连续阅读，后续回复不抢走位置。短回复后继续到达的内容可能出现在视口下方，由用户主动向下阅读。同一轮阅读期间，主对话显示窗口可能超过 20 条；列表仍按需构建，首次加载保持最近 20 条。定位只管理客户端视图，不修改消息、数据库或生成协议。逐帧定位具有取消标记和最多 40 次查找的边界。
